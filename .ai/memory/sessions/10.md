## THE UNRESOLVED BUG: Chrome hears nothing from the peer

### User-stated root cause and directive (verbatim, the spec to implement)

> Always: Create or resume context from inside a user gesture. Since
> the audio context is already created, resume it after user gesture.

Chrome's autoplay policy: an AudioContext created outside a user
gesture starts suspended, and a `resume()` called outside a gesture is
rejected — everything in the graph is then silent (remote playback
dead, analysers flat, outbound MediaStreamAudioDestinationNode track
silent).

### Where the code creates/resumes OUTSIDE a gesture today

`AudioGraph.resume()` is called from:

- `usePhoneCalls.startCall` / `acceptCall` — inside click handlers ✓
  (gesture-safe, intended design),
- `acquireLocalInput()` — from useCallMedia's attach effect
  (network-triggered, NO gesture),
- `addRemote()` — from pc.ontrack (network event, NO gesture).

If the first resume() on the Chrome side happens (or the context gets
created) via one of the gesture-less paths, Chrome keeps it suspended
and every later gesture-less `resume()` is a no-op → the user hears
nothing and the FFTs stay flat. The fix per the user's directive: never
create/resume outside a gesture; if the context already exists and is
suspended when media arrives, resume it from the NEXT user gesture
(e.g. resume inside every call-UI click — hangup included — and/or an
always-on document click/keydown listener that resumes it, the classic
autoplay-unlock pattern).

### Symptom timeline (user reports, chronological)

1. "Some device": I hear exactly what I said, can't hear the peer;
   "some device": peer FFT always flat.
2. Chrome: can't hear the peer. Safari: can hear the peer.
3. Firefox: LOCAL FFT flat too + can't hear the peer; Chrome still
   can't hear the peer. Firefox console:
   `callmedia: cannot open the microphone DOMException: The object can
   not be found here` (NotFoundError).
4. Safari ↔ Safari (iPhone/Mac): works completely OK — and per the
   user, always did.

Notes: "I hear exactly what I said" is consistent with acoustic
feedback now that echo cancellation defaults OFF (the toggle is the
remedy) — no loopback exists in the graph (MDN:
MediaStreamAudioDestinationNode has 0 outputs, no local playback).

### Confirmed-and-fixed quirks (already in the tree)

- **Firefox capture rejection**: Firefox's constraint solver rejects
  the whole getUserMedia (NotFoundError, "The object can not be found
  here") when the device backend lacks a NAMED capability
  (echoCancellation/noiseSuppression/autoGainControl) — even set to
  false. Since the toggle defaults OFF, captureConstraints() returned
  all-false and EVERY Firefox capture failed → flat local FFT, silence
  sent. Fix: `openMicrophone()` tries the constrained capture and falls
  back to plain `{audio: true}` on NotFoundError/OverconstrainedError;
  NotAllowedError (a real denial) is never retried. (Chrome is the
  opposite: omitting the constraints turns processing ON, so "off" must
  say explicit false — hence the try-then-fallback shape.)
- **Receive-side hardening**: the graph now binds the bare `ev.track`
  wrapped in `new MediaStream([ev.track])`, never `ev.streams[0]` —
  stream-association semantics differ across browsers, and a shared
  association stream can accumulate ended tracks whose id ordering
  decides which track a source node binds (MDN "Track ordering" note on
  MediaStreamAudioSourceNode). `MediaStreamTrackAudioSourceNode` is NOT
  an option: undefined in the probed Chromium and unsupported in
  Firefox.

### Diagnostic logging in place (grep `[audiograph]`)

- `context created: <rate>Hz, state=<state>` and `resumed: state=…`
  (from resume()),
- `mic captured: ctx=…Hz, track settings=…` (the capture),
- `remote connected/muted/unmuted/ended: id=… muted=… ctx=…`
  (the receive path).

On the next Chrome test these pinpoint the dead layer: ctx suspended →
autoplay/gesture issue (the user's diagnosis); track live+unmuted but
analyser flat → graph issue; track never unmutes → wire/negotiation
issue.
