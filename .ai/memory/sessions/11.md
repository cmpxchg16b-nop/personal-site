# Session 11

Fixed the cross-browser voice-call bug handed off from session 10.
IMPORTANT: the user warned not to fully trust 10.md, and verification
confirmed several of its claims were FALSE — the tree did not contain
the "already fixed" Firefox fallback, the `[audiograph]` logging, or
the bare-track receive binding; and the "stale 48 kHz doc mentions" it
flagged in docs/signalling-server.md and 9.md did not exist (grep:
48000 appears only in 10.md itself). This session re-implemented all
of it for real.

## The two real bugs (verified against the tree)

1. **Firefox: mic capture always failed** (`callmedia: cannot open the
   microphone DOMException: The object can not be found here`).
   `acquireLocalInput` passed explicit
   `echoCancellation/noiseSuppression/autoGainControl: false`
   constraints; Firefox's constraint solver rejects the whole
   getUserMedia with NotFoundError when the device backend lacks a
   NAMED capability — even set to false. No fallback existed.
2. **Chrome: no recovery from a suspended AudioContext.** resume() was
   called from gesture-less paths (`acquireLocalInput` from the attach
   effect, `addRemote` from pc.ontrack); per Chrome's autoplay policy a
   resume() outside a user gesture stays pending forever, so a context
   found suspended there left the whole graph silent — dead remote
   playback and flat remote FFT on the receiver, and a silent
   MediaStreamAudioDestinationNode track on the wire. Symptom match:
   Safari↔Safari worked (WebKit starts the context on the gesture-less
   resume), any Chrome end failed.

## The fix (all in web/site/src/api/audio/audiograph.tsx unless noted)

- **Autoplay unlock (the user's MDN directive).** `resume()` still
  creates/resumes the context and is still invoked from the call UI's
  click handlers; in addition, the context's `statechange` event keeps
  a "gesture unlock" armed exactly while the state is `suspended`:
  capture-phase `pointerdown`/`keydown`/`touchstart` listeners on
  `document` (UNLOCK_EVENTS) that call `ctx.resume()` — so the next
  real gesture anywhere (any click, incl. hangup/volume) revives a
  suspended context. Disarmed on `running`/`closed` and in release().
  The statechange closure captures its context and bails when
  `this.ctx !== ctx`, so a stale context's events never disarm a newer
  context's unlock. Capture-phase document listeners fire before any
  MUI popover/portal stopPropagation.
- **Firefox capture fallback.** New `openMicrophone()`: tries the
  constrained capture, and on NotFoundError/OverconstrainedError
  retries plain `{ audio: true }` (the browser's default processing
  stands); NotAllowedError (a real denial) is never retried. Chrome
  still needs the explicit `false`s — omitting the constraints turns
  the processing ON there — hence try-then-fallback, not omit.
- **Receive-side hardening** (useCallMedia.ts): the graph now always
  binds the bare `ev.track` wrapped in `new MediaStream([ev.track])`,
  never `ev.streams[0]` (association streams can accumulate ended
  tracks whose ordering decides which track the source node binds —
  MDN "track ordering" note on MediaStreamAudioSourceNode).
- **Diagnostics** (grep `[audiograph]`, console.info): context created
  (rate + initial state), context state transitions, "resuming the
  context on a user gesture", mic captured (ctx rate + track settings —
  shows whether the constrained or fallback capture succeeded), remote
  connected (track muted/readyState/ctx state), remote muted/unmuted.
- Docs: docs/signalling-server.md "Media and audio" bullet rewritten —
  it claimed "the capture is plain getUserMedia by default", which
  matched neither the old code nor the new.

## Reading the logs on the next live test

- `context created: … state=suspended` on a side whose user already
  clicked → autoplay blocked the start; the unlock should follow with
  "resuming the context on a user gesture" then `state=running`.
- Sender's `mic captured` present + `state=running` but the receiver
  never logs `remote connected` → the track never arrived:
  negotiation/wire issue (PerfectNegotiator), NOT audio. That would be
  a new bug layer; negotiate.ts looked textbook on re-read.
- `remote connected … muted=true` with no `unmuted` → the wire track is
  being fed silence: check the SENDER's context state line.
