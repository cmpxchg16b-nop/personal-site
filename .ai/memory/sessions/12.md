# Session 12

The "Chrome hears nothing from the peer" bug (handed off from sessions
10/11, whose files are deleted) is ROOT-CAUSED and FIXED. It was never
the autoplay policy, the audio graph wiring, or the negotiation: it is
a long-lived Chromium bug, and the fix is the dummy media element.

## Root cause: chromium issue 40094084

Chrome never decodes a WebRTC-received MediaStream that is only
attached to WebAudio. The RTP packets arrive at the transport and are
discarded before the decoder (`packetsDiscarded ≈ packetsReceived`,
`totalSamplesReceived: 0` in getStats), the received track stays muted,
and every `MediaStreamAudioSourceNode` tap — the audible path AND the
FFT analysers — sees pure silence. Safari and Firefox decode such
streams natively, which is why only Chrome ends were deaf. References
(user-supplied):

- https://issues.chromium.org/issues/40094084 — "MediaStream from RTC
  is silent (in WebAudio, MediaRecorder, etc.) if not attached to a
  media element". Open since 2019, present since M56, still unfixed.
- https://stackoverflow.com/questions/74263974/ — same symptom; the
  accepted answer names the workaround: a muted `<audio>` element.
- https://stackoverflow.com/questions/55703316/ and
  https://stackoverflow.com/questions/24287054/ — same bug, other
  shapes.

Corollary: the receive side was the only broken layer. The SEND path
(mic → gain → analyser → MediaStreamAudioDestinationNode track → wire)
always worked — Safari heard the Chrome peer, and the outbound RTP
carried real audio energy. Session 10/11's gesture-resume/unlock work
was correct hardening but could not fix this: the AudioContext was
running on the deaf ends.

## The fix: a dummy muted `<audio>` element per remote stream

With any media element pulling the received stream, Chrome decodes and
the WebAudio graph gets the samples. Implemented in
`web/site/src/api/audio/audiograph.tsx`:

- `RemoteEntry` gains `element: HTMLAudioElement`.
- `addRemote` additionally creates a DETACHED, MUTED `<audio>` element
  with `srcObject = stream` and plays it. Muted, because the graph
  alone carries the audible path through the remote gain (the speaker
  volume). Detached (never appended to the document) is sufficient —
  verified — and the entry's reference keeps the element from being
  garbage-collected, which would stop the pull. Muted autoplay is
  gesture-free, so `play()` from the network-triggered ontrack path is
  allowed; a rejection is logged and non-fatal.
- `removeRemote` pauses the element and clears its `srcObject`
  (release() tears down through removeRemote as before).

Docs: `docs/signalling-server.md` ("Phone sessions → Media and audio")
now states the Chrome limitation and the element workaround.

## Validation

- `npx tsc --noEmit`, `npm run lint -- --quiet`, `npx prettier --check`
  clean.
- Live two-party call, Chrome↔Chrome on this machine: before the fix
  both receivers discarded ~98% of packets and decoded zero samples;
  after the fix, zero discards and millions of decoded samples each
  way, both CallPanel spectrum canvases live. The user also confirmed
  audibility in a manual e2e test.
