# Session 14

The phone-session wire protocol is SIP-lized. Two user directives drove
it: (1) unify `application/x-phone-session` and
`application/x-phone-session-event` — both are behavior, both drive the
session state — into ONE SIP-subset message kind with the SDP body
stripped; (2) SIP-like messages must NEVER be echoed — "the behavior of
the application must not rely on the echoing of SIP-like message" —
with true separation between chat control and SIP. Chat control was
left untouched except where the refactor forced it.

## The new wire format (`application/x-sip`, body `sip: DCSip`)

datachannel.tsx. One MIME, one builder (`newSipDCMsg`), one validator
(`isWellFormedSip`) — the old pair of each is gone. DCSip mimics SIP:

- `callId` — the dialog identifier, SIP's Call-ID; created by the
  caller's INVITE, named by every later message of the dialog. (The
  field rename sessionId → callId propagates through usePhoneCalls,
  types.ts's ActivePhoneCall/PhoneCallMessage, useChatMessages.)
- The start line is a request XOR a response: `method?: "INVITE" |
"CANCEL" | "BYE"` or `response?: DCSipResponse`. Responses are the
  paired consts DC_SIP_RESPONSE_OK ({code:200, phrase:"OK"}) and
  DC_SIP_RESPONSE_DECLINE ({code:603, phrase:"Decline"}) — the pairing
  is enforced by the union type and by isWellFormedSip.
- Extension headers (SIP's X-* convention) carry what standard SIP
  can't: `X-Media?: "voice"|"video"` (INVITE only — STANDS IN FOR the
  stripped SDP body's m= lines; absent means voice) and
  `X-Call-Status?: DCCallStatus` (INVITE only — the UI overlay, see
  below). isWellFormedSip rejects X-headers on non-INVITEs.

Verb map: invite → INVITE; accept → 200 OK; reject → 603 Decline;
cancel → CANCEL; end → BYE. The statuses (DC_CALL_STATUSES, the old
DCPhoneSessionStatus renamed DCCallStatus; kind likewise DCCallKind)
are unchanged: inviting < accepted < ended < cancelled < rejected, fold
= precedence max — `statusEstablishedBy(sip)` maps each message's start
line onto the state it establishes (INVITE → inviting is the floor).

Documented omissions (in the DC_MSG_MIME_SIP comment — keep it
accurate): no SDP body (this system's real SDP offer/answer rides the
SS's client-to-client relay between the two PerfectNegotiators — that
is where "the SDP" lives, hence stripped here); no ACK, no CSeq (SCTP
ordered+reliable; the fold is order-independent); From/To live on the
DCMsg envelope.

## THE BIG ONE: SIP is never echoed

The echo bounce is a CHAT-layer mechanism; SIP now opts out of it
completely:

- Receive path (useDataChannel's dc.onmessage): the
  `dc.send(encodeDCMsg({ ...msg, echo: true }))` bounce is skipped for
  DC_MSG_MIME_SIP.
- Send path (sendTo): after a successful `dc.send`, a SIP message is
  recorded LOCALLY as the sender's own copy:
  `setDcMsgs((prev) => applyDCMsg(prev, { ...msg, echo: true }))`. The
  echo flag on the STORED copy marks "our own send" — it is never on
  the wire frame (a wire frame with echo set would key the conversation
  to the wrong peer). Dropped sends (channel not open) store nothing —
  no phantom calls.
- Consequence: own sends take effect at send time, not after the
  echo round-trip. The derivation's convergence argument is unchanged:
  each end folds its own sends (recorded locally) + the peer's sends
  (received) — the same frame set as before.
- The DCMsg.echo doc comment now states the dual meaning; the
  file-header comment, UseDataChannelResult docs, and the
  DC_MSG_MIME_SIP "No ACK, no CSeq, and no echo" bullet all spell out
  the carve-out.

Chat control keeps its own echo discipline (sender applies its amend
when the echo returns) — a separate layer the SIP dialog never depends
on. Its one forced touch: DCChatControl.phoneSession → `.sip?: DCSip`,
and applyChatControlDCMsg's phone branch now requires BOTH target and
payload to be INVITEs naming the same callId (an amend can no longer
turn a stored INVITE into anything else). The UI-state layer is
unchanged in shape: the INVITE's stored X-Call-Status is the log
entry's status; only the caller (INVITE's author) amends it when the
folded protocol state drifts; self-terminating via the chat-control
echo.

## Derivation and rendering

- usePhoneCalls: per conversation collect ALL sip messages; the latest
  INVITE (by creationTimestamp) is the current session, earlier ones
  are log entries; fold every message with a matching callId (the
  INVITE included — it folds to inviting, precedence 0). kind =
  `invitation["X-Media"] ?? "voice"`, loggedStatus =
  `invitation["X-Call-Status"] ?? "inviting"`. Senders: startCall sends
  the INVITE (fresh callId UUID, X-Media kind, X-Call-Status inviting,
  audio.resume() still inside the click gesture); the `say()` helper
  sends `{ callId, ...startLine }` — acceptCall → 200 OK, rejectCall →
  603 Decline, hangupCall → BYE once accepted, CANCEL while ringing.
- useChatMessages: skips non-INVITE sip messages (`m.sip?.method !==
"INVITE"` — responses/CANCEL/BYE are protocol frames, not renderable);
  INVITEs become PhoneCallMessage as before.
- UI components untouched: types.ts keeps the PhoneSessionStatus /
  PhoneCallKind aliases (now = DCCallStatus / DCCallKind) so
  PhoneCallItem / ChatApp / CallPanel / IncomingCallWindow compile
  unchanged.

## GOTCHAS

- TS narrowing in isWellFormedSip: after the request-XOR-response
  check, `sip.method` stays `DCSipMethod | undefined` to the compiler
  (it can't correlate two optionals) — extract `const method =
sip.method` and re-check undefined before `.includes(method)`.
- Wire INCOMPATIBLE with x-phone-session*: old-format frames hit no
  mime branch and are dropped as unknown kinds. Both ends must run the
  new build. No migration (in-memory store only).
- A peer running old code that DID bounce a SIP frame would
  double-store the caller's INVITE (local copy + bounced copy) →
  duplicate log entries. Not defended against — same-version
  deployments only.
- docs/signalling-server.md was rewritten for the SIP framing (echo
  bullet, mime table, chat-control paragraph, the whole Phone sessions
  section) — and a pre-existing dangling fragment ("amend the
  invitation with).") at the end of the dead-session bullet was
  removed.

## Validation

`npx tsc --noEmit`, `npm run lint -- --quiet`, `npx prettier --check`
clean. No live browser test from here — needs the user's two real
browsers; the call flow to verify: INVITE rings the callee, 200 OK
attaches media both ends, BYE/CANCEL/603 settle the log entries
identically on both sides, and (new) the caller's outgoing panel/log
entry appear INSTANTLY at click time (no echo round-trip).
