# Session 16

The deliverable: `HeadlessRTCClient` in `pkg/rtc` (`client.go` +
`transport.go`) — the Go counterpart of the browser's `useSignalling` +
`usePeerSessions`, i.e. a headless RTC peer that is "more of a bot than a
full client" (the user's framing). Multi-peer by design: one peer session
(pion pc + Negotiator) per channel member, negotiators built through an
injected `NegotiatorFactory`.

## API shape (mirrors the established contracts)

- `NewHeadlessRTCClient(NegotiatorFactory, RTCClientConfiguration)`.
  `PerfectNegotiatorFactory` adapts `NewPerfectNegotiator` (Go func types
  are return-invariant, so the adapter exists). Config: ChannelId (default
  main), SubscriberId (empty = SS-assigned), Username, ICEServers,
  NewPeerConnection override, KeepAliveInterval/MemberListInterval/
  ReplyTimeout (defaults 5s/5s/5s, mirroring the browser's, well below the
  SS's 10s default aging), Logger. NO transport knobs — see below.
- `Run(ctx, ssEvIn <-chan, ssEvOut chan<-) error` — EXACTLY the
  `Negotiator.Negotiate` / `SignallingServiceProvider.Run` channel
  contract (the SSProxy read/write stream pair in channel form). The
  client knows NOTHING about websockets/auth; the caller wires the pair
  to a transport. Returns nil on ssEvIn close, ctx.Err() on cancel,
  registration error, or ErrAlreadyRunning. Re-Run after return is fine
  (handlers persist, like http.ServeMux patterns).
- `HandleDataChannel(label, DataChannelHandler)` + `HandleDataChannelFunc`
  — the http.ServeMux.Handle mirror: panics on nil handler / duplicate
  label (dup detected on the hub, panic re-raised on the caller's
  goroutine via the note's ack). `DataChannelHandler.ServeDataChannel(ctx,
  channelId, peer, dc)` — ctx is the SESSION's context; dc may still be
  connecting (attach OnOpen/OnMessage). Invoked once per (session, label)
  incarnation, on its own goroutine, panics recovered+logged. The client
  hardcodes NO labels — dcmsg/dcbin are the caller's business.
- `SubscriberId()`, `Peers()` — note/reply queries to the hub.
- `transport.go`: `SignallingTransport` interface (same channel
  signature, producer closes its outbound) + `WebSocketSignallingTransport`
  (gorilla; URL/Header/Dialer/WriteTimeout=10s default). The endpoint is
  NOT on the JWT whitelist — Header carries the session cookie.

## CSP hub — the interesting part

Per the user's directive, NO mutexes: one hub goroutine (started in the
CONSTRUCTOR, lives for the client's lifetime like the provider's Run)
owns all state; everyone else coordinates via an internal `serviceChan`
of sealed `clientNote` types: runNote (Run attach), handleNote
(HandleDataChannel), announcedNote (pion OnDataChannel), rebuildNote
(glare rebuild — see below), selfNote/peersNote (accessors). While no Run
is in flight, the run-scoped select cases are nil channels (the
nil-channel idiom), so one select serves both phases.

- Registration happens INLINE on the hub before the main loop (provably
  nothing can reach the client pre-registration: the SS cannot resolve
  its address), bounded by ReplyTimeout, with the browser's
  retry-once-with-empty-id on SubscriberIdIsRegistered.
- Listing rounds are hub state (msgId + accumulated members), superseded
  by the next tick if incomplete — no waiter map needed.
- Sessions reconcile against each completed listing round (start new,
  close dropped), PLUS adopt-on-offer: an inbound c2c offer from an
  undiscovered peer creates the session (the browser loses that race for
  up to one listing interval; a headless client can simply not lose the
  offer).

## THE DEADLOCK TRAP: rebuild-through-hub vs hub→session send

The glare rebuild factory is invoked on the NEGOTIATOR's goroutine but
mutates hub-owned session state → it must post a rebuildNote and WAIT for
the reply. If the hub could meanwhile block sending to that session's
input channel: hub waits for negotiator, negotiator waits for hub —
deadlock. Fix: each session has a pumpIn goroutine — the unbounded-queue
idiom (nil-channel-gated output case) between the hub-facing channel
(buffered 16) and the negotiator's input — so the hub's send can never
wedge behind a busy negotiator. The hub's own sends to run.out (register/
keepalive/listing) keep the negotiator's documented contract: they block
with a ctx escape hatch (transport backpressure).

## Pion finding: the post-rebuild re-offer is TIMING-DEPENDENT

The client test `TestHeadlessRTCClientSurvivesGlare` (scripted impolite
raw peer colliding an offer through the full stack) flaked: the bot's
re-offer of the re-created channel sometimes never comes. Root cause in
pion v4.2.18 (peerconnection.go:1095): entering stable CLEARS
isNegotiationNeeded and re-arms negotiationNeededOp, but
checkNegotiationNeeded then returns FALSE because data channels multiplex
over the single SCTP application m-line, which the answer to the
colliding offer already carries. Whether a re-offer fires depends on the
ops-chain interleaving — and it DOESN'T MATTER: the re-created channel
opens via DCEP over the established SCTP association regardless. The test
now answers a re-offer if one arrives within a short window and proceeds
otherwise. (This also means the rebuild's channel restoration never
depended on the re-offer at all.)
