# Session 17

The deliverable: `pkg/rtc/echobot` — the reference data-channel stack of
an echo-purpose bot on `HeadlessRTCClient` (session 16's framework; the
client itself hardcodes no labels). Three files: `dcmsg.go` (the DCMsg
codec), `dcbin.go` (the binary frame codec), `echobot.go` (the bot). It
started in `pkg/rtc` and was moved into the subpackage on the user's
request; the move renamed the exported API to kill the stutter:
`echobot.New(client, echobot.Configuration{Logger})` returns
`echobot.Bot` (was `NewEchoBot`/`EchoBotConfiguration`). Construction
registers both well-known labels (`DataChannelLabelMessages = "dcmsg"`,
`DataChannelLabelBinary = "dcbin"`) on the client; duplicate labels panic
through `HandleDataChannel`.

## dcmsg: decode raw, echo verbatim

The decoder keeps the frame's top-level fields as
`map[string]json.RawMessage` and validates via helpers
(`requiredStringField`, `optionalStringField`, `optionalBoolField`,
`requiredNumberField`, `requiredIntField`) that mirror the frontend's
`decodeDCMsg` checks EXACTLY, null-parity included (a present-but-null
optional field is malformed, since `x !== undefined` there). The bounce
is `raw["echo"] = true` + re-marshal — byte-faithful, unknown fields and
number literals preserved, the mirror of `{...msg, echo: true}`. The
frontend does NOT validate `mimeVersion`/`creationTimestamp`/`inReplyTo`;
neither does the bot.

Echo discipline (mirrors useDataChannel): echoes are never re-echoed (the
loop guard; the bot keeps no message store, so no from/to check needed);
SIP (`application/x-sip`) is never bounced; everything else is bounced —
including chat-control (the sender applies it on echo; the bot never
applies, it has no UI state).

The echo-purpose additions (user-specified):

- `text/plain`: after the bounce, ALSO send a fresh plaintext DCMsg with
  identical content and `inReplyTo` = the original msgId.
- file-transfer-status: bounce, and record fileId → announcing msgId per
  peer, so the dcbin-side hash report can thread onto it.
- SIP INVITE (voice or video): answer `603 Decline` (bare response body:
  callId + `{code:603, phrase:"Decline"}` — X-* headers are INVITE-only,
  `isWellFormedSip` rejects them on responses). CANCEL/BYE: ignored.

Outbound frames are built with `newDCMsgOut` (generates msgId, stamps Unix
seconds like `Date.now()/1000`) + field assignment + `encode()` — the
shared base of the frontend's three builders.

## dcbin: reassemble, ack, hash on the fly

`dcbin.go` ports binaryframes.ts (BE ints, FILE 48-byte header, FACK 32
bytes; payload_size doubles as the consistency check). Only the FACK
encoder exists — the bot never sends files. The reassembly mirrors
`useBinaryDataChannel.handleFrame`: first frame must be seq 0/offset 0;
every frame must continue the contiguous prefix (`total` match, seq, offset,
no overflow past `total`); corruption drops the transfer (state deleted,
frame unacknowledged; a seq-0 retransmission restarts cleanly). Every
ACCEPTED frame gets a cumulative FACK; a failed ack is logged+swallowed
(it only stalls the sender's window).

The hash design went through three user iterations — (1) store the file
in memory, (2) cap retention+hash at a configurable max (400 MiB default)
while acking past the cap, (3) FINAL: no cap, no retention at all. The
sha256 is computed on the fly and reported LIVE over the session's dcmsg
channel: first accepted chunk → a new `sha256:<hex>` plaintext message
(`inReplyTo` the announcement when known); every later non-empty chunk →
a chat-control `amend` of that message. An empty file reports
`sha256:e3b0...` at its single frame. The bot's own outbound amends are
legal chat control: they target the bot's OWN hash message (the frontend
applies amends under the sender's list).

## The cross-channel bridge

The hash reports ride dcmsg but are triggered on dcbin — so the bot keeps
a `peers` registry (mutex-guarded): each `serveMessages` invocation
records the session's dcmsg channel (plus the announcements) and a
ctx.Done goroutine drops the entry, replace-safe across glare rebuilds
(delete only if same entry pointer). Per-session dcbin reassembly state is
invocation-local heap captured by the OnMessage closure — session
teardown collects it; no explicit purge needed (unlike the frontend's
subscribeReset maps).

One struct `Bot` owns both handlers — justified by the bridge. The bot's
self id comes from `client.SubscriberId()` per handler invocation (always
registered by then: sessions exist only inside a run).

## Tests and the environment finding

`echobot_test.go` duplicates the client_test.go harness (clientTestNet,
startClient, waitFor — test-only helpers don't cross packages) and adds a
`wireProbe` speaking RAW wire frames (map-built JSON, hand-rolled FILE
encoder, independent FACK decoder) so the bot is tested against the
documented formats, not its own codec. 8 tests: text bounce+reply
(incl. unknown-field fidelity, impolite bot), echo never re-echoed,
chat-control bounce-without-reply, voice+video declines + CANCEL/BYE
silence, 10 malformed-frame drops, the full file flow (announcement
bounce, cumulative FACKs, initial hash + per-chunk amends with correct
targets and inReplyTo), empty file, corrupt-stream drops.

FINDING: under `-race` on a loaded machine a pion handshake takes
SECONDS (the `pkg/rtc` suite shows the same ~5s/test floor; it survives
because its waits stay under its 10s timeout). The echobot suite's waits
(channels + multi-frame exchanges) crossed 10s at `-count=2`, so its
testTimeout is 30s. Validated: `gofmt`/`go vet` clean;
`go test -race -count=2 ./pkg/rtc/...` green; whole-repo `go test
./pkg/...` green. (Pre-existing gofmt drift in unrelated files —
pkg/auth/jwt.go, pkg/session/session.go, etc. — left untouched.)

## Follow-ups / open items

- Still no binary consuming echobot (cmd/server has no bot); a real
  deployment needs the JWT story for the WS transport first.
- The bot amends per 16 KiB chunk (no throttle, per spec) — a 400 MiB
  file is ~25k amends; fine for a testing bot, worth revisiting if it
  ever fronts real traffic (the frontend throttles its own status amends
  to 4/s).
- Two echo bots pointed at each other loop forever on plaintext replies
  (reply-to-reply). Inherent to the echo purpose; not guarded.
- The peers registry leaks nothing but the announced-msgId map of a
  rebuilt session resets — a hash report concurrent with a glare rebuild
  may lose its inReplyTo thread.
