# Session 19

The deliverable: the `sign` subcommand — session 18's "issuing helper"
follow-up, done as a proper kong subcommand pair. The binary's CLI split
into `ServeCmd` and `SignCmd` (the user rejected both the bolted-on
subcommand field on a flat serving CLI AND a default-command design):
`server serve ...` serves, `server sign ...` issues a session JWT and
exits. Bare `server` errors with kong's own "expected one of serve,
sign".

## The split (cmd/server)

Root `CLI` now holds only what both subcommands share — the JWT secret
indirection (`--jwt-auth-secret-from-env` / `--jwt-auth-secret-from-file`)
and `--jwt-issuer` — plus the two `cmd:""` fields; every other flag moved
into `ServeCmd` (addr, config-xml, ss-aging, healthz-probe, blacklist,
visitor knobs, nonce lifespan). Dispatch is idiomatic kong, no manual
`ctx.Command()` switching (the user's correction): `main` is just
`ctx := kong.Parse(&cli); ctx.FatalIfErrorf(ctx.Run())` — kong's RunNode
binds every target of the selected path, so each subcommand's
`Run(cli *CLI) error` receives the root flags automatically. Root flags
must precede the subcommand word (`server --jwt-auth-secret-from-file f
sign ...`); usually moot since the env var defaults to JWT_SECRET and
loadDotEnvFiles still runs before kong.Parse.

Every pre-subcommand invocation had to gain the `serve` word:
e2e's startServerOnAddr, the Dockerfile HEALTHCHECK
(`serve --healthz-probe`), scripts/personal-site.service's ExecStart,
and the README's `go run ./cmd/server serve ...` snippets.

## SignCmd (cmd/server/sign.go)

Flags: `--sub` (required — the signalling endpoint 400s identity-less
tokens), `--jti` (empty = fresh uuid per invocation), `--username` (the display
name claim), `--validity` (default 720h; 0 = NO exp claim — the direct
answer to session 18's "the config-file JWT expires and the bot
reconnect-loops into 401s"; negative rejected). The claim set mirrors
what every login handler signs (VisitorLoginHandler.GetMapClaims et al.):
sub, jti, aud=["session"], nbf=now, exp=now+validity, username. No iss —
the validator never checks it and no handler sets it (the issuer name
only guards IssueToken against an empty value). The token alone goes to
stdout (shell-composable); a sub/jti/username/expiry summary goes to
stderr via the slog logger.

## e2e (e2e/sign_test.go)

Four tests against the real binary: claim-set shape + fresh-jti-per-invocation
(`TestSignClaims`, parsing with a validator over the e2e throwaway
secret), the no-expiry path (`TestSignNoExpiry`), kong's required-flag
rejection of a sub-less invocation (`TestSignRequiresSubject`), and the loop
closed against a running server (`TestSignTokenAcceptedByServer`: the
issued token authenticates GET /api/profile as a bearer, and the profile
reflects the token's sub/jti/username).
