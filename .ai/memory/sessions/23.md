# Session 23

The deliverable: the echo bot's data-channel handler is split in two. A
new package, `pkg/rtc/msg_handler`, carries the `BotMessageHandler`
interface (plus `ResponseWriter` and the message types) and a generic
`Server` that owns every sub-message protocol mechanic; `pkg/rtc/echobot`
shrinks to the echo policy alone. The bot is now three layers — bot
client (`HeadlessRTCClient`) → DC handler (`msg_handler.Server`) →
message policy (`BotMessageHandler`) — the split modeled on net/http,
which the client's `DataChannelHandler` already mirrored.

## The interface (user-specified, refined)

`BotMessageHandler` has the four mandated methods, each returning nothing
(the ServeHTTP shape): `HandleChatMessage(ctx, *ChatMessage, w)`,
`HandleFileChunk(ctx, *FileAnnouncement, *FileChunk, w)`,
`HandleAttachment(ctx, *FileAnnouncement, *Attachment, w)`,
`HandleCalling(ctx, *SipMessage, w)`. The announcement param is nil when
no announcement was seen (cross-channel ordering is not guaranteed — same
fallback semantics as the old unthreaded hash report).

`ResponseWriter` (bound per invocation to the handled message): `Reply
(text) (MsgId, error)` threads on the handled message — on the
announcement for chunks/attachments — and returns the new msg id so a
later `Amend(target, text)` can rewrite it (that pair IS the hash-report
flow). For calls: `Reject(code, phrase)` (works today: 603 Decline) and,
per user directive, shaped on webrtc's design — `Accept(tracks
...webrtc.TrackLocal)` mirroring `PeerConnection.AddTrack`, `OnTrack(fn)`
mirroring `PeerConnection.OnTrack` with `*webrtc.TrackRemote`. Both are
inert today (`ErrMediaUnsupported` / never fires): HeadlessRTCClient has
no track support. Also `ErrNotACall` (not an INVITE) and
`ErrNoMessagingChannel` (peer's dcmsg not up). Send errors are RETURNED
now (was: log-and-swallow-bool); the echo handler logs them.

## What stays in the Server (user directives, both enforced)

- **File assembly is the DC handler's.** Reassembly AND byte
  concatenation live in `binarySession`/`inboundTransfer` (moved from
  echobot.go); the handler only ever sees high-level constructs
  (`FileChunk`, `Attachment` with assembled `Data`). Deliberate behavior
  note: bytes now materialize transiently per transfer (the frontend —
  the source of truth — buffers the whole Blob too); the echo handler
  still retains nothing.
- **No framework state, no handler locks (two user directives).** An
  intermediate cut carried per-transfer handler state on `FileChunk.State
any` — rejected: a file chunk is a file chunk; framework types carry no
  user state, and how a feature keeps its state is the handler
  implementer's own affair (the Telegram-bot-framework shape). The
  running-sha256 reporting is therefore decoupled from the handler into
  `hashreport.go`'s `hashReporter` — a `sync.Map` keyed by (peer, file
  id): one transfer's chunks are serialized by the Server (documented as
  an interface guarantee), so a report's fields are single-goroutine and
  only the map is shared. No mutex, no actor, no framework support.
  Known bound: a transfer the Server drops mid-stream (corrupt) or tears
  down with its session leaves its report entry behind (the pre-refactor
  code kept it in inboundTransfer, which died with the transfer); bounded
  by the number of aborted transfers.

Also moved into msg_handler: the dcmsg/dcbin codecs (dcmsg.go/dcbin.go,
package-renamed), the hub (now storing the full `*FileAnnouncement` per
canonical file id — `decodeFileTransferBody` returns a metadata struct,
not just the id — because Attachment metadata comes from the
announcement), and the well-known label constants (echobot keeps aliases,
so e2e/tests are untouched). `dcMsgIn` gained `timestamp` (from
`creationTimestamp`; new `optionalNumberField`). echobot.New returns
nothing now (the Bot type is gone; both call sites discarded it).

## Wire behavior: unchanged

Bounce discipline, drop rules, the 603 decline flow, FACK cadence, the
hash-report throttle (open on first chunk, amend per 500, final always —
22's semantics), the empty-file single report. The echobot suite passes
with ONE kind of change: its decode side now uses an independent `rawMsg`
decoder (`decodeMsgRaw`) — the suite's own stated philosophy, made real
now that the production codec is unexported in another package; the
encode side was already independent.

Docs: signalling-server.md's bot paragraph rewritten for the three
layers; its stale "amended per chunk" (superseded in 22) fixed.

## Follow-ups / open items

- msg_handler has no suite of its own (covered via echobot's wire suite);
  a stack suite with a scripted non-echo BotMessageHandler would pin the
  interface itself (nil-announcement paths, writer errors).
- The hashReporter leaks an entry per aborted transfer (above); a
  per-session purge (the Server never tells the handler a transfer died)
  would need a framework hook — deliberately not added.
- Accept/OnTrack are inert until HeadlessRTCClient grows media support:
  the browser attaches mic/camera tracks to the pair's EXISTING peer
  connection and lets perfect negotiation renegotiate; the client would
  need an AddTrack analog plus OnTrack dispatch.
- Inbound chat-control messages are bounced per protocol but not surfaced
  to BotMessageHandler (no method; the echo bot keeps no store) — a
  future HandleChatControl could.
- The Server has no Close (hub lives for the Server's lifetime — same
  lifetime story as the client's hub).
- Still open from earlier sessions: c2c ping/pong unanswered by headless
  clients (16); the config-file bot JWT is never refreshed (18/19/20);
  the React "Maximum update depth" near datachannel.tsx (22).
