# Session 26

The report: a FLAC song "sounds weird" when re-streamed through the
music bot, but plays fine in any normal player. The resolution: the
bot sends **stereo opus without ever negotiating `stereo=1`**, so every
browser builds a **mono decoder** and downmixes the wide-stereo mix on
the fly — up to ~31% of the stereo (side) energy collapses, which reads
as thin/hollow/"weird" against the original. The decode/encode pipeline
itself was **bit-exact throughout**; the bug was purely in SDP codec
negotiation.

## Root cause

- pion's default media engine registers opus with fmtp
  `minptime=10;useinbandfec=1` — **no `stereo=1`**. The track's own
  `opusTrackCodec.SDPFmtpLine` is ignored by pion; what rides the wire
  is the media-engine codec, so the answer/offer carried mono-only.
- RFC 7587: no `stereo=1` in the negotiated fmtp ⇒ the receiver
  advertises mono-only reception. libwebrtc then instantiates a mono
  opus decoder and downmixes every stereo packet.
- The downmix is lossless-correct as audio (libopus mono-decoding a
  stereo stream is a proper (L+R)/2, measured corr ~0.99) but the mix
  loses its width. Measured mid/(L+R)/2 energy kept per asset:
  red-winsnap **0.69**, unreal2 **0.88**, estrayk **0.89**, keygen-8
  **0.98**, fight-for-fun **0.95**, hybrid-funky-stars **1.00**. The
  wide-stereo songs degrade audibly.
- Human mic calls never exposed this: mics are mono, so a mono decoder
  was always correct for them. The music bot is the only stereo sender.

## The fix (`cmd/server/main.go`)

- New `stereoOpusPCFactory(iceServers []string)`: a
  `webrtc.NewAPI(webrtc.WithMediaEngine(m))` factory whose engine
  registers the audio defaults with opus upgraded to
  `minptime=10;useinbandfec=1;stereo=1` (PT 111), then calls
  `RegisterDefaultCodecs()` for the video list — registration is
  idempotent per payload type, so the audio entries aren't duplicated.
- `startBotClient` gained a `pcFactory func() (*webrtc.PeerConnection,
  error)` parameter (echo bot passes `nil`; music bot passes the
  stereo factory), set on `RTCClientConfiguration.NewPeerConnection`.
- `pkg/rtc/musicbot/convert.go`: `opusTrackCodec.SDPFmtpLine` updated
  to the stereo string for consistency (cosmetic; pion matches the
  engine codec, not this field).

## Verified

- SDP offer+answer both carry `stereo=1`; `track.channelCount == 2`;
  user confirmed correct stereo by ear and in a second browser.
- Build/vet/gofmt clean.

## Everything that was ruled out (do not re-investigate)

All measured, all clean — the "weird" was never here:

- **FLAC decode** is byte-exact vs ffmpeg for every asset (all 6),
  header stream-info precedence and end-of-data counts included.
- **`sampleToInt16` / `stereoNormalizer`** s16 fast path is bit-exact;
  the opus **encode→decode round-trip correlates ~0.99**.
- **RTP on the wire** is perfect: seq +1, timestamp +960, ~50 pkt/s,
  `packetsLost 0`, `concealedSamples` negligible, jitter buffer
  healthy, playout at exactly real-time rate.
- The **browser genuinely decodes the correct audio at 1× real time**
  (measured corr ~0.98 against the FLAC). It was just mono.

## Two hard-won methodology lessons

1. **Opus waveform correlation needs a fine lag search.** Opus adds a
   ~6.5 ms codec delay (312 samples at 48 kHz). A coarse 5 ms-step
   cross-correlation scan returns a spuriously low corr (~0.07–0.36)
   that looks like corruption but is just misalignment. Several rounds
   were spent chasing a phantom "garbled stream" before a per-sample
   lag refinement (±~2000 samples) showed corr ~0.9+. **Always refine
   the lag before concluding content is wrong.**
2. **MediaRecorder timing artifacts.** A long `MediaRecorder` capture
   spanning agent turn-gaps reads as ">1× speed" (e.g. 73 s of audio
   over a "45 s" window) purely because wall-clock elapsed between the
   start and stop calls. A tight 20 s capture measured 19.98 s of audio
   over 20.00 s wall — real-time. Use a short, bounded capture for
   pacing claims.

## Residual nuance (worth remembering)

After the fix, an in-place capture on the **same long-lived page/peer
connection** still showed identical L/R (mono downmix), while a fresh
call in another browser was correct stereo. Best explanation:
libwebrtc pins the opus receive decoder's channel count at decoder
creation and does not rebuild it on renegotiation — a connection whose
audio m-line was established before the stereo fmtp was in effect keeps
its mono decoder. A fresh connection (or the next page load) negotiates
stereo from the start and is correct. Not chased further once the user
confirmed by ear.
