# Session 27

The report: open /chat, click a bot, status reaches connected; close the
browser, reopen, and the status stays unconnected — webrtc-internals shows
iceConnectionState/connectionState stuck at new while signalingState reads
stable.

## Root cause

The "stable" was a red herring: **a fresh RTCPeerConnection also reports
signalingState stable** — no SDP was ever exchanged. The deadlock:

- The bots register with auto-assigned ids at startup (serverConfig.xml
  sets no subscriberId) and so hold the smallest ids (1000/1001); every
  browser gets ≥1002. Lexicographic politeness ⇒ **the bots are the polite
  peers**: only they create data channels, and channel creation is what
  triggers an offer. The impolite browser side just waits (`ondatachannel`).
- Bot-side sessions are keyed by subscriber id and rebuilt ONLY on member
  listing transitions (new member → startSession+offer, member gone →
  closeSession).
- The browser persisted its subscriber id in localStorage and
  re-registered it after a reload. The SS has no unregister; a WS close
  leaves the registration alive (aging 10s), and a same-tuple
  re-registration is a **refresh** — so a quick reload produces NO
  membership transition at all. The bot keeps its stale, dead session for
  the id; it already negotiated, so it never offers again; the fresh
  impolite browser pc waits forever. (Slow reloads — aging expiry observed
  by a listing round — recovered, hence "nearly always broken".)

Reproduced first as a failing e2e (probe re-registering its stored id:
incarnation 2 registered as the same 1000 and no data channel ever
opened) before fixing.

## The fix — an incarnation model, both ends

1. **Browser** (`web/site/src/api/ss/react.tsx`): registerSubscriber
   always sends an empty subscriberId — a page load is a new incarnation,
   never resurrect the dead one's id. localStorage persistence
   (`ss.subscriberId`), its helpers, and the SubscriberIdIsRegistered
   retry loop removed (dead code with an always-empty id).
2. **SS** (`pkg/models/ss/ss.go`, handleRegister): a registration evicts
   every OTHER live registration of the registrar's own (userId,
   userSessionId) tuple — a client registers exactly once per
   incarnation, so same-tuple siblings are dead by definition. The
   registrar's own id is exempt (same-id re-registration stays a refresh:
   roaming reconnects and bots re-registering their configured id keep
   their registration). This makes the incarnation change immediately
   visible to listChannelMembers (peers rebuild at once, not after
   aging) and stops a dead registration from being kept alive forever by
   its successor's address-matched activity (touch refreshes every
   same-address subscriber — without eviction, reload N times and N dead
   ids linger while the browser stays open). evict() now frees the
   username only while it still maps to the evicted id.

Why not bot-side-only fixes: polling makes any leave+join between rounds
invisible, so server-side liveness alone can't fix it; rebuilding on pc
failure leaves the polite re-offer racing the peer's return and doesn't
fix browser↔browser pairs. Fresh-id-per-incarnation makes every reload
walk the proven first-load path on both ends.

Known accepted wrinkles: two tabs of one session now compete (later load
wins — the older tab's keepalive starts failing; previously they shared
one id and corrupted each other's negotiation anyway); after ~1000 id
churn the auto-assign cursor could hand a reincarnation its predecessor's
freed id and refresh it (the deadlock would return for that pair —
negligible, noted, not engineered for).
