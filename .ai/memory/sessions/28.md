# Session 28

The ask: support a 44100 Hz / 16-bit signed / stereo FLAC audio source
(the model only accepted linear PCM 48000/2ch and μ-law 8000/1ch). The
user redirected mid-session: **don't add 44.1 kHz PCM — add an opus
source family instead** (a remote opus stream over http), 48000 Hz only,
with decode/re-encode avoided (the data is already opus). Second review
directive mid-implementation: use `github.com/pion/webrtc/v4/pkg/media/oggreader`
and `github.com/pion/opus` where possible; and later: drop the
`sampleToInt16` stage for float sources — the opus encoder takes integer
and float alike.

## The opus family

- **Model** (`pkg/models/audiosource`): new `SampleOpus = "opus"` +
  `CompressionOgg = "ogg"`; the third accepted combination is
  `opus/48000Hz/(1|2)ch` (ogg ⇒ opus and opus ⇒ ogg, both ways
  validated). The numeric-shape fields (BitDepth, NumericType,
  Interleaved) do not apply to an opus source and are not checked for
  one. `Stream` split: the base interface lost `io.Reader`;
  `SampleStream` (sample families) and `PacketStream` (opus) refine it.
- **Demuxing** (`ogg.go`): `github.com/pion/opus/pkg/oggreader` —
  **not** webrtc's `pkg/media/oggreader`, which serves whole-page
  payloads with no lacing (a multi-packet page would concatenate opus
  packets into one invalid RTP payload). pion/opus's serves whole
  packets via `ParseNextPacket` (CRC-checked, continuation-discarding
  for live joins). go.mod: pion/opus v0.1.0 promoted from indirect to
  direct (the user's manual `go mod tidy` also bumped webrtc v4.2.18→
  v4.2.20 and friends).
- **The 48000 rule**: enforced on the Ogg ID header's `SampleRate`
  field (the encoder's declared _input_ rate — informational per RFC
  7845 §5.1, but the only field that can say it; the codec's own clock
  is 48000 regardless). Channels 1–2, version 1.
- **Timing comes from each packet's own table of contents** (revised
  after the live-radio failure — see the debugging arc below): the TOC's
  frame size times the frame count (RFC 6716 §3.1), never the pages'
  granule positions — arbitrary for a live stream. The two header
  packets are skipped by magic prefix (an `OpusHead` mid-stream
  re-baselines the format — chained segments). The end-of-data count
  check compares served TOC samples vs `NumTotalSamples`, tolerating
  the encoder's pre-skip and tail padding. (The first cut timed packets
  by granule deltas with a pend/settle queue — one page of latency, and
  fatally wrong when joining a live stream; an early version of that
  also let the count check fire at EOF while the last settled packet
  was still queued — caught by test.)
  queued). A truncated tail (`io.ErrUnexpectedEOF` from pion's reader)
  is discarded like EOF, then count-checked.
- **The player** (`player.go`): third family — `pkts` field, opus track
  (the same codec the linear PCM family encodes toward), and
  `runPackets`: packet-paced (wait until wall clock catches media time
  written; a live stream's blocking reads already run at real time and
  never wait), `WriteSample` with the packet's own duration. Switching
  between opus songs is a stream swap; the pacing restarts with the new
  song. No encoder, so **pure-Go builds play opus songs** (only the
  linear PCM family needs libopus).
- **Float bypass**: `stereoNormalizer.readFrameFloat32` +
  `musicEncoder.encodeFloat32` (libopus `EncodeFloat32`); float sources
  no longer round-trip through s16 (`sampleToInt16` lost its float
  branch; player carries `pcm`/`fpcm`, swapped on retune).

## Tests

- `audiosource/ogg_test.go`: in-test Ogg builder (lacing + CRC, page
  flags), packet/TOC-duration asserts (incl. a live-edge granule the
  durations must ignore), spanning packet across pages, header
  discipline (44.1 kHz input refused, channels>2 refused, version≠1
  refused, mono ok), rewind, http re-fetch on rewind, chained segment,
  count-check mismatch, malformed streams (CRC, zero-length packet).
- `musicbot_test.go`: `opusSong` builds a synthetic ogg song; wire
  tests assert the RTP payload IS the source packet byte for byte —
  `syncRTPToSong` first, because the empty-room window drops the first
  packets before the track binds (content assertions must sync to the
  packet cycle, not assume packet 0). Remote test serves the stream
  over httptest and asserts re-fetch on loop. Neither needs
  `requiresOpus` — the family is cgo-free.

## Traps hit (do not repeat)

- **A pacing wait must never be the only door for control messages.**
  The opus pump's first cut serviced stop/switch/ctx only inside
  `if wait > 0 { select }` — a live stream's reads block on the network
  and arrive at real time, so the wait never opens: the pump ignored
  stops (leaking its http connection) and the next `/play`'s setSource
  deadlocked the peer's whole dcmsg handler (the bot dead for that
  peer until restart — found by playing a real radio, trancepulsefm).
  Control is now checked between every two packets; the wait's select
  remains the timed path. Pinned by TestPlayerPacketPumpLiveStream (a
  self-paced fake source whose reads sleep past their duration).
- `go mod tidy` needs the network; when the proxy is blocked it still
  rewrites go.mod — the user re-ran it manually with network.
- `*seq++` parses as `(*seq)++` in Go but is needlessly obscure — write
  the assignment.
- pion's `WriteSample` packetizes synchronously and drops silently on an
  unbound track; duration→timestamp has a fractional-tick accumulator,
  so odd packet durations don't drift.
- httptest handler goroutines touch test counters — use atomics (the
  race detector caught `fetches++` in the remote-stream wire test; the
  two pre-existing http tests in audiosource had the same latent race).

## The browser debugging arc (live at localhost:3000)

The user asked for frontend+backend logs and a live browser test
(web/site dev server on :3000, Go server on :8080, visitor login).
Instrumentation that stayed: `logSdp` in web/site/src/api/ss/negotiate.ts
(logs every offer/answer's per-section mid + a=setup), and the same
summary in pkg/rtc/negotiate.go at Info. Three separate bugs surfaced,
all in the negotiation/timing layer, none in the opus code itself:

1. **"Failed to set SSL role for the transport" on every call.**
   webrtc-internals showed the bot's answer to the browser's mic-offer
   carrying `a=setup:active` while the established transport had the bot
   as DTLS server (bots are polite ⇒ initial offerer ⇒ server). pion's
   CreateAnswer never consults the established transport — an actpass
   offer is answered with defaultDtlsRoleAnswer=client. Chrome refuses
   the flip and wedges in have-local-offer, so every LATER
   renegotiation (a song switch's track replacement included) fails —
   that was the "no sound" for trancepulsefm, not the audio path. Fix:
   the peer-connection factories take the session's politeness
   (`RTCClientConfiguration.NewPeerConnection func(polite bool)`) and
   pin `SettingEngine.SetAnsweringDTLSRole` — Server for the polite
   side, Client for the impolite (pkg/rtc/client.go's
   defaultPeerConnectionFactory, cmd/server's stereoOpusPCFactory).
   Pinned by TestDefaultPeerConnectionFactoryAnsweringRole.
2. **The radio's granule positions are live-edge counters** (e.g.
   771303869 — the encoder's samples since the station started), so the
   first page's "delta" against preSkip measured ~321 s of media: the
   pump wrote one packet and paced itself hours into the future.
   Probed the real stream (`curl` + a throwaway parser over pion's
   oggreader): pages of 50 uniform 20 ms packets, toc 0xFC. Durations
   now come from each packet's own TOC (RFC 6716 §3.1 frame size ×
   frame count — the same math pion's decoder uses); granule
   positions are no longer read at all. The count check tolerates the
   encoder's pre-skip + tail padding.
3. **Hangup killed the peer connection** (disconnected → failed; one
   run stormed 15,915 offer/answer cycles). At hangup BOTH sides
   renegotiate at the same instant (browser removes its mic, the bot
   removes the music): glare ⇒ the polite bot rebuilds its pc ⇒ the
   rebuilt pc answers with a fresh ICE/DTLS identity against an offer
   that was not an ICE restart — a browser cannot fold that into the
   running transport (pion↔pion tolerates it, which is why the wire
   tests always passed). Rollback would be the clean yield but pion
   v4.2.20 cannot roll back a local offer (SetLocalDescription rejects
   an empty-SDP rollback; the state machine has no have-local-offer →
   setLocal(rollback) transition). So the flows are sequenced instead:
   handleHangup defers the track withdrawal by hangupDetachDelay
   (500 ms) — the music is already off, and the withdrawal goes out
   after the peer's offer, alone. Verified live: hangup keeps the pair
   Connected, and the next /play reaches the bot at once.

   Remaining known fragility (documented in signalling-server.md's
   limitations): a glare at any OTHER moment (e.g. a browser track
   change colliding with a bot-side one) still hits the rebuild and
   kills the pair until a re-registration.
