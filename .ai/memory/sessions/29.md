# Session 29

The report: the music bot's mid-call song switch is flaky — `/play A`,
accept, music plays, `/play B` — sometimes it works, sometimes it
doesn't. Once the user's song list was in hand, the flakiness resolved
into a pattern: **every failure crossed a codec-family boundary**
(chiptune/μ-law → any linear-PCM song; hybrid-funky-stars or chiptune →
trancepulsefm/opus; "many more combinations"); every same-family switch
worked.

## Root cause — browser-side, not the bot

Cross-family switches replace the whole player (attach the new track
before detaching the old — one coalesced renegotiation), so the browser
receives a FRESH track on a new m-line while the old one is still
bound. `AudioGraph.addRemote` keyed bindings by pair
(`channelId:peer`) and started with `if (this.remotes.has(id)) return`
— "an id already connected is left alone". The replacement track was
silently dropped; the old entry only self-tears-down on its track's
`ended` — and pion's RemoveTrack direction-FLIPS the old m-line rather
than removing it, so Chrome fires `mute`, never `ended`. The stale
entry lingered for the rest of the call and swallowed every later
replacement.

The intermittency: pion's RemoveTrack nulls the transceiver's sender
(setSendingTrack(nil) → setSender(nil)), so a LATER AddTrack recycles
the freed transceiver (isSendAllowed: kind + nil sender + direction not
send*). The browser then re-binds the new RTP to the ALREADY-BOUND
receiver track and fires no ontrack — the stale graph entry plays the
new song by accident. The FIRST cross-family switch on a pair has no
free transceiver, always allocates a new m-line, always hit the drop.
Whether later switches recycle depends on switch order — hence
"sometimes".

## Fix (web/site/src/api/audio/audiograph.tsx only)

- `RemoteEntry` records the bound track.
- `addRemote`: same track under an existing id → no-op; a different
  track → tear the old entry down and bind the new stream (replace,
  not collide).
- The `ended` listener removes the entry only if it still belongs to
  that track — a replaced track's late `ended` must not kill its
  successor (same id).

No Go changes: the bot's switch path (attach-before-detach, coalesced
offer, pion's negotiation-needed re-fire on stable) verified clean in
the server log (one offer/answer per switch, collision=false, no
rebuild).

## Traps hit (do not repeat)

- **`mute` ≠ `ended`.** A direction flip keeps the m-line alive; the
  track never ends. Don't gate resource teardown on `ended` alone.
- An idempotence guard (`if (has(id)) return`) becomes a silent drop
  the day the key starts carrying replacements.
- The user's repro steps said "sometimes" — the deterministic pattern
  only appeared once the failing SONG NAMES were listed (session 28's
  lesson: get the exact repro data). Cross-family = replace player +
  new track; same-family = stream swap, browser untouched.
- pion's AddTrack scans `pc.rtpTransceivers` and reuses the first
  `isSendAllowed` one (v4.2.20 peerconnection.go:2220); RemoveTrack
  stops the sender AND nils it (rtptransceiver.go:318). Recycling order
  = insertion order — m-line placement of later switches is
  history-dependent.
- The sdpSummary/logSdp summaries print the mid of the PREVIOUS section
  when a=setup precedes a=mid in the SDP — off-by-one in the summary,
  harmless, don't misread it.
