# Session 30

Request: a video element on the home page playing the owner's live
stream over WHEP from a configurable endpoint (a MediaMTX path,
`http://localhost:8889/mystream/whep`), without touching the chat
subsystem's WebRTC at all.

## What was built

- `web/site/src/api/whep.ts` — a standalone WHEP client: recvonly
  audio+video transceivers, the SDP offer POSTed to the endpoint
  (`Content-Type: application/sdp`), the 201's answer plus Location
  taken back, trickle ICE as PATCHes of
  `application/trickle-ice-sdpfrag` (with `If-Match: *`) to the session
  resource, teardown by DELETE. The wire details mirror MediaMTX's own
  embedded web reader (extracted with `strings` from the shipped
  binary): the fragment repeats the offer's ice-ufrag/ice-pwd and m=
  lines; an OPTIONS probes the endpoint's Link-header ICE servers
  before the offer; the opus fmtp gains stereo=1/sprop-stereo=1 so
  stereo streams stay stereo.
- `web/site/src/components/WhepVideo.tsx` — the framed 16:9 video
  surface: connecting/offline veil, LIVE chip, auto-reconnect loop
  while offline (5s pause), Retry button, muted autoplay plus native
  controls.
- `web/site/src/components/LiveSection.tsx` — the Section scaffold,
  placed between the hero and about; absent entirely when unconfigured.
- The endpoint is runtime server configuration, NOT a build-time env
  var (the first NEXT_PUBLIC_WHEPURL draft was dropped on the user's
  request): a `<homeLiveWHEPURL url="..."/>` element of serverConfig.xml
  (serverConfig.xsd and serverConfig.xml.example updated), parsed by
  pkg/models/serverconfig, served by pkg/api/homelive at
  GET /api/homeLiveWHEPURL on the JWT whitelist, wired at startup
  exactly like /api/iceServers; the frontend reads it through
  src/hooks/useHomeLiveWHEPURL.ts. Copy in both translation bundles
  (live.*).
- e2e/home_live_test.go covers the configured and unconfigured cases,
  anonymously.

## Validation

- tsc --noEmit and eslint clean; go build/vet clean; TestHomeLiveWHEPURL
  passes (boots real servers per subtest).
- Live against the user's MediaMTX v1.20.1 (WHIP-published stream):
  OPTIONS 204 (StrictMode's first client is closed before its POST),
  POST 201 with a cross-origin-readable Location
  (/mystream/whep/<uuid>), PATCH 204 per candidate, H264 + stereo opus
  decoded, audio audible; unmounting (navigate to /chat) DELETEs the
  session — the MediaMTX control API's reader count drops accordingly.
  Mobile viewport (390x844) screenshot clean.
- Server rebuilt and restarted with its original args
  (`./server serve --config-xml=serverConfig.xml`, log
  /tmp/ps-server.log); the element added to the gitignored
  serverConfig.xml so the running site keeps its Live section.

## Traps hit (do not repeat)

- WHEP trickle's content type is `application/trickle-ice-sdpfrag` (not
  `...trickle-sdp-frag`), and MediaMTX wants `If-Match: *`; the fragment
  is session-level ice-ufrag/ice-pwd plus, per media, its m= line,
  a=mid and the a=candidate lines.
- The "no sound" report was a MUTED BROWSER TAB, not the chromium
  40094084 shape of session 12 — check the mundane first. webrtc-internals
  and the MediaMTX control API (`curl localhost:9997/v3/paths/...`)
  settle media questions in seconds.
- Shell precedence: in `kill X; go build && nohup ./server & sleep 3;
  curl ...` the `&` backgrounds build AND server together, so the curl
  ran before the binary existed. Sequence restarts explicitly.
- create_directory rejected `pkg/api/homelive` as "outside the project"
  while sibling file tools accept root-relative paths; the
  `personal-site/`-prefixed path worked.
- The offline veil + auto-retry loop were not exercised against a real
  failure (each config edit needs a server restart): the state machine
  is three lines of React and the POST-failure branch saw the server's
  400/404 shapes during bring-up.
