# Session 31

The request: design and implement a **sip bot** — a session border
controller (SBC, in SIP terms a B2BUA) interconnecting the chat
subsystem's WebRTC phone sessions with an external SIP network, so a
chat user can phone an arbitrary SIP subscriber. Telegram-style CLI
like the music bot; users bring their own SIP credential
(`/register <user@host> <password>` — no automatic allocation in v1);
the constructor takes an external on-memory user session storage
(`UserSessionStorage` interface + `OnMemoryUserSessionStorage` impl);
design doc `docs/sip-bot.md` before any implementation; use the
already-fetched `github.com/emiago/sipgo` + `github.com/emiago/diago`
rather than hand-rolling SIP. Mid-request the user added: a
`testSIPContact` attribute on `<sipBot/>` (example `9664@192.168.1.2`)
and a `/test-call` command dialing it (unavailable when unconfigured).

## What was built (all compiling, vet-clean)

- `docs/sip-bot.md` — the design doc: two legs (webrtc-leg = the music
  bot's dcmsg dialog + opus m-line on the pair's existing peer
  connection; sip-leg = one shared diago transaction user per process,
  every user's registration/call a transaction with their own From +
  digest), the CLI, the session storage, the call flow, the codec
  matrix (opus↔opus passthrough first, G.711↔PCM↔opus transcoding
  behind the cgo tag like the music bot's encoder), 12 numbered
  caveats (password crosses the chat, outbound-only, one call per user,
  no early media/DTMF/SRTP, telephony-grade 6:1 resamplers, NAT…).
- `pkg/rtc/msg_handler` — small framework extension, required for SBC
  signalling termination: `ResponseWriter.Cancel(callId)` /
  `Bye(callId)` (+ `ErrNoCallId`), folding the bot's own dialog end
  into the existing `sipDialogNote` → `foldDialog` amend machinery.
  No handler-visible changes for the other bots.
- `pkg/rtc/sipbot/` — `session.go` (UserSession / UserSessionStorage /
  OnMemoryUserSessionStorage), `sipbot.go` (Configuration incl.
  TestSIPContact; New wires msg_handler.Server + one diago; inbound SIP
  INVITEs declined 603), `account.go` (register keepalive with
  de-REGISTER on cancel, dial with per-user From + digest,
  parseAddressOfRecord), `handler.go` (the BotMessageHandler: CLI,
  one-call-per-peer, the hangup matrix, account revival from the stored
  credential on /call), `call.go` (peerCall with a small mutex — the
  SIP dial goroutine, the callee-hangup watcher and the serialized
  dcmsg goroutine genuinely meet; the relay: two self-paced pumps,
  "empty room" while the track is unbound), `transcode.go`
  (passthrough + G.711 paths, 1:6/6:1 resamplers, pcmAccumulator for
  ptime freedom, RFC 6716 TOC durations), `opus_codec.go` + `_stub.go`
  (libopus enc+dec behind cgo; pure-Go builds relay opus↔opus and fail
  G.711 legs with an explanatory error).
- Hosting — `serverconfig.go` `SipBotXML` (BotClientXML +
  testSIPContact), `serverConfig.xsd` `sipBotType`, the example
  document, `cmd/server/main.go` `startSipBot` on the shared
  `startBotClient` with `stereoOpusPCFactory`.

## The bug hunt so far (chronological, suspects eliminated)

1. **First failure was a test-design bug, not a bot bug**: the probe's
   `waitTrack` timed out. Root cause: pion's OnTrack fires only when
   RTP actually arrives, and the sip bot sends media only when the
   callee streams — unlike the music bot's always-on pump, which starts
   feeding the track at bind time. Fix: the fake streams opus in a ctx
   loop _before_ the probe waits for the track, and payload assertions
   collect a heard-set instead of positional reads.
2. Then: in the two 200-OK tests, "Callee answered." never arrives —
   `dg.Invite` appears to never return. But `TestSipBotTestCall` (the
   IDENTICAL SIP flow: 401 → digest retry → 180 → 200 → ACK, callee
   BYE asserted) passes.
3. **Isolated diago-vs-fake works**: `TestDebugDialOnly` (register +
   invite with digest + ACK against the fake, no WebRTC) returns in
   200 ms. So the fake and the diago usage pattern are sound.
4. **Not the OnResponse callback**: stripped the `sayp("Ringing…")`
   from the dial's OnResponse (diago warns a blocking callback stalls
   response processing) — still fails. Restored.
5. Wire flow at the fake is COMPLETE in the failing case too: INVITE →
   401 → digest retry → 180 → 200+SDP → the bot's ACK arrives (the
   fake's `dialogs.ReadAck` confirms the dialog — `waitDialog` passes;
   the "ACK missed" warning is transaction-layer noise about the first
   401'd transaction). The bot's dcmsg goroutine is healthy (the
   browser's 200 OK is processed, "the browser answered; the track is
   on the wire" logs, the renegotiation completes). So: wire exchange
   complete, fake happy, yet the dial goroutine never produces
   `setDialog` → "Callee answered.".
6. **The goroutine dump (12 s, mid-stall) exonerated the bot**: the
   dial goroutine had COMPLETED — the relay pump and the dialog watcher
   (both spawned after `setDialog`) existed, and nothing sat in
   `sayp`/`SendText`. So "Callee answered." had been sent on a healthy
   channel and the probe still waited. That pointed back at the test —
   and there it was: a botched fuzzy edit had left `chat("/call …")`
   duplicated in `TestSipBotHangupCommand`, so the command ran twice;
   the second was refused ("Already in a call") and the awaited line
   threaded on the FIRST /call's msg id. One-line fix; the test passed
   in 0.04 s. Lesson: when production code and test both "look right",
   diff the test's intent against what it literally does — and beware
   fuzzy edit tools removing an assignment in the wrong region.

## Resolution (final state: all green)

- `TestSipBotCallEndToEnd` then exposed the LAST real issue, in two
  acts. Act 1: the fake streamed to a nil IP — `strings.Lines` KEEPS
  the trailing newline, so the SDP parser's IP came out as
  `"127.0.0.1\r\n"` and `net.ParseIP` returned nil (test-only bug;
  `TrimRight(line, "\r\n")`). Act 2: with media flowing SIP→browser,
  the browser→SIP direction never started: the probe's `AddTrack(mic)`
  RECYCLED the bot's sendrecv mid=0 transceiver, and pion re-binds a
  recycled m-line's inbound RTP to the already-bound receiver WITHOUT
  firing OnTrack (the session-29 trap, now seen from the receiver's
  side) — the bot's onMic never ran. The production browser never hits
  this because accept attaches the mic FIRST (fresh m-line on the quiet
  connection), then the bot's media follows; the test was restructured
  to exactly that order (mic AddTrack + 300 ms settle, then the 200
  OK). Design-doc caveat #13 records it.
- Final validation: full sipbot suite green, `-race` clean (a test-fake
  race on recorded fields fixed with predicate-only assertions under
  the fake's mutex), `CGO_ENABLED=0 go build/vet` clean (shared codec
  constants had to move out of the cgo-tagged file into transcode.go),
  and `go test ./...` for the whole repo green. Debug scaffolds
  (zz_dbg*_test.go) removed; the opusVoice/streamOpus helpers and the
  fake PBX stay as the suite's SIP network.

## Traps hit (do not repeat)

- pion's `OnTrack` needs actual RTP; a relay that only forwards needs
  its peer to speak before any track materializes. Music-bot tests
  never noticed: its pump always plays.
- `sip.Uri` keeps Host and Port as separate fields; stuffing
  "host:port" into Host silently mis-builds request URIs. UserSession
  now carries `Host` + `Port int` (the bug the AOR parse test caught).
- Scheme toleration needs a helper (`withSipScheme`) — blindly
  prepending "sip:" breaks inputs that already carry one.
- libopus has a real group delay (lookahead + the resamplers' span):
  transcoder round-trip assertions must compare period structure (zero
  crossings), never index-wise sample signs.
- Accumulator ordering test: drain fully (or use a fresh accumulator)
  before asserting oldest-first — leftovers from an earlier sub-case
  poison the frame head.
- `zz_dbg_test.go` / `zz_dbg2_test.go` are TEMPORARY debug scaffolds;
  delete them once the stall is found.
