# Session 33

The request (sip bot follow-up): **DTMF support, end to end**. Today a
browser user phoning an IVR on the SIP network cannot answer the voice
menu — no dial pad in the frontend, and the bot's relay drops
telephone-event on both legs (docs/sip-bot.md caveat 6). The work has
two halves: the frontend (a dial pad + capability detection on the
WebRTC API) and the sip bot's backend (telephone-event signalling on
both legs, and the DTMF data plane WebRTC-leg → SIP-leg). The reverse
data-plane direction (SIP → WebRTC) is deliberately NOT built — the
WebRTC-side users are end users, the SIP-side ones are IVRs/enterprise
phones that consume DTMF rather than produce it — and the design doc
must say so.

Background reading: docs/webrtc-sip-dtmf-consideration.md (the whole
feature's RFC 4733 mechanics, the pion receive recipe, the browser-side
capability predicate, and the linphone model: capability decides whether
the pad exists, the user decides whether it shows).

## The plan

### 1. Signalling / control plane (backend)

The capability announcement must travel through the bot on both legs:

- **sip-leg: already done, no code change.** `sipStack.open` lists
  `media.CodecTelephoneEvent8000` (PT 101) in diago's codecs, so the
  outbound INVITE's offer always carries telephone-event (WebRTC-leg
  user is the caller), and an inbound call's 200 OK answer echoes it
  iff the SIP caller's offer had it (diago's negotiation intersects —
  WebRTC-leg user is the callee). Verify in tests; document.
- **webrtc-leg: register telephone-event in the MediaEngine** — pion
  registers only Opus/G722/PCMU/PCMA by default, so today the bot's
  answers strip the browser's telephone-event and its offers never
  carry it. Register `audio/telephone-event`, 8000 Hz, fmtp `0-16`,
  PT 126 (Chrome's own choice; 101 collides with pion's VP9-RTX in
  the video list and `addCodec` errors on PT collisions across
  same-type registrations):
  - `pkg/rtc/client.go` `defaultPeerConnectionFactory` — gains an
    explicit MediaEngine (defaults + telephone-event). Browsers always
    register it; the factory's comment already says it mirrors the
    browser. This also covers the test suite, whose bot runs on the
    default factory.
  - `cmd/server/main.go` `stereoOpusPCFactory` — parameterized with a
    `dtmf bool`: the sip bot passes true (its calls face IVRs), the
    music bot false (a music line has no use for a keypad — the
    frontend's capability check then correctly hides the pad on music
    calls).

False positives are embraced (the doc's linphone model): when the
webrtc-leg negotiates telephone-event but a given call's sip-leg did
not, browser DTMF reaches the bot and is re-encoded onto a dialog that
never agreed to it — the callee drops the unknown-PT packets. The pad
staying visible is the accepted cost; necessity is the user's call,
not SDP's.

### 2. Data plane (backend): WebRTC-leg → SIP-leg only

New file `pkg/rtc/sipbot/dtmf.go`:

- `telephoneEventPT(receiver)` — the negotiated telephone-event PT off
  `receiver.GetParameters().Codecs` (never hardcode: pion echoes the
  browser's PT when answering, uses our registered 126 when offering).
- `parseDTMFEvent(payload)` — the RFC 4733 4-byte payload (event code,
  E bit, duration), plus the code→digit rune mapping (0–9, `*`=10,
  `#`=11, A–D=12–15; anything else dropped).

`pkg/rtc/sipbot/call.go` / `handler.go`:

- `onMic` gets the `*webrtc.RTPReceiver` it currently discards;
  `peerCall.setMic(track, receiver)` stores the mic and the negotiated
  DTMF PT (+found flag).
- `pumpBrowserToSIP` dispatches on the packet's PT: the DTMF PT goes
  to the event parser, everything else flows to `toSIP.put` as today.
  (Mandatory once telephone-event is registered: pion's
  `checkAndUpdateTrack` delivers same-SSRC packets of any registered
  PT on the mic's read stream — feeding event payloads to the opus
  decoder/passthrough would corrupt audio.)
- Event handling: dedupe the END packet by (code, timestamp) — RFC
  4733 retransmits it 3× — and on a fresh END enqueue the digit. We
  act on END only; a wholly lost END (all 3 retransmits) loses the
  digit, accepted (SRTP on the webrtc-leg rarely loses; a stuck-key
  timeout is complexity without a caller).
- SIP-side emission via **diago's own DTMFWriter**
  (`dialog.AudioWriter(diago.WithAudioWriterDTMF(&w))`): the returned
  writer carries the pump's audio as today (mutex-serialized pass-
  through) and `w.WriteDTMF(rune)` injects the 7-packet RFC 4733
  sequence (PT 101, the PT the sip-leg negotiated — diago answers and
  offers 101 on both emission points). WriteDTMF blocks ~140 ms per
  digit, so digits drain on a dedicated goroutine fed by a small
  buffered channel on the relay (drop on overflow — a flooded pad must
  not grow memory or stall the audio pump's reads); the goroutine dies
  on the relay's stopCh.
- **SIP-leg → WebRTC-leg: not implemented** (by decision, see the
  header). One correctness fix in that direction though: diago's
  `RTPPacketReader` does NOT filter PTs, so today a SIP-side
  telephone-event payload (4 bytes) is handed to the audio bridge as
  if it were opus/G.711 — a garbage blip. `pumpSIPToBrowser` will read
  the last packet's PT (`RTPPacketReader.PacketHeader`, documented
  safe in the reader's own goroutine, which the pump is) and drop
  anything that is not the negotiated audio codec's PT. That is the
  whole reverse direction: silent drop, documented.

### 3. Frontend

- **`useCallMedia`**: expose
  `dtmfFor(channelId, peer): { insert(digit) } | null` — non-null iff
  the pair's mic sender exists, `sender.dtmf` is non-null, and
  `sender.getParameters().codecs` contains `audio/telephone-event`
  (the doc's two-phase predicate; `canInsertDTMF` is re-checked live
  inside `insert`, it gates pressing, not rendering). getParameters()
  populates only after negotiation completes, so after each attach a
  bounded async waiter (~5 s, 100 ms steps) watches for a non-empty
  codec list and bumps the media version — no PeerSessions plumbing
  changes. Mid-call renegotiation flipping the capability later is out
  of scope (our bot negotiates telephone-event at call setup, so it
  cannot appear later in this architecture).
- **`FloatingCard.tsx`** (new): the draggable fixed-position card
  extracted out of `VideoWindow` (same pointer-drag mechanics, same
  `home` prop shape), with a caption strip that takes optional action
  buttons. A drag never starts from an interactive element
  (`closest("button")` guard) so the dial pad's keys stay clickable
  while the card still drags from anywhere else. `VideoWindow`
  refactors onto it — behavior unchanged (it has no buttons inside).
- **`DialPad.tsx`** (new): a FloatingCard with the 12-key grid
  (1–9, `*`, 0, `#`) and a close icon button in the caption; `home`
  parameterized like the video card's; a key press calls
  `insert(digit)`.
- **`ChatApp`**: owns `dialPadOpen` (viewport chrome, like
  mobileListOpen). The dialer of the open conversation =
  `dtmfFor(...)` when its call is accepted. Renders `<DialPad>` while
  open && a dialer exists; passes the toggle state down to
  ConversationView → MessageInput.
- **`MessageInput`**: a MUI `DialpadIcon` IconButton right next to the
  send button, rendered only when the dialer exists, toggling the
  card's visibility.
- i18n: `chat.dialPad.{title,show,hide}` in en.json + zh.json.

### 5. Tests

- `pkg/rtc/sipbot/sipbot_test.go`: `TestSipBotCallDTMF` — the /call
  end-to-end flow, then the probe "presses" digits. pion's
  `TrackLocalStaticRTP.WriteRTP` rewrites the PT to the bound codec's,
  so a probe cannot emit telephone-event through the track API (the
  doc's note 5): the probe's PC factory (injectable via
  `RTCClientConfiguration.NewPeerConnection`) registers telephone-event
  AND a tiny interceptor that rewrites the PT of outbound mic packets
  carrying a magic payload prefix — the wire then carries genuine
  same-SSRC telephone-event RTP. The negotiated PT is learned from the
  probe's own sender `GetParameters()` after the call is up (no
  hardcoding). The fakePBX records received PTs alongside payloads;
  assertions: PT-101 packets encoding the pressed digit's start and
  deduped END arrive, audio keeps flowing, a retransmitted END does
  not double the digit.
- fakePBX: record `(PT, payload)` pairs; its SDP already offers
  telephone-event at 101 (as PBXs do).
- A signalling assertion: the bot's webrtc-leg offer/answer now
  carries telephone-event — covered implicitly by the DTMF test (the
  probe could not negotiate it otherwise), plus the existing
  end-to-end test keeps passing (the relay tolerates the new codec in
  the negotiation).

### 7. Out of scope (documented, not built)

- SIP-leg → WebRTC-leg DTMF transport (the reverse direction): events
  from the SIP side are dropped at the relay, never reach the browser.
- SIP INFO / KPML / in-band DTMF flavors — RFC 4733 only.
- Stuck-key timeout on the parser, per-digit duration passthrough
  (diago's fixed ~100 ms encoding stands), DataChannel fallback when
  telephone-event is not negotiated.

## Outcome

Built as planned; all green. The one deviation: the test's injector
learns the wire's telephone-event PT from `rtc.TelephoneEventCodec`'
s registered value (the bot offers the webrtc-leg's media, so its
MediaEngine's PT is what both directions carry — deterministic), not
from the probe sender's `GetParameters()` (pion answers with the
REGISTERED codec list there, not the negotiated intersection — the
negotiated one is only on `RTPReceiver.GetParameters()` via the
transceiver, which is what the bot's `telephoneEventPT` reads).

### Backend

- `pkg/rtc/client.go` — `TelephoneEventCodec` (audio/telephone-event,
  8000 Hz, fmtp 0-16, PT 126) exported, and
  `defaultPeerConnectionFactory` gains an explicit MediaEngine
  (defaults + telephone-event): the factory mirrors the browser, which
  always registers it.
- `cmd/server/main.go` — `stereoOpusPCFactory(iceServers, dtmf bool)`:
  the sip bot passes true, the music bot false (a music line has no
  keypad; the frontend's capability check then correctly hides it).
- `pkg/rtc/sipbot/dtmf.go` (new) — `telephoneEventPT` (the negotiated
  PT off the receiver's transceiver codecs), `parseDTMFEvent` + the
  code→digit mapping, `dtmfDeduper` (END retransmissions deduped on
  (code, start-timestamp)).
- `pkg/rtc/sipbot/call.go` — `setMic` takes the receiver and stores
  the DTMF PT; `pumpBrowserToSIP` dispatches packets by PT: DTMF →
  parse → dedupe → a 16-deep digit channel (drop on full) drained by
  `sendDigits` into diago's `DTMFWriter` (installed via
  `WithAudioWriterDTMF`, so audio passes under the same lock);
  `pumpSIPToBrowser` drops any payload whose PT is not the negotiated
  audio codec's (`RTPPacketReader.PacketHeader`, read in the pump's
  own goroutine) — the reverse direction's whole implementation:
  silent drop.
- `pkg/rtc/sipbot/handler.go`, `inbound.go` — the OnTrack
  registrations pass the receiver through to `onMic`.
- `pkg/rtc/sipbot/sipbot.go` — the stale "the relay drops it" comment
  rewritten (telephone-event is load-bearing now), the package doc
  carries the DTMF paragraph.

### Tests

- `TestSipBotCallDTMF` — the /call flow, then the probe presses "5"
  and "#": RFC 4733 packets sharing the mic's SSRC through the
  `dtmfInjector` (an interceptor rewriting the PT of magic-prefixed
  outbound payloads — pion's track API cannot write a foreign PT).

  packets, [4 3] per code) prove the END dedupe — while audio flows
