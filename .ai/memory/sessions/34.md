# Session 34 — the sip bot's proxy-media rework (plan of record, ready to execute)

## The request (compacted)

Rework `pkg/rtc/sipbot`'s media plane: from a full B2BUA with optional
transcoding into a **transcoding-free media relay** — the spirit of
FreeSWITCH's proxy-media mode (neither full B2BUA media handling nor
bypass-media), rtpengine, the Janus SIP plugin. The bot stays a normal
peer on the WebRTC network and a normal UA on the SIP network (one SIP
identity per user — untouched).

Today: the bot answers the near leg immediately, then originates the far
leg; the webrtc leg always negotiates opus; when the sip leg settles on
G.711 the relay transcodes (libopus + zaf/g711 + resamplers).

Target: media negotiation is **end to end** — the bot relays the SDP
media declarations and codec selections between the legs, re-originating
encryption parameters (and transport/PT/SSRC/sequence/timestamps) per
leg; the negotiated codec comes from the intersection of what the
WebRTC UA and the SIP UA themselves support, never forced to opus; no
transcoding anywhere, only RTP decrypt/re-encrypt bridging. Everything
else (per-user registration, signalling relay, call setup/teardown, the
crypto bridging) stays functionally unchanged.

## The user's clarifications (course corrections, in order)

1. The six principles: (1) proxy-media only; (2) no media re-encoding;
   (3) the bot's own codec preferences never participate — topology is
   UA(WebRTC) — bot — UA(SIP), only the two UAs' media support matters;
   (4) inbound: the bot's offer toward the webrtc leg carries the media
   support determined by the SIP UA; (5) when the SIP UA offers and the
   WebRTC UA answers, the WebRTC UA's selection is relayed to the SIP
   UA; (6) when the WebRTC UA offers and the SIP UA answers, the SIP
   UA's selection is relayed to the WebRTC UA. "If you doubt the overly
   strict phrasing, stick to the basic principle and go with your own
   design and flow."
2. The pragmatic outbound flow (the browser's media capability is not
   knowable ahead of time): `/call` → the bot does NOT ring the browser
   immediately; it offers the SIP leg a **presumed WebRTC codec list** —
   configurable, default `[opus, g722, pcmu, pcma]` — takes the SIP
   leg's answer (its selection C), and only then rings the browser with
   C as the webrtc-leg's media capability offer.
3. The in-band call verbs (INVITE/200 OK/BYE/CANCEL) between the browser
   and the bot ride **dcmsg** (the pair's RTC data channel), not the WS
   — the WS c2c channel carries only the SDP/ICE. (No ordering across
   the two.)
4. **No hook.** The hook approach (a `BeforeLocalDescription` callback
   in pkg/rtc's PerfectNegotiator + client plumbing) is rejected: the
   media capability announcement in the SDP the bot sends to the WebRTC
   UA is controllable with pion/webrtc's own API
   (`RTPTransceiver.SetCodecPreferences`) — no intercepting the
   negotiator's description generation, no patching generated SDP.

## The final design (no hook)

One audio codec **C** end to end per call, plus telephone-event as the
auxiliary alongside (DTMF, unchanged). The vocabulary is what both SDP
dialects express and the relay passes: **opus, G.722, PCMU, PCMA** +
telephone-event.

The pin mechanism (the whole trick): pion generates an offer's AND an
answer's per-m-line codec list from the transceiver's codec preferences
(`addTransceiverSDP` → `transceiver.getCodecs()`);
`SetCodecPreferences` overrides them, and pion refreshes them from a
remote description ONLY when an offer CREATES the transceiver
(`setCodecPreferencesFromRemoteDescription`, peerconnection.go:1272, the
`transceiver == nil` branch). So the bot pins **once, at attach time**,
and the pin sticks: the bot's speaker-track offer carries `[C,
telephone-event]`, and the browser's mic — which joins the same m-line
later — is answered with the same pin, because the transceiver already
exists and keeps its preferences. The mic and the speaker converge to
**one sendrecv audio m-line** (the browser's accept attaches the mic a
getUserMedia after the bot's offer landed, so the mic's addTrack reuses
the browser-side transceiver of the bot's m-line).

The one framework affordance (pkg/rtc + msg_handler, no negotiator
interception):

```go
// pkg/rtc/client.go:
// AddTrackWithCodecPreferences adds track like AddTrack and pins the
// codec preferences of its transceiver — the two pion calls as one hub
// operation, so the pin is in place before the renegotiation the attach
// triggers. The pin is recorded with the track and re-applied when a
// glare rebuild re-adds the track to the fresh connection. A nil codecs
// is AddTrack exactly.
func (c *HeadlessRTCClient) AddTrackWithCodecPreferences(peer ss.SubscriberId, track webrtc.TrackLocal, codecs []webrtc.RTPCodecParameters) (*webrtc.RTPSender, error)

// pkg/rtc/msg_handler/response_writer.go (the ResponseWriter's media
// method twin; AttachMedia stays for the music bot):
AttachMediaWithCodecPreferences(track webrtc.TrackLocal, codecs []webrtc.RTPCodecParameters) error
```

### Outbound (`/call`) — the SIP leg leads

1. `/call` → account resolves (unchanged) → "Calling X…" → the SIP dial
   starts AT ONCE on its own goroutine (the offer = the presumed list +
   telephone-event). The browser is NOT rung; no track, no OnTrack, no
   INVITE yet.
2. SIP failure (busy/unreachable/no common codec) → `Call failed: …` —
   the browser was never disturbed (no webrtc-leg verbs exist; the
   tellBrowserEnded/hangup paths learn to skip Cancel/Bye when
   `callId == ""`).
3. SIP 200 OK → C = the negotiated codec (diago's `MediaProps.Codec` —
   the first non-telephone-event of the intersection, in the answer's
   order, i.e. the callee's pick). `c.setCodec(C)`: stores C and creates
   the speaker track (a `TrackLocalStaticSample` with C's capability).
   The relay arms (`setDialog`, the SIP→browser pump starts; its writes
   drop on the unbound track — the empty room).
4. Ring the browser with the selection: `w.OnTrack(...)`, then
   `w.AttachMediaWithCodecPreferences(track, [C, tel-event])` (the offer
   carries the pin), then `w.Invite(voice)`, then `sayp("Callee
answered.")`. Attach BEFORE the INVITE so the offer leads the ring.
   Exact-once discipline: after each step re-check `c.ended` under the
   call's mutex — an end landing mid-ring Cancels the just-sent ring
   and BYEs the just-answered callee.
5. The user accepts → dcmsg 200 OK → `handleResponse`: activate; the
   defensive re-attach is a no-op (the track is already attached).
   The mic arrives after gUM: it joins the m-line (transceiver reuse),
   the bot's answer keeps the pin (prefs persist), `OnTrack` fires on
   the first mic RTP → the browser→SIP pump starts.
6. The callee's audio reaches the browser from the moment the browser
   answers the bot's offer (before the accept — the frontend renders it
   muted until the accept click resumes the AudioContext; verified with
   the frontend: a pre-accept remote track is harmless).

### Inbound (a SIP subscriber phones the user)

1. INVITE on the account's socket → parse `[S]` off the body (diago's
   `media/sdp` + `CodecsFromSDPRead` on the audio m-line). No SDP →
   **488** (late-offer inbound stays unsupported). C = the first codec
   of the **presumed list** present in `[S]` (the presumed browser's
   selection among the caller's support — principle 5 in substance).
   None → **488**, the browser never rings.
2. Create the call, `c.setCodec(C)` (the track exists from the start),
   `w.OnTrack(...)`, `AttachMediaWithCodecPreferences(track, [C,
tel-event])` — the offer carries the SIP-determined selection toward
   the browser (principle 4's substance) — then `w.Invite` + `180` +
   the watchers, as today.
3. The user accepts → dcmsg 200 OK → `handleResponse` →
   `go answerInbound`: `serverDialog.AnswerOptions(diago.AnswerOptions{
Codecs: [C-diago, media.CodecTelephoneEvent8000]})` — diago intersects
   with the caller's offer, so telephone-event echoes only when offered.
   The answer's SDP is pinned to C. ACK-awaited, as today.

### Deviations from the principles' letter (owned, in the doc)

- The browser never sees the SIP UA's FULL list; it sees the single
  selection. The selection is always within the SIP UA's support, and
  the presumed list's order IS the browsers' preference order, so the
  presumed selection coincides with what the browser would have picked.
- The presumption can be wrong (an exotic WebRTC client lacking C): the
  mic then arrives with a codec ≠ C — `onMic` drains it (one-way audio,
  logged) rather than bridging garbage. Same drain covers the residual
  race where the browser's mic offer beats the bot's ring-time offer
  (an instant accept + instant gUM) onto a fresh, never-pinned m-line.
- Outbound UX change: the browser rings once the callee HAS answered; a
  busy/unreachable callee never rings the browser; a callee who starts
  talking immediately is dropped at the unbound track until the accept
  (the widened empty-room window — doc §11.5).

### The relay, reduced

DELETE `transcode.go`, `opus_codec.go`, `opus_codec_stub.go` and their
tests — no libopus, no G.711 codecs, no resamplers, no cgo gating in the
sip bot (a pure-Go build loses nothing; the music bot's own opus use is
separate). The relay:

- pumpSIPToBrowser: read a payload off the dialog; drop when its PT is
  not the negotiated audio codec's (the tel-event drop, unchanged);
  else `track.WriteSample(payload, dur)` — dur from the opus TOC
  (`opusPacketDuration`, moved from transcode.go) or `len(payload)/8` ms
  for the 64 kbps 8 kHz codecs (G.711, G.722).
- pumpBrowserToSIP: ReadRTP off the mic; the DTMF dispatch by PT
  (unchanged); audio payloads into diago's DTMF-wrapping writer
  (unchanged — it re-stamps PT/SSRC/seq and paces by the codec's 20 ms
  ticker).
- `voiceTrackCodec` (the fixed opus track codec) is gone; the track is
  per-call, created by `setCodec`.
- `onMic` accepts the mic iff its codec's MimeType matches C's; else
  drain + log (today's degenerate-case discipline).

## Library facts verified in source (the load-bearing mechanics)

pion v4.2.20 (module cache):

- `AddTrack` recycles the first `isSendAllowed` transceiver: kind
  matches, sender nil, and `currentDirection` NOT sendrecv/sendonly
  (peerconnection.go:2213, rtptransceiver.go:344) — so the speaker's
  attach recycles a recvonly mic transceiver and vice versa; one m-line
  converges.
- `OnTrack` fires on the first RTP for a receiver with
  `!haveReceived()` (runIfNewReceiver peerconnection.go:1492,
  startReceiver:1402) — NOT at SetRemoteDescription. The session-29 trap
  is precisely "a track re-binding a receiver that already received"; a
  fresh call's receiver is fresh in either offer order, and
  `configureRTPReceivers` recreates the receiver when a track vanishes
  from the SDP (so a second call on the pair still gets its OnTrack).
- `SetCodecPreferences` validates against the MediaEngine; PT 0 in a
  preference means "the engine's PT" (rtptransceiver.go:54).
- `setCodecPreferencesFromRemoteDescription` runs only when a remote
  offer CREATES the transceiver (peerconnection.go:1272) — a pin set at
  attach persists across the mic's later re-offer and the bot's answers.
- `onNegotiationNeeded` is enqueued on pion's ops chain
  (peerconnection.go:332) — async — so a pin applied synchronously right
  after AddTrack lands before the offer is created (a lost race here is
  benign and self-heals at the mic's answer: only the first offer's
  codec list would be unpinned; the send directions stay pinned).
- The answer's codec list is NOT intersected with the offer by pion
  beyond the transceiver preferences — so the pin must list only what
  the offer carried. (Borders: browsers always offer the four +
  tel-event; the exotic-client case is the drain path above.)
- The sip bot's PC factory (`stereoOpusPCFactory` in cmd/server) already
  registers opus-111 (stereo fmtp), G722-9, PCMU-0, PCMA-8, and (dtmf=true)
  telephone-event-126 — the pin's codecs are always registered.
  `rtc.TelephoneEventCodec` (PT 126) is the pin's tel-event entry.

diago (vendored v0.32.2 + patches):

- The negotiated codec = the first non-telephone-event of
  `filterCodecs` (`CodecAudioFromSession`); outbound the intersection
  rides the ANSWER's order (the callee's pick), inbound the offer's.
- `AnswerOptions.Codecs` overrides the answer's codec list per call
  (dialog_server_session.go) — the inbound pin needs no diago change.
- The outbound offer = the account's static `MediaConfig.Codecs`
  (sipStack.open) — the presumed list simply becomes that list; no
  per-call override needed.
- `generateSDPForAudio` emits rtpmap lines by a PT switch — G.722 needs
  a patch for its canonical `a=rtpmap:9 G722/8000` (the generic branch
  appends a spurious `/1` channel count); `CodecsFromSDPRead` parses
  static PTs 0/8 without an rtpmap line — add the `9` shorthand.
- `RTPPacketWriter.Write` blocks on the codec's 20 ms ticker after each
  write (the browser→SIP pump is paced by it — existing behavior).
- DTMFWriter hardcodes tel-event PT 101 (unchanged; the
  unnegotiated-tel-event false positive stays caveat 6's).

The frontend (verified by exploration, session continues unchanged):

- Its perfect negotiator (web/site/src/api/ss/negotiate.ts) answers any
  SDP offer regardless of call state; mic attach is `pc.addTrack`
  (peersessions.tsx) — reuses a transceiver whose direction is not
  recvonly (so the mic joins the bot's sendrecv m-line).
- The accept order is: dcmsg 200 OK → getUserMedia → addTrack → mic
  offer (usePhoneCalls.ts + useCallMedia.ts). The browser's mic offer
  always trails the accept by the gUM latency — the bot's ring-time
  offer always lands first in practice.
- A remote track arriving pre-accept plays muted and breaks nothing
  (useCallMedia + audiograph.tsx).
- NO frontend change is needed: a real browser's mic track is raw
  (getUserMedia), the browser encodes to whatever the answer pins. (The
  pion probe in tests is codec-bound — it must create its mic track
  with the EXPECTED pinned codec; the test controls the PBX side, so the
  pin is deterministic.)
