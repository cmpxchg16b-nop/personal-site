# Session 35 — the accept gate: no callee audio before the browser answers

## The request

Two issues against session 34's proxy-media rework, reported from a
live run:

1. `/call <aor>` → the callee answers → the browser rings (correct) —
   but the callee is **audible before the user clicks accept** (wrong).
2. After `/call`, nothing shows while the callee is being rung — there
   should be progress, and the bot could amend its chat message.

Issue 2 was **voided by the user mid-session**: the `Calling <aor>…`
line exists and renders (replies are not threaded away in the frontend)
— they had simply missed it. Only issue 1 was real.

## The diagnosis (two broken assumptions, one bug)

Session 34's design owned pre-accept audio as harmless on two grounds;
a live browser falsified both:

- **The "empty room" window is milliseconds, not the ring's length.**
  The design assumed the callee's pre-accept audio drops at the
  unbound speaker track (pion drops `WriteSample` to a track with no
  bound sender). But the browser's perfect negotiator answers the
  bot's ring-time SDP offer at once — it is call-state-blind — so the
  track binds while the call still rings, and `pumpSIPToBrowser`
  forwards the callee's RTP for the entire ring period.
- **The frontend does not mute a pre-accept track.** The session-34
  note claimed the frontend "renders it muted until the accept click
  resumes the AudioContext". In fact `useCallMedia`'s `subscribeTracks`
  connects EVERY inbound audio track into the audio graph on arrival
  (`addRemote` → the shared remote gain → the speakers), gated by
  nothing but the AudioContext state — and typing `/call` + Enter is
  already a user gesture, so the autoplay unlock
  (`armGestureUnlock`) has the context running by ring time.

Net: an answered callee's "hello?" played through the user's speakers
while the call UI still showed the incoming-ring popup.

## The fix — the accept gate (bot side)

The relay's SIP→browser pump drops the callee's payloads until the
webrtc-leg is actually answered — the behavior docs/sip-bot.md §11.5
always claimed, now implemented:

- `peerCall` gains `accepted chan struct{}`, created at construction
  (both sites: `handler.call`, `serveInbound`).
- `activate()` closes it — exactly once, under the existing
  phase-guard (a duplicate 200 OK returns false before the close).
- `armLocked` hands it to the relay; `pumpSIPToBrowser` checks it per
  payload (a `select`/`default` — instant once closed) and drops until
  it opens. The pump keeps READING while gated, so no stale burst
  backs up in the dialog's socket buffer.
- The browser→SIP pump needs no gate: the mic exists only after the
  accept click (frontend: 200 OK → gUM → addTrack), and `activate()`
  runs in the 200 OK's handler before any mic RTP can arrive.
- Inbound was safe by construction (`armRelay` runs only in
  `answerInbound`, post-accept) and gets the same gate for free — it
  starts already open.

No frontend change: with no RTP before the accept, the remote track
stays muted (its unmute is RTP-triggered) even though the graph
connects it at ring time.

Alternatives considered and rejected:

- **Frontend-side gating** (route a remote track into the graph only
  once its call is accepted) — the wrong layer for the root cause:
  media crossing a B2BUA toward an unanswered party is the bot's bug,
  and the gate must hold for any client, not this one frontend. The
  frontend's track routing remains as it is (defense in depth would be
  a separate, cosmetic change).
- **Delaying the attach until the accept** — breaks session 34's
  load-bearing ordering: the bot's offer must lead the ring so the
  mic's later `addTrack` reuses the bot's pinned m-line (the
  transceiver-reuse convergence, §8's pin).

## The test

`TestSipBotCallHoldsCalleeAudioUntilAccept` (+ a `trackCount` probe
helper): register, `/call`, the callee answers, the browser rings —
then the fake PBX streams the callee's voice for 500 ms (≈25 packets)
**while the call still rings** and asserts not one packet crossed
(pion's `OnTrack` is RTP-triggered: a single leaked packet would have
fired a track). Then the probe accepts, the voice crosses byte for
byte, and the callee's BYE ends the call cleanly.

**Mutation-tested**: with the gate neutralized (`if false { continue }`)
the test fails in 0.6 s — "the callee's audio reached the
still-ringing browser (1 track(s) fired)" — exactly the reported bug.

Known limit of the negative assertion: under extreme scheduling
starvation the stream goroutine might not run within the 500 ms
window, making a run vacuously pass. That is the harmless direction (a
false pass, never a false failure), and the mutation test proves the
assertion's potency when the stream runs.
