# Session 36 — outbound calls route through the registrar (the default outbound proxy)

## The request

A live `/call <user>@<callee-provider-domain>` from a user registered
as `<user>@<its-own-sip-server>` failed (domains redacted — the shape
is what matters):

```
fail to write request on init req="INVITE sip:<user>@<callee-provider-domain> SIP/2.0":
udp conn [<bot's-ipv6>]:57324 err. write udp [<bot's-ipv6>]:57324-><callee's-ipv4>:5060:
sendto: network is unreachable. transaction transport error.
```

The user's reading, confirmed: the INVITE was resolved and sent
**directly to the callee's domain**, while the account's socket was
bound to the IPv6 source of the route to the (IPv6) registrar — an
IPv4-only callee domain is unreachable from that socket. A registered
user's registrar is its default outbound proxy; the INVITE should leave
through its own SIP server, Request-URI untouched, and the proxy routes
onward.

## The diagnosis (library mechanics that matter)

- sipgo v1.6.0 `sip.Request.Destination()` (sip/request.go:207) has a
  fallback chain: `MessageData`'s destination (what `SetDestination`
  sets) → the top Route header's address → **the Request-URI's own
  host:port**. Nothing in the dial path set the destination, so every
  outbound INVITE fell through to the callee's domain. (The hunt for a
  hidden setter was a red herring — the fallback IS the setter. An
  empirical scratch test settled it: destination = "example.com:5060"
  right after `dg.NewDialog`.)
- diago v0.32.2 has `RegisterOptions.ProxyHost` for REGISTER but no
  outbound-proxy knob on the INVITE path (`dg.Invite` =
  NewDialog + Invite + Ack, no hook in between).
- `bindHostFor` (sipbot.go) binds each account's socket to the source
  address of the route to ITS registrar — so the socket's family is the
  registrar's, and any wire destination in another family is
  unreachable from it. Routing everything through the registrar makes
  the socket's family always right by construction.
- In-dialog requests are safe: CANCEL copies the INVITE's destination
  (sip/request.go:326); ACK/BYE follow the dialog's route set (the
  proxy's Record-Route keeps them on the path — sipgo's buildReq turns
  Record-Routes into Routes, and `Destination()`'s Route fallback then
  resolves the proxy).

## The fix

`pkg/rtc/sipbot/account.go`:

- `account.dial` no longer calls the `dg.Invite` helper; it spells the
  helper out (NewDialog → `dialog.InviteRequest.SetDestination(
a.session.proxyAddr())` → Invite → Ack, same options, same
  errors.Join close discipline) — the one insertion the helper has no
  knob for.
- `UserSession.proxyAddr()`: the account's SIP server as a host:port
  destination — port defaults to 5060 (SetDestination parses with
  net.SplitHostPort, so a port must be present — `hostPort()`'s
  port-less form would NOT parse), an IPv6 literal re-bracketed via
  net.JoinHostPort.

No vendored-diago change: `dialog.InviteRequest` is promoted through
the embedding (verified compiling/running in the scratch test).

## The tests

- `TestSipBotCallRoutesViaRegistrar` (sipbot_test.go): register against
  the fakePBX, then `/call 1234@callee.invalid` (RFC 2606's reserved
  TLD — unresolvable). The INVITE must arrive AT THE REGISTRAR with
  `inviteRURI == "sip:1234@callee.invalid"` (a new fakePBX field,
  `req.Recipient.String()`), then the call comes up end to end (browser
  rings, 200 OK, /hangup → the callee's BYE). **Mutation-tested**: with
  the SetDestination neutralized the test fails in 30 s — "timed out
  waiting for the callee's INVITE at the registrar" — the reported bug.
- `TestProxyAddr` (account_test.go): the destination's format table
  (default port, explicit port, IPv4, bracketed IPv6 both ways), each
  asserted to round-trip through net.SplitHostPort.
- The existing suite is insensitive to the change by construction: in
  every test the callee host IS the registrar, so the destination is
  unchanged — full suite, -race, and CGO_ENABLED=0 all green;
  TestSipBotIPv6 exercises proxyAddr's IPv6 re-bracketing for real.

## Traps hit (do not repeat)

- **Reading library source for a setter that isn't one**: the
  destination "must be set somewhere" reasoning burned real time before
  a 20-line scratch test showed the fallback in `Request.Destination()`
  doing it. When a value has a fallback chain, grep the GETTER's
  overrides (Request overrides MessageData.Destination()), not just the
  setter's callers.
- `hostPort()` vs `proxyAddr()`: the URI form drops a zero port; the
  destination form must never (SplitHostPort errors). Don't reuse one
  for the other.
