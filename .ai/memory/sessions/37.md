# Session 37 — SIP MESSAGE: `/send` outbound, inbound forwarding, the size knob (plan of record)

## The request

The sip bot bridges calls; now it bridges **pager-mode instant messages**
(RFC 3428 SIP MESSAGE) too:

1. `/send <aor> <message>` — the chat user sends a SIP MESSAGE carrying
   `<message>` into the SIP network (WebRTC-leg → SIP-leg, the /call
   pattern: a chat command becomes a transaction on the account's own
   client, with the account's identity, through the account's registrar).
2. The message's byte size cap is a server-config knob with a fair
   default: SIP MESSAGE rides UDP, and the budget derives from the IPv6
   minimum L3 MTU (1280) minus the IPv6+UDP headers (48) minus a presumed
   SIP header block — landing around 800–1100 bytes of body.
3. Inbound: a SIP MESSAGE arriving at a registered account's socket is
   forwarded to that user's browser. Two media types: `text/plain`
   (forwarded verbatim, attributed to the SIP From) and a **reduced**
   `message/cpim` (RFC 3862): attachments and signatures stripped, the
   inner From/To preserved, rendered as plaintext. Encrypted CPIM is not
   supported. Any other media type: dropped silently (the browser is
   never bothered), the SIP side gets **415 Unsupported Media Type**.
4. The existing bridge implementations (/call → diago INVITE, the DTMF
   relay, the unsolicited WriterFor path) are the pattern references.

Doc-first: this note, then docs/sip-bot.md, then the code.

## Library facts verified in source (the load-bearing mechanics)

- **sipgo v1.6.0 `Server.OnMessage`** exists (server.go:325) — but
  vendored diago v0.32.2 never registers it (NewDiago wires
  Invite/Cancel/Ack/Bye/Info/Options/Refer/Notify only), so an inbound
  MESSAGE today falls to sipgo's OnNoRoute. diago is vendored precisely
  for this (§11.21): patch 3 adds a `WithMessageHandler` option +
  dispatch.
- **Outbound send path**: `sipgo.Client.Do(ctx, req)` (client.go:214) is
  the HTTP-like request/response — returns the final response, respects
  ctx; with no options it runs `clientRequestBuildReq`, which fills in
  Via/To/From/CSeq/Call-ID/Max-Forwards **only when absent** — so a
  pre-stamped From (the account's AOR + tag, the REGISTER/dial
  discipline: diago's default From would be the socket's address, not
  the AOR) survives untouched. 401/407 → `Client.DoDigestAuth(ctx, req,
res, auth)` mutates the same req (Authorization, CSeq++, Via rebuilt)
  and resends — the destination (below) is a MessageData field and
  persists across the retry.
- **Routing**: session 36's rule applies verbatim — the Request-URI is
  the target's, but the datagram leaves through the account's own SIP
  server: `req.SetDestination(session.proxyAddr())`, same as
  `dialog.InviteRequest.SetDestination` in account.dial. The account
  socket's family is the registrar's by construction (bindHostFor), so
  the fallback (resolving the target's own host) would be both wrong
  routing and a family hazard.
- **The account's client is private**: diago pins a per-transport
  `*sipgo.Client` (createClient: WithClientNAT + the socket's bind
  host/port for the Via) and exposes none of it. sipbot owns the UA but
  must NOT mint a second client on it — the Via would carry the UA's
  default host, not the account socket's, and responses would route
  nowhere. Patch 3 therefore also exposes
  `Diago.Client(transport string) (*sipgo.Client, error)` — a thin
  getter over the existing getTransport/getClient pair.
- **`sip.NewRequest(sip.MESSAGE, uri)` + `req.SetBody`** — SetBody also
  maintains Content-Length (message.go:146). Content-Type is a plain
  `sip.ContentTypeHeader` appended by hand.
- **The fake PBX** (sipbot_test.go) already speaks registrar+callee;
  it gains `srv.OnMessage` (a recorder with a scripted response code)
  and a client-side `sendMessage` (its `f.client.Do`) for the inbound
  direction.

## The design

### Outbound: `/send <aor> <message>`

- CLI parsing is the one place the raw line matters: `strings.Fields`
  would shred the message's inner whitespace, so `/send` cuts the raw
  text — command, then the aor token, then the remainder trimmed (inner
  spacing and newlines preserved). Missing pieces → the usage line.
- The account to send from is `/call`'s `ensureAccount` — a live
  registration, a revived stored credential, or a pool loan (announced,
  exactly like /call's). Sending mid-call is allowed; MESSAGE is
  dialog-free.
- `account.sendMessage(ctx, target, text)` (new message.go): the target
  completion is dial's (a bare user joins the account's domain); From is
  the AOR + fresh tag; To the target; Content-Type
  `text/plain; charset=utf-8`; SetDestination(proxyAddr());
  `client.Do` bounded by a 5 s ctx (the /register discipline —
  synchronous on the peer's channel goroutine, so the reply is the
  wire's real answer; caveat 10 already owns the bounded-stall
  tradeoff); 401/407 retried with the account's digest credential. 2xx →
  "Message sent to …."; anything else → the failure reply carrying the
  SIP status.
- The size cap (below) is enforced in the handler before anything
  leaves, like every CLI input validation.

### The size knob: `maxMessageBytes`

- `<sipBot maxMessageBytes="…"/>`, mirrored `SipBotXML.MaxMessageBytes`,
  carried by `Configuration.MaxMessageBytes`; **default 800**; the XSD
  types it positive-integer; the wiring rejects ≤ 0 and anything above
  65507 (the largest UDP payload — past it no transport can comply).
- The arithmetic (documented in §10): IPv6's minimum link MTU is 1280
  (RFC 8200); minus 40 (IPv6) and 8 (UDP) leaves **1232** for the whole
  SIP datagram; a typical MESSAGE header block (Via, From+tag, To,
  Call-ID, CSeq, Max-Forwards, User-Agent, Content-Type, Content-Length)
  is ~350 bytes, and a digest-challenged retry adds an Authorization
  header of ~230 — reserving ~430 lands the body budget at ~800. Only
  the bot's OWN datagram to its registrar is budgeted — what proxies add
  downstream (their own Vias) rides their own links. Deployments on TCP,
  or on networks with known path MTUs, raise the knob.
- Outbound-only enforcement (that is where the bot is the sender). An
  over-limit `/send` is rejected in chat with the actual and the limit —
  never truncated silently.

### Inbound: SIP MESSAGE → the browser

- diago patch 3's `WithMessageHandler` gets one closure per account
  (sipStack.open's new onMessage parameter, binding the owning peer —
  inboundServe's exact shape), so routing needs no To-header matching:
  the socket IS the account.
- The handler (message.go):
  - `text/plain` → `Message from sip:<From>:\n\n<body>`.
  - `message/cpim` → the reduced parse: CPIM headers (textproto
    semantics — folding honored), keep `From:`/`To:`; the encapsulated
    MIME entity's first `text/*` part is the message — a
    `multipart/mixed`'s attachments and a `multipart/signed`'s signature
    are stripped by that same selection (recursion capped at depth 2);
    base64/quoted-printable transfer encodings decoded. Rendered:
    `Message from <inner From> to <inner To>:\n\n<body>`. A malformed
    one → 400, silently dropped.
  - anything else — including encrypted CPIM (`application/pkcs7-mime`,
    `multipart/encrypted`) and a bare multipart top level → **415**,
    silently dropped (the WebRTC UA is never bothered).
- Delivery is the unsolicited path (`h.writers.WriterFor(peer)` +
  Reply — the session-start announcement's twin). Success → 200 OK; a
  peer with no live session (ErrNoMessagingChannel) → 480, the
  registered-but-gone answer.
- Charsets pass through as-is beyond utf-8/us-ascii (documented
  simplification — the chat renders UTF-8).

### The diago patch (PATCHES.md gains patch 3)

`third_party/diago/diago.go`: a `messageHandler` field +
`WithMessageHandler(func(req, tx) error)` option; NewDiago registers
`server.OnMessage` through the same errHandler wrapper as its siblings
(the zero value answers 405 — sipgo's own no-route behavior, so an
option-less diago is byte-identical in behavior to upstream). Plus
`Diago.Client(transport)` — the accessor above. No other behavior
changes.

## Considerations weighed

- **Synchronous /send** (bounded 5 s) over /call's async goroutine: a
  MESSAGE round trip is REGISTER-shaped, not INVITE-shaped (no ring, no
  human answer), and the synchronous answer carries the proxy's real
  verdict. The bounded stall on the peer's channel is caveat 10's
  already-owned tradeoff.
- **Reject over truncate** for over-limit messages: silent truncation
  corrupts meaning; the reply states both sizes so the user can split
  by hand.
- **Reject at the handler**, not in account.sendMessage: all CLI input
  validation lives in the handler (registerUsage, callUsage); the
  account method trusts its caller — the same division dial uses (the
  bad-address error surfaces from dial, but arity/whitespace are the
  handler's).
- **No inbound size cap**: the cap guards the bot's own UDP datagrams;
  an inbound oversized datagram is the sender's fragmentation problem,
  and the webrtc leg (SCTP) fragments freely. Documented, not enforced.
- **In-dialog MESSAGE** (RFC 3428 allows it mid-INVITE-dialog): treated
  as page-mode like the rest — forwarded, answered; no dialog matching.
  Documented.
- **No Contact on the outbound MESSAGE**: not required by RFC 3428; the
  registration is the routable identity. Minimal wire shape.
- **Inbound MESSAGEs are unauthenticated** — caveat 3's inbound-call
  posture extended verbatim; the doc says so.
