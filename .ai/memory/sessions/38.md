# Session 38 — video calls: `/video-call`, inbound video passthrough, the muxed sip-leg media (plan of record, verified, NOT yet implemented)

## The request

The bot bridges voice and pager-mode messages; now it bridges **video**:

1. `/video-call <aor>` — `/call`'s twin, except the SDP offer the bot
   sends on the SIP leg carries a **video `m=` line** (and the browser
   rings as a video call).
2. Inbound: when the caller's INVITE offer carries a video `m=` line,
   pass it to the WebRTC leg too — the browser rings as a video call,
   the 200 OK answers with a video section.
3. A **presumed WebRTC video codec list** mirrors the audio one
   (`webrtcCodecs`): configurable, with sane defaults — it is the
   sip-leg offer's video codec list and the inbound selection order.
4. **Port reuse**: in the SDP the bot originates (either leg), audio +
   video + telephone-event RTP share **one port** where possible (the
   WebRTC leg gets it free — pion always BUNDLEs); and the bot
   **respects the peer's answer**: a peer that answers video on a
   different port gets the bot's video sent there.
5. **diago patch is the LAST RESORT — the user explicitly asked for a
   clean solution WITHOUT patching the vendored diago.** (Verified
   below: achievable, diago's own exported seams suffice.)

## Library facts verified in source (the load-bearing mechanics)

### diago (vendored v0.32.2 + patches 1–3 — no patch needed for this)

- **Static-SDP injection is the seam.** `DialogClientSession.Invite` →
  `invite()` does `inviteReq.SetBody(sess.LocalSDP())`
  (dialog_client_session.go:229), and `LocalSDP()` returns `s.sdp`
  verbatim when set (media_session.go:341-344) — `InitWithSDP(sdp)` is
  the setter (media_session.go:248-270). `initMediaSessionFromConf`
  **no-ops when `d.mediaSession != nil`** (dialog_media.go:151-157), and
  `DialogMedia.InitMediaSession(m, r, w)` is exported
  (dialog_media.go:132). So: build a `media.MediaSession` by hand,
  `Init()` (opens the RTP/RTCP sockets, assigns the port), generate the
  full SDP (audio + video) ourselves, `InitWithSDP(it)`, inject it into
  the dialog before `Invite()` — the wire carries OUR SDP.
- `InitWithSDP` re-parses our SDP: Laddr from c= + m=audio (must equal
  the Init'd socket — we generate from it, so consistent), Mode
  sendrecv, and **replaces `s.Codecs` parsed from our audio m-line**
  (Fmtp is lost — harmless: `codecsMatch` excludes Fmtp, and LocalSDP
  stays static so nothing regenerates).
- **Outbound answer path untouched by the injection**: `waitAnswer` →
  `applyRemoteSDP` → `checkEarlyMedia` → errNoRTPSession (rtpSession is
  nil) → `sess.RemoteSDP(answer)` on OUR session (audio-only parse; a
  video m-line in the answer is simply never read — no error) → diago
  itself creates the RTPSession, the packet reader/writer, and runs
  `MonitorBackground()` (dialog_client_session.go:357-380). `Ack()` →
  `Finalize()` is a nil-op without DTLS. `MediaProps.Codec` =
  filterCodecs' first non-telephone-event — the negotiated audio codec,
  exactly as today. On dial error, `errors.Join(err, dialog.Close())`
  closes our injected session's sockets via `DialogMedia.Close`
  (dialog_media.go:83-113 — `m.Close()` when `m != nil`).
- **Inbound answer path**: with `d.mediaSession != nil`,
  `Answer()`/`AnswerOptions()` take the early branch:
  `RespondSDP(d.mediaSession.LocalSDP())` — our static answer SDP on the
  wire, ACK-awaited as today (dialog_server_session.go:133-149,
  174-195). The early branch does NOT run `RemoteSDP(offer)` nor create
  the RTPSession — so serveInbound does both itself, all exported:
  `sess.RemoteSDP(offer)` (audio negotiation + Raddr off the offer),
  `rtpSess := media.NewRTPSession(sess)`, `rtpSess.MonitorBackground()`
  (requires Raddr set — it is),
  `inDialog.InitMediaSession(sess, media.NewRTPPacketReaderSession(rtpSess), media.NewRTPPacketWriterSession(rtpSess))`.
  **`d.rtpSession` stays nil on this path** → `DialogMedia.Close` will
  not `MonitorClose` it → the monitor goroutines (rtcpTicker) would leak
  — so register `inDialog.OnClose(func() error { return rtpSess.Close() })`
  (`OnClose` is exported, dialog_media.go:115; hooks run before
  `m.Close()`). Side effect: a mid-call re-INVITE on an inbound video
  call fails (replaceRTPSessionUnsafe needs rtpSession) — a documented
  caveat; audio-only calls keep the native path.
- **The read path surfaces every PT** (no PT filter in
  `RTPSession.ReadRTP`, rtp_session.go:263-360) — telephone-event
  already surfaces this way (the relay drops it by PT). **THE TRAP**:
  the read-stats gate — on an SSRC *switch*, a packet whose PT is not in
  `sess.Codecs` logs "unsupported payload_type" and returns `(0, nil)`
  (rtp_session.go:298-315); with muxed audio+video (two SSRCs
  alternating) EVERY video packet would hit it, and the
  RTPPacketReader.Read then returns 0 with a STALE PacketHeader.
  **Fix without a patch**: after `InitWithSDP`,
  `sess.Codecs = append(sess.Codecs, videoCodecs...)` (exported field).
  Audio negotiation is unaffected (the answer's audio codecs never
  name-match video entries). (A defensive `n == 0 → continue` in the
  pump is still warranted — keep-alive/zero reads exist.)
- **The write path**: `RTPPacketWriter.WriteSamples(payload, tsDelta,
  marker, payloadType)` is exported and bypasses the 20 ms ticker
  (rtp_packet_writer.go:163-168 — only `Write` waits on it);
  `NewRTPPacketWriter(w RTPWriter, codec)` + `ClockDisable()` (kills the
  ticker). `MediaSession.WriteRTPRaw(data)` is exported
  (media_session.go:1087) — writes a marshaled datagram to Raddr on the
  dialog's own socket (the muxed video send: right source port), does
  NOT touch `WriteRTP`'s shared `writeRTPBuf` (no race with the audio
  writer), and UDP writes are datagram-atomic. For a **demuxed answer**
  (the peer's video port ≠ its audio port — common, e.g. Asterisk): a
  bot-owned UDP socket bound to the session's Laddr.IP sends to the
  peer's video address (the send source port is unconstrained in RTP;
  the bot is direct-routed — caveat 9). Both behind a small
  `media.RTPWriter` implementation each.
- `media.CodecsFromSDPRead` (codec.go:164) resolves dynamic PTs through
  rtpmap lines — reused for the bot's video parse of offers/answers (its
  static-PT shorthands are audio-biased; video PTs are dynamic anyway).
- The vendored sdp package (media/sdp/sdp.go) is a FLATTENED map:
  `MediaDescription("video")` returns the single video m-line (errors
  only on >1 of the same type); `Values("a")` flattens all attributes
  (so video formats resolve against all rtpmap lines — fine while PTs
  are globally unique, which every normal offer keeps; the pathological
  per-m-line PT reuse is a documented caveat, pre-existing for audio).
- `media.GetCurrentNTPTimestamp()` (rtp_utils.go:22) and
  `sip.ResolveInterfacesIP` (used by diago at dialog_media.go:162) are
  exported — the SDP o= line and the unspecified-bind fallback reuse
  them.
- diago's `WithTransport` (diago.go:87-122) computes the media bind/
  external IPs we must mirror in the hand-built session: bindIP =
  parse(bindHost) — the bot's `bindHostFor` always yields one — with
  `ResolveInterfacesIP` as the unspecified fallback; externalIP =
  parse(ExternalHost) when non-unspecified, else bindIP. NewDiago's
  mediaConf for the bot: secureRTP 0, rtpNAT 0, dtls nil (the bot passes
  only Codecs) — plain RTP, no write-side NAT latching.
- `Codec.SampleDur` on our video codecs is cosmetic (the writer's ticker
  is disabled, WriteSamples takes explicit deltas) — set 33 ms.

### pion v4.2.20

- `TrackLocalStaticRTP.WriteRTP` rewrites SSRC + PT to the bound values
  and preserves Timestamp/SequenceNumber/Marker
  (track_local_static.go) — the SIP→browser video write; the payload
  alias is safe (synchronous marshal). `Kind()` derives from the codec's
  mime prefix — the video track needs a video/* capability.
- `RTPTransceiver.SetCodecPreferences` validates via
  `codecParametersFuzzySearch` (rtptransceiver.go:54-69,
  rtpcodec.go:108): exact (mime+rate+channels+fmtp) then partial
  (mime+rate+channels) — partial suffices. Pin params: VP8
  `{MimeType: webrtc.MimeTypeVP8, ClockRate: 90000}` (exact); H264
  `{MimeType: webrtc.MimeTypeH264, ClockRate: 90000, SDPFmtpLine:
  "level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f"}`
  (exact vs the engine's PT-106 entry); VP9 `{"profile-id=0"}` if the
  vocabulary includes it. A bare pin intersects RTCPFeedback to ∅
  (`rtcpFeedbackIntersection(nil, engine)`) → the offer's video m-line
  carries NO rtcp-fb — consistent with v1's no-PLI-forwarding (caveat).
- The engine's default video registrations (already in
  `stereoOpusPCFactory` via `RegisterDefaultCodecs`,
  cmd/server/main.go:568): VP8=96, VP9=98/100, AV1=45, H265=116, H264 in
  six fmtp variants (102/104/106/108/127/39) + RTX satellites. **No
  factory change needed**; the webrtc-leg video PT is pion's own (VP8
  96), the sip-leg's video PTs are the bot's constants — the legs are
  separate PT spaces, the relay re-stamps.

## The design (NO diago patch)

New file **`pkg/rtc/sipbot/video.go`**:

- The video codec vocabulary: `defaultWebRTCVideoCodecs = ["vp8",
  "h264"]` (VP8 first — every browser, royalty-free, no fmtp; H264 — the
  SIP world's common denominator); `ParseWebRTCVideoCodecs(csv)`
  mirroring the audio parse; `sipVideoCodecByName`: vp8 →
  `{Name:"VP8", PayloadType:102, SampleRate:90000, SampleDur:33ms}`,
  h264 → `{Name:"H264", PayloadType:103, SampleRate:90000, Fmtp:
  "packetization-mode=1;profile-level-id=42e01f"}` (vp9 → 104, if
  admitted to the vocabulary — pion's engine has it). PTs 102+ are clear
  of the audio offer's 0/8/9/96/101 (a customized audio list must keep
  that true — note in docs).
- `webrtcVideoCodecParams(codec)` → the pion pin (above).
- Video SDP reads (diago's own parser): `videoCodecsFromSDP(body)`;
  `selectVideoFromAnswer(body, presumed)` — outbound: the answer's first
  video codec matching our offered by name+rate (the callee's pick), the
  answer's video addr (c= IP + m=video port); port 0 or no video m-line
  → no video (degrade to voice). `selectVideoFromOffer(body, presumed)`
  — inbound: the first PRESUMED codec the offer carries (browser
  preference order, audio's selectCodec mirrored), **adopting the
  offer's PT** (the answer echoes — RFC 3264), the offer's video addr,
  the offered format list (for a rejection line), and the offered fmtp
  for h264 echo (`a=fmtp:<pt> ` grep — CodecsFromSDPRead does not parse
  fmtp). Both PT directions are the SAME number by RFC 3264's echo rule
  — one videoPT per call.
- The SDP generator replicating diago's `generateSDPForAudio` shape
  (media_session.go:1220-1315): same head (`v=0`, `o=- <NTP>>32 <same>
  IN IPx <originIP>`, `s=Sip Go Media`, `c=IN IPx <connIP>`, `t=0 0`),
  the audio section (PCMU/PCMA/G722 static rtpmap lines, opus
  `a=rtpmap:96 opus/48000/2` + fmtp from the codec's Fmtp or
  `useinbandfec=0`, telephone-event 101 + `0-16`, `a=ptime:20`,
  `a=maxptime:20`, `a=sendrecv`), then the video section on the SAME
  port: `m=video <port> RTP/AVP <pts>`, rtpmap lines, h264's fmtp,
  `a=sendrecv`. The answer variant: audio section from
  `sess.CommonCodecs()` (the negotiated filter), video = the selected
  codec at the OFFER's PT (+ fmtp echo), or the rejection
  `m=video 0 RTP/AVP <offered formats>` (RFC 3264 keeps the format
  list). Plain RTP/AVP only (the bot's sip leg never does SDES/DTLS).
- `sipStack.newVideoMediaSession(ctx, session)`: mirror diago's
  bind/external IP logic; `&media.MediaSession{Codecs:
  clone(stack.codecs), Laddr: {IP: bindIP}, ExternalIP: externalIP,
  Mode: sendrecv}` → `Init()` → generate → `InitWithSDP` → append the
  video codecs to `sess.Codecs` (the read-stats gate).
- The browser→SIP video writers: `sessionRTPWriter{sess}` (muxed:
  marshal + `sess.WriteRTPRaw`) and `udpRTPWriter{conn, raddr}`
  (demuxed: own socket on sess.Laddr.IP) — both `media.RTPWriter`; the
  packetizer is `media.NewRTPPacketWriter(that, videoCodec)` +
  `ClockDisable()`, driven by `WriteSamples(payload, tsDeltaFromPrev,
  marker, videoPT)`.

## Considerations weighed (the caveats to write)

- **No PLI/FIR/NACK crosses in v1** (either direction): the pinned
  webrtc-leg video m-line carries no rtcp-fb; a decoder needing a
  keyframe waits for the sender's periodic one (browsers keyframe at
  stream start, which follows the answer — the first picture always
  lands). Follow-up: forward PLI (pion's WriteRTCP ↔ the session's
  WriteRTCP).
- H264 profile interop is nominal (42e01f pinned on both legs) — an
  endpoint sending an incompatible profile yields forwarded-but-
  undecodable video; VP8-first default order minimizes it.
- Muxed reads flip-flop diago's single-SSRC read stats — cosmetic
  (RRs alternate SSRC).
- The demuxed-answer fallback sends video from a dedicated socket
  (same local IP, different source port) — symmetric-RTP peers latch;
  the deployment is direct-routed (caveat 9).
- Early media (183+SDP) stays unsupported (caveat 5) — the video
  parse reads only the final answer.
- Mid-call re-INVITE on an INBOUND video call fails (the injected
  path leaves d.rtpSession nil); audio-only calls unaffected;
  mid-call media changes are caveat 4's territory anyway.
- A caller reusing one PT for two codecs across m-lines (legal in
  classic SDP) confuses the flattened attribute parse — pre-existing
  diago shape, documented.
