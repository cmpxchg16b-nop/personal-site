## Correction 1: session 38's "no diago patch" premise was WRONG — patch 4 exists

Session 38 verified "`MediaDescription("video")` errors only on >1 of
the same type" — false: the vendored `sdp.MediaDescription` errors on
**any SDP with more than one m-line total** (`if len(values) > 1` on ALL
m= lines, before the type filter — which was dead code). Every
audio+video SDP failed to parse: our own `InitWithSDP(offer/answer)`,
the inbound `RemoteSDP(offer)`, and — the unrecoverable one — diago's
own client answer path (`waitAnswer → applyRemoteSDP →
sess.RemoteSDP(answer)` → Ack+Bye, no exported seam around it;
checkEarlyMedia's rtpSession branch funnels into the same RemoteSDP).

So `third_party/diago` gained **patch 4**: the guard counts only m-lines
of the requested type (the type filter does the real work). Single-m-line
SDPs — all upstream ever parses — behave byte-identically; the vendored
module's own tests pass. PATCHES.md documents it. The user's "patch is
the last resort" condition was met: no seam exists. The rest of the
no-patch design then worked exactly as planned.

## Correction 2: pion's VP8 payloader transforms WriteSample payloads

`TrackLocalStaticSample.WriteSample` on a VP8 track runs pion's
VP8Payloader, which PREPENDS the VP8 payload descriptor (1–4 bytes:
`vp8HeaderSize` + pictureID; EnablePictureID is on in pion's engine
default, so the prefix grows as the pictureID climbs). The browser-side
probe's camera must be a `TrackLocalStaticRTP` written with `WriteRTP`
(which bypasses the payloader) for the byte-for-byte assertions to hold.
(SIP→browser was unaffected: the bot's own video track toward the
browser is already a TrackLocalStaticRTP, and the fake streams raw.)
