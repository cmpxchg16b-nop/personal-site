# Session 40 — group chat, step 1: the virtual subscriber in the SS data model + the group-chat design doc

The user is extending the WebRTC chat subsystem (person-to-person only
today) to group chat — in tiny steps, not one-off. This session is step
1: the data model learns the virtual subscriber (groups are its first
instance), and the design doc exists.

## Course corrections mid-session (user directives)

1. First draft carried `subscriberType` ON the register event (clients
   declare their type). REJECTED: **no one can register as a group** —
   the register event stays exactly what it was; a person cannot claim
   to be a group. Groups are **completely virtual**, living purely in a
   **GroupRepository** the SS consults alongside its registration state.
2. Fan-out candidates must be ordered **from possible to impossible**:
   SFU, MCU, P2P.
3. When the SS receives an SDP offer targeting a group (e.g. the user
   clicks a group chat in the browser, the browser reconciles a peer
   session per member), it logs `group chat unimplemented (todo)` to the
   console.
4. TERMINOLOGY: there is no such thing as a "virtual group". The
   concept pair is **actual subscriber** (backed by a real UA
   registration — a browser or a bot) vs **virtual subscriber** (a
   subscriber that exists in a channel WITHOUT any real UA registration
   behind it); **a group is an INSTANCE — the first instance — of the
   virtual-subscriber concept**. Docs and code comments use exactly
   that.
5. ROLE NUMBERS: **the lower the number, the higher the privilege** —
   `GroupRoleOwner` 0, `GroupRoleAdmin` 1, `GroupRoleMember` 2 — so a
   re-join with a LOWER-numbered role is a promotion.

## What shipped

- `docs/group-chat.md` (new, living doc): the idea — the **actual
  subscriber** (backed by a real UA registration) vs the **virtual
  subscriber** (exists in a channel with NO registration behind it), a
  **group being the FIRST INSTANCE of the virtual-subscriber concept** —
  step 1's patch list, the road ahead (creation — no wire event yet, the
  repo is the seam; membership; fan-out SFU > MCU > P2P; calls out of
  scope; UI).
- `pkg/models/ss/groups.go` (new): `Group{ChannelId, SubscriberId,
Name}`, `GroupRepository` interface, `OnMemoryGroupRepository`
  (RWMutex-guarded, defensive copies, `ErrGroupExists` on duplicate),
  and the `var _ GroupRepository` assertion. Group methods:
  `CreateGroup` / `DeleteGroup` (no-op when absent; also drops the
  group's memberships) / `GetGroupsByChannelId` (sorted) /
  `GetGroupBySubscriberId` (nil,nil on miss) — all ctx-aware. The
  interface ALSO carries the RELATIONSHIP methods (user directive):
  `JoinGroup(ctx, channelId, groupId, operator, member, role)` and
  `LeaveGroup(ctx, channelId, groupId, operator, member)`. `GroupRole`
  numbers run LOWER-NUMBER = HIGHER-PRIVILEGE (`GroupRoleOwner` 0,
  `GroupRoleAdmin` 1, `GroupRoleMember` 2), so a re-join with a
  lower-numbered role IS a promotion; an identical (member, role, group)
  re-join is a NO-OP; a different role updates the record (promotion or
  demotion). The operator is recorded on the membership
  (`GroupMembership.Operator`): operator == member means a self-action,
  otherwise it reads as e.g. "admin [operator] invited/promoted/kicked
  x". The repo RECORDS, it never authorizes — who-may-add-whom is the
  caller's policy. Join to an unknown group → `ErrGroupNotFound`; leave
  of a non-member / unknown group → no-op. No membership READ method yet
  — it lands with the step that needs it (fan-out); the same-package
  test inspects the impl white-box.
- `pkg/models/ss/ss.go`:
  - `SubscriberType` string type + `SubscriberTypePerson` /
    `SubscriberTypeGroup` constants; every REGISTERED subscriber is a
    person.
  - `UserProfile.SubscriberType` (`json:"subscriberType"`, always
    present). Register event UNCHANGED.
  - New error code 6 `ErrorCodeSubscriberIdTakenByGroup`.
  - Provider gains an INJECTED `groups GroupRepository` (interface only,
    never the concrete impl — DI): `NewSimpleOnMemorySSProvider(groups)`
    / `NewSimpleOnMemorySSProviderWithAging(aging, groups)`, nil → fresh
    in-memory repo. `cmd/server` wires `NewOnMemoryGroupRepository()`
    explicitly.
  - `handleRegister`: a group-occupied id is rejected with
    TakenByGroup; `assignSubscriberId` gained an `occupied` predicate so
    auto-assignment skips group-held ids.
  - `handleListChannelMembers`: registered subscribers + group ids,
    merged, deduped, sorted, paged together.
  - `handleQueryProfile`: group repository FIRST, then registered
    subscribers, until a hit (group → type group + its Name; registered
    → type person).
  - `handleRelay`: a c2c event to a group is unroutable (a virtual
    subscriber has no address) → SubscriberNotFound; if it carries an
    SDP OFFER, additionally `slog` Warn `group chat unimplemented
(todo)` (only offers log — trickle candidates would spam).
  - Repo errors: ctx cancellation stops the handler; other errors
    degrade (listing → persons only, profile → falls through to
    registrations).
- TS prototype (`web/site/src/api/ss/types.ts`): `SubscriberType =
"person" | "group"`, `UserProfile.subscriberType`, error-code enum
