# Session 40 — ICE auto-reconnect: audit, implementation, review findings, and results (implemented and validated)

## The request

Evaluate whether and how an established WebRTC peer connection automatically
recovers after ICE/WebRTC disconnects. **“ICE auto-reconnect”** is the shorthand
for this investigation.

The subject is the browser `RTCPeerConnection` and the pion `PeerConnection`
used by the headless clients. A signalling reconnect or a brand-new peer session
is not, by itself, evidence that ICE auto-reconnect is implemented.

The requested target is automatic ICE recovery in the browser after a
disconnect, with a short initial sleep and capped exponential retry. The bot
needs the equivalent too: its peer connections face the same ICE failures, and
its outer WebSocket reconnect loop cannot repair ICE while signalling remains
alive.

## Scope

In scope:

- ICE / peer-connection transitions to `disconnected` and `failed` after an
  initially usable connection, while the signalling path remains available.
- Whether those transitions are merely observed or trigger automatic recovery.
- Recovery through ICE restart and renegotiation, or deliberate peer-connection
  recreation if that is the actual design.
- Restoration of media and data channels, including behavior across repeated
  failures and intentional teardown.
- Browser and pion/headless-client behavior, plus their interoperability.

Out of scope except where it directly supports ICE restart:

- WebSocket redial, SS re-registration, and membership reconciliation.
- The built-in bots' outer signalling reconnect loops.
- Rebuilding every peer session because the signalling proxy was replaced.

## Questions to answer from code

1. **Detection:** which `oniceconnectionstatechange`,
   `onconnectionstatechange`, `OnICEConnectionStateChange`, or
   `OnConnectionStateChange` handlers exist? Do they update UI/logs only, or
   initiate recovery?
2. **Disconnected versus failed:** is transient `disconnected` given a grace
   period or left to the WebRTC implementation's own connectivity checks? Is
   `failed` treated differently? Is `closed` correctly excluded?
3. **Restart trigger:** does either side invoke an ICE-restart API or recreate
   its peer connection? What prevents both peers from restarting simultaneously?
4. **Negotiation:** if ICE restarts, how does the new offer/answer travel through
   the existing negotiator, and how are offer collisions and DTLS roles handled?
5. **Lifecycle:** are timers, retries, and late state events canceled on session
   teardown? Can an old session restart after it has been replaced?
6. **State after recovery:** do existing tracks, senders, data channels, and
   call state survive, or are they explicitly rebuilt/reset?
7. **Retry policy:** what happens if recovery fails repeatedly — retry limit,
   delay/backoff, terminal teardown, or an unbounded loop?

## Code paths to trace

- Browser offer/answer and ICE-restart negotiation:

- Browser data-channel/media consumers, to establish what survives recovery.
- Headless peer lifecycle: `pkg/rtc/client.go`.

- Existing tests around those files; locate any frontend state/recovery tests

- Bot call/media state only after the core lifecycle is understood, especially
  where a recovered or replaced peer connection would affect an active call.

## Initial audit findings (pre-implementation)

- **Browser:** `peersessions.tsx:251-254` only reports `pc.connectionState` to
  the UI hook. There is no `oniceconnectionstatechange` or `restartIce()` in
  `web/site/src`; `negotiate.ts` handles SDP and candidates but no ICE failure.
- **Bot:** `client.go:1216-1229` attaches only `OnDataChannel` and `OnTrack`;
  `negotiate.go:285-299` attaches only negotiation-needed and ICE-candidate
  callbacks. No ICE-state recovery exists in `pkg/rtc`.
- **Verdict:** application-level ICE auto-reconnect is currently **absent in
  both UAs**. WebRTC's own connectivity checks may heal a transient outage, but
  there is no application-driven restart when they do not.
- **API facts:** browser `restartIce()` fires `negotiationneeded` and keeps the
  restart request pending across incomplete negotiation (MDN, verified). Pion
  v4.2.20 has no `PeerConnection.RestartIce()` method; its equivalent is
  `CreateOffer(&OfferOptions{ICERestart: true})` (`go doc`, verified).

## Target behavior and design constraints

- Put recovery in each UA's negotiation layer: it already owns offers, answers,
  candidates, and glare. Browser and bot should implement the same policy.
- Arm recovery only after a connection has first become usable. On a later
  `disconnected`, wait a few seconds so transient outages can heal; on `failed`,
  act promptly. If recovery does not reach a connected state, retry with capped
  exponential backoff and jitter rather than a tight loop.
- A successful connection cancels pending retries and resets the backoff.
  Session teardown and negotiator shutdown cancel them too; stale callbacks from
  a replaced pion connection must not restart the new incarnation.
- Browser recovery calls `pc.restartIce()` and lets the existing
  `onnegotiationneeded` path make the offer. Pion recovery requests an offer
  with `OfferOptions.ICERestart`; because its current `makeOffer` skips unstable
  states, the Go implementation must latch the restart request until an offer
  can actually be made rather than dropping it.
- Reuse the existing peer connection in the normal case, preserving tracks,
  data channels, and call state. Either UA may detect the failure and drive
  recovery, but only the **polite** UA originates an automated ICE-restart
  offer. The impolite UA sends `iceRestartRequest` over the existing c2c
  signalling path and keeps its retry watchdog until ICE reconnects. This
  prevents simultaneous automated restarts from entering pion's established-
  session glare-rebuild path.
- Keep the session alive between retries; membership teardown remains the
  terminal condition. The implementation defaults are a **3 second** disconnect
  grace, an immediate first restart on `failed`, and retries of **2, 4, 8, 16,
  30, 30… seconds**, capped at 30 seconds and independently jittered by ±20%.

## Evaluation method

1. Inventory all ICE/connection-state handlers and all ICE-restart,
   renegotiation, session-close, and session-recreation calls, with file/line
   references.
2. Draw the recovery sequence separately for browser-initiated and
   pion-initiated recovery. Identify the side that acts, the messages exchanged,
   and the point where media/data becomes usable again.
3. Distinguish WebRTC's built-in connectivity behavior from an application-level
   auto-reconnect feature. No explicit restart logic may still be a deliberate
   design, but it must not be reported as implemented application recovery.
4. Inspect tests for actual ICE/transport failure with signalling kept alive.
   Closing the WebSocket or calling `close()` does not test ICE auto-reconnect.
5. If existing tests cannot establish the behavior, propose focused failure-
   injection tests before changing implementation. Verify recovery of media or
   a data channel, not only a return to a `connected` state.
6. Run the narrow browser/Go tests needed to confirm the findings. This audit
   alone does not authorize implementation changes.

## Implementation plan (authorized; completed)

**Execution correction:** the first simultaneous-failure test forced both pion
peers to offer an ICE restart together. The polite peer's established-session
glare rebuild left its replacement data channel stuck connecting; initial-glare
tests do not cover that transport mismatch. The recovery protocol therefore
uses single-owner restart offers rather than relying on that glare path.

1. **Browser policy:** add a small ICE-recovery controller beside
   `negotiate.ts`. It arms only after `connected`/`completed`, waits 3 seconds
   on `disconnected`, restarts immediately on `failed`, and keeps a retry
   watchdog through `checking` until recovery or teardown. A polite controller
   calls `restartIce()`; an impolite one requests a restart through c2c.
2. **Recovery protocol:** add optional `iceRestartRequest` to the matching
   TypeScript and Go `ClientToClientEv` models. The SS remains a dumb relay.
   Only the polite negotiator honors the request, using its normal ICE-restart
   offer path; the requester owns the retry/backoff until ICE reconnects.
3. **Pion policy:** add the same state machine to `PerfectNegotiator`. Funnel
   every pion callback through its single-owner event loop with a source-PC tag
   to reject stale events, and drive the retry timer from the loop's `select`.
4. **Pion offers:** refactor `makeOffer` to accept ICE-restart intent. Latch a
   restart requested outside the stable signaling state, consume it on the next
   successful local offer (including an already-needed renegotiation), and keep
   the retry watchdog armed until ICE actually reconnects. Re-check live ICE at
   timer entry so a queued connected event cannot race a redundant restart.
5. **Lifecycle:** stop timers and detach ICE-state handlers on negotiator
   shutdown; reset backoff only on a real connected state. Normal restart keeps
   the same peer connection, tracks, and data channels. Repeated `failed`
   transitions must not reset an active retry's backoff to zero.
6. **Browser tests:** add Vitest as the project's first focused frontend unit
   test runner. Use fake timers for grace, immediate failure, exponential cap
   and jitter, spontaneous recovery, checking-state retries, pre-connection
   failures, errors, and close cancellation. Add negotiator-level tests for
   polite restart offers, impolite requests, and honoring a peer's request.
7. **Pion tests:** add state/backoff/unit protocol tests and real two-peer tests
   through `SimpleOnMemorySSProvider`. Cover either role independently and both
   roles failing together; assert fresh SDP ICE credentials, no ordinary
   recovery PC replacement, and a working existing data channel.
8. **Validation and note:** run gofmt, the focused rtc tests (including race),
   the frontend ICE tests, lint/type/build checks, then broader Go tests as
   confidence allows. Replace this executing status with the implementation
   result, exact validation commands, and any remaining live-browser/network
   failure-injection blind spots.

## Intermediate findings and review corrections

1. **A retry could bypass its own backoff.** The first implementation treated
   every `failed` transition as an immediate restart. Each unsuccessful attempt
   could therefore go checking → failed → immediate restart forever. Both UAs
   now accelerate only the initial failure, or a failure during the pre-first-
   attempt disconnect grace; once an attempt is active, later failures wait for
   the exponential watchdog.
2. **A timer can race the recovery notification.** A Pion retry timer and the
   queued connected event can be ready together; processing the timer first
   would restart already-healthy ICE. Timer entry now re-checks the live
   transport. The same guard already existed in the browser controller.
3. **`completed` is healthy too.** Final review caught that pion's
   `ICEConnectionStateCompleted` was initially omitted. Like `connected`, it now
   arms future recovery, cancels an active recovery, resets backoff, and stops
   the timer-entry restart. Browser `completed` handling was already present.
4. **Stale-event protection had to cover every callback, not just ICE state.**
   Tagging only ICE-state events left queued negotiation-needed and candidate
   events from a glare-replaced PC able to emit traffic for its replacement.
   Every Pion-originated local event now carries its source PC and is discarded
   after that source is replaced. Tests cover stale state, offers, and the
   end-of-candidates case.
5. **Unstable signaling needed an explicit Pion latch.** Browser `restartIce()`
   retains restart intent across in-flight negotiation; Pion's
   `CreateOffer(OfferOptions{ICERestart:true})` does not provide that control
   flow. A restart outside stable is now latched, emitted when an answer/offer
   returns signaling to stable, and consumed by the next successful local
   offer. A unit test applies a real answer and verifies fresh credentials.
6. **The simultaneous-restart test falsified the original glare assumption.**
   Forcing both established Pion peers to offer a restart together made the
   polite peer rebuild; its replacement data channel stayed `connecting` for
   the full 30-second timeout. The initial-glare suite passes and even shows
   the same extra ordinary offer, so that offer alone was not the root cause —
   the new failure was the one-sided rebuild of an already-established
   ICE/DTLS/SCTP session. This drove the protocol correction: only the polite
   peer originates automated restart offers; the impolite peer sends
   `iceRestartRequest` and retains the retry watchdog. Both roles can still
   detect and drive recovery independently, including asymmetric failures.
7. **Frontend test tooling had a version constraint.** Latest Vitest 5 required
   newer `@types/node` than the project's existing v20. Vitest 4.1.12 supports
   that dependency set and was selected instead of forcing installation or
   upgrading unrelated Node types.

## Implementation result

- `web/site/src/api/ss/ice_restart.ts` implements the browser state machine:
  arm after connected/completed, 3-second disconnect grace, immediate initial
  failure action, 2/4/8/16/30-second capped retries with ±20% jitter, retry
  through checking, and cancellation on recovery/close.
- `web/site/src/api/ss/negotiate.ts` owns the browser ICE handler and the
  single-owner protocol: polite calls `restartIce()`, impolite sends a request,
  and polite honors requests through the existing negotiation-needed path.
- `pkg/rtc/negotiate.go` mirrors the policy for every built-in bot peer:
  serialized ICE events, live-state timer checks, pending restart offers,
  source-tagged callbacks, and `OfferOptions.ICERestart`. No bot-specific outer
  WebSocket supervisor changes were needed.
- `web/site/src/api/ss/types.ts` and `pkg/models/ss/ss.go` add the matching
  optional `iceRestartRequest` wire field; the SS remains a dumb relay.
  `docs/signalling-server.md` documents the protocol and ownership rule.
- Normal recovery reuses the existing peer connection, so tracks, data
  channels, and call state are not rebuilt. The tests prove fresh ICE
  credentials and bidirectional messages on the original data channel for
  either role and for simultaneous failure.
- `pkg/rtc/ice_restart_test.go` adds the state/backoff/protocol unit coverage
  and real two-peer SDP/ICE tests. `ice_restart.test.ts` and `negotiate.test.ts`
  add 13 browser tests. `web/site/package.json` gains `npm test` (Vitest), with
  the compatible dependency locked in `package-lock.json`.

## Remaining test blind spots

- The Pion tests inject disconnected/failed through the real negotiator event
  queue while running actual SDP/ICE negotiation; they do not impose an OS-level
  packet blackout. The browser tests use a mocked UA and fake timers. A live
  browser ↔ bot test with real network impairment remains follow-up coverage.
- Existing data-channel continuity is explicitly tested. Active audio/video
  continuity after ICE restart is not separately fault-injected, although normal
  recovery deliberately retains the PC and all full RTC/media suites pass.
