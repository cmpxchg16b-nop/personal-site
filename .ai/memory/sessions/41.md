# Request

Investigate why selecting a peer or bot on `/chat` can leave the status at
`Unconnected` indefinitely, with no local or remote ICE candidates visible in
browser WebRTC diagnostics. The current hypothesis is a connection-lifecycle
logic issue rather than signaling or ICE configuration.

# Scope and status

Status: complete. Investigation, implementation, two review/correction rounds,
validation, and final note writeback are finished. The delegated review loop was
stopped after round 2 at the user's direction; no review round 3 was run.

Trace the peer-selection and connection startup path, identify reproducible or
code-confirmed causes, implement the smallest justified fix, and validate it.
Record review findings and corrections here. Avoid changing signaling or ICE
behavior without evidence that it is involved.

# Initial considerations

- No candidates suggests startup may be blocked before `setRemoteDescription`,
  `createOffer`/`createAnswer`, or `setLocalDescription`, rather than candidate
  gathering itself failing.
- Check ordering, awaiting, initialization guards, stale async continuations,
  peer/bot branch differences, and error handling that could leave the UI in
  `Unconnected` without surfacing a failure.
- Distinguish verified facts from hypotheses; browser candidate visibility alone
  does not establish which lifecycle step was reached.

# Investigation and plan

## Verified findings from initial inspection

- Clicking a peer only selects the rendered conversation. `usePeerSessions`
  creates sessions automatically from channel membership; selection itself does
  not start WebRTC.
- The header renders `Unconnected` for a missing state or `new`. Its lookup uses
  the selected user id, which is currently the signalling subscriber id, so the
  label alone does not distinguish a missing session from a stalled fresh one.
- Browser session creation waits for proxy, own channel/subscriber registration,
  channel membership, and settlement of `useICEServers`. A never-settling query
  prevents even `RTCPeerConnection` construction; query failure deliberately
  falls back to no configured ICE servers.
- Initial negotiation is demand-driven. Only the polite side creates subscribed
  data channels, and the first creation normally triggers `negotiationneeded`;
  the impolite side waits for an offer. No local candidates before that offer
  can therefore be normal on the impolite side, but neither side progressing is
  not.
- There are focused negotiator and ICE-restart tests, but no
  `usePeerSessions` lifecycle tests.
- Session 27 fixed a similar reload-specific deadlock caused by reusing a
  subscriber incarnation while the remote retained its stale session. Check
  whether that behavior regressed instead of rediscovering or blindly reapplying
  its fix.
- Current HEAD (`e109e57`) changed pion negotiation/ICE event handling and added
  browser ICE recovery. Its browser initial-offer path is mostly unchanged;
  recency alone is not evidence of causation.

## Narrowed implementation plan after reproduction

1. Keep session creation membership-driven (avoid the extra stale-listing
   lifecycle of offer-adopted sessions), but listen for c2c traffic before a
   peer session exists. A naïve early buffer plus a later switch to a fresh
   per-session proxy stream has a handoff race: the test injects membership
   synchronously after the offer, before the early reader's microtask can run.
2. Use one hook-level inbound reader feeding a per-peer queue. The queue is
   created by either an initial offer or membership, whichever comes first;
   every later c2c event for that pair uses the same queue. Thus both orders
   preserve offer/candidate delivery without synthesizing offers, altering
   ICE, or changing roles. Ignore stray answers/candidates that have no queue.
   Close queues on proxy/identity/membership teardown; graceful queue EOF is
   necessary to end negotiators now that their input is hook-owned.
3. Add a Vitest hook-lifecycle regression with a minimal React-hook runner
   and mock UA/transport (no new dependency): early offer + candidate, then
   membership, must produce remote SDP, an answer, and candidate handling.
   Also keep a polite initial-offer control and exercise teardown/reload where
   useful. Run this test against the unfixed code first.
4. Re-run the real Chromium harness against the fix and require SDP answer
   and candidate startup. Attempt data-channel opening, but distinguish a UA
   environment limitation with a plain native-PC control rather than masking
   it; use Firefox for full channel-open verification if available. Remove
   the temporary harness sources before normal project validation. (This
   wording records the plan correction after Chrome's control also failed.)

## Implementation and real-browser verification

- `web/site/src/api/ss/peersessions.tsx` now owns one proxy inbound reader and
  a `PeerInbox` per `(channel, peer)`. An unknown initial offer creates the
  inbox; membership creation uses the same inbox, or creates it first when the
  listing wins. Subsequent SDP/candidates/restart requests use that queue.
  This covers both event/membership orders without changing session creation,
  perfect negotiation, ICE restart, signalling wire format, or polite roles.

## Independent review round 1 and correction plan

The reviewer confirmed the original root cause and found two concrete defects
in the first fix:

1. **P1 — initial registration discarded pending offers.** The demux accepts
   offers while `me === null`, but the `[proxy, me]` teardown treats the initial
   null-to-registered transition like an identity replacement and closes every
   inbox. The required regression will queue offer + candidate with no identity,
   flush the demux, register without membership, then discover the peer. Current
   tests all started registered and missed this ordering.
2. **P2 — unadopted inboxes had no bounded lifecycle.** A sender that departed
   before ever appearing locally left its pending inbox until full teardown.
   Demux also accepted traffic addressed to a different subscriber. The
   correction must not drop an offer merely because one possibly stale listing
   omits its sender.

Focused correction plan:

- Distinguish only the genuine initial same-proxy null-to-registered transition
  from unmount, proxy replacement, and later identity replacement. Preserve
  pending inboxes through that initialization; every genuine replacement still
  performs full teardown. Filter demux by the current registered address and
  discard pending inboxes whose full `(channel, to, from)` address does not
  match the identity being initialized.
- Key inboxes by the full signalling address. For an unadopted inbox, retain
  the first completed own-channel listing that omits the sender (that snapshot
  may predate the offer), and retire it on the second consecutive such listing.
  A fresh offer resets that evidence; a listing without the own channel is not
  negative evidence and does not advance it. This bounds retention by progress
  of authoritative membership evidence rather than an arbitrary timer.
- Plan correction during implementation: `useSignalling` preserves the
  `channels` array identity across identical rounds, so reconciliation would
  otherwise never observe the second omission. Carry a separate monotonically
  increasing successful-listing revision into `usePeerSessions`; preserve the
  channel array identity, but rerun reconciliation on that revision. This
  changes no membership protocol and leaves existing sessions untouched.
- Add fail-before coverage for the exact P1 ordering and for an early sender
  that never appears. Also cover the one-absence retention race so the P2
  cleanup cannot reintroduce the original startup loss. No production timeout,
  forced offer, ICE, negotiation-role, or broad reconnect change is authorized.

- P1 correction: the teardown exempts only a same-proxy transition whose

- P2 correction: an unadopted inbox survives one possibly stale omission and

  identical omission actually reaches reconciliation. The expiry test reuses

## Independent review round 2 and correction plan

The reviewer verified the round-1 corrections and found two remaining concrete
lifecycle defects:

1. **P1 — best-effort listings were treated as expiry authority.** Member-page
   timeout/EOF still returns partial pages, and failed member-profile queries
   drop members from the rendered channel. Both can make a live early sender
   appear absent; two such rounds could retire its only offer. The UI should
   remain best-effort, but omission evidence requires a completed own-channel
   member listing with no transport truncation and no unresolved member
   profiles.
2. **P2 — definitive registration failure left pre-registration inboxes alive.**
   `me === null` conflated registration-pending with registration-failed, so
   reconcile returned forever and pending entries had no terminal cleanup.

Focused correction plan:

- Keep the existing best-effort `ChatChannel[]` UI output, but make the listing
  producer return separate per-channel membership-completeness metadata.
  Member paging must end with an explicit successful `hasMore: false`; every
  member profile needed for the rendered omission decision must resolve.
  Failed/incomplete rounds may still render partial UI, but cannot advance
  pending-inbox omission counts. Pass this metadata alongside the successful-
  listing revision into `usePeerSessions`.
- Expose registration failure as a distinct outcome from the actual
  registration promise. Pending retains the genuine pre-registration offer
  window; definitive failure performs terminal lifecycle cleanup and stops
  accepting new anonymous pending traffic. Do not infer failure from a timer
  local to the consumer.
- Add producer-level tests for truncated member pages and failed profile
  resolution. Add composed `useSignalling` → `usePeerSessions` regressions in
  which two faulty rounds cannot expire an early offer, plus a registration-
  failure outcome regression that proves pending state is cleared. Run these
  against the round-1 implementation before production edits and record exact
  failures.

Fail-before evidence for review round 2:

- `npm test -- --run src/api/ss/peersessions.test.tsx --silent` on the round-1
  production code: 12 tests, exactly 5 failed and 7 passed. Both producer
  completeness assertions were undefined; both composed faulty-round tests
  created the later PC but had `remoteDescription: null` after the complete
  listing; the registration-failure test replayed
  `offer-before-failed-registration`. All seven round-1 lifecycle tests passed.
- Harness-only setup corrections before that evidence: unanswered pongs were
  needed because unrelated pongs kept re-arming the page timeout, and producer
  listings had to use the well-known main-channel UUID used by real
  registration. These changes affected only test traffic, not production.

### Review round 2 correction result

- P1 correction: paged replies now retain the terminal reply (or null on
  timeout/EOF). A channel earns `completeMembershipChannelIds` membership only
  when member paging explicitly ends with successful `hasMore: false` and every
  member profile resolves. Partial pages and failed profiles still produce the
  same best-effort UI channels, but `usePeerSessions` cannot advance pending-
  inbox omission counts from them. The listing revision remains only the
  scheduling signal; the separate completeness result is the expiry authority.
- P2 correction: `useSignalling` exposes a proxy-scoped `registrationFailed`
  only after the actual registration promise finishes without a usable
  identity. Pending registration still preserves early offers. Definitive
  failure runs the existing full lifecycle cleanup and makes demux ignore new
  anonymous pending traffic; it does not stop the existing best-effort listing
  or ping behavior.
- The five new tests run real `useSignalling` producer logic with protocol
  replies and run `usePeerSessions` beneath it. Two assert incomplete producer
  metadata, two drive two faulty rounds then a complete discovery and prove
  the original offer answers, and one drives a real failed registration before
  proving stale pending SDP is not adopted and a fresh offer still works.
  These are not manually assigned ideal-revision tests.
- No real-UA or Go rerun was performed for this frontend producer/lifecycle
  rework; no Go, ICE, negotiation, or wire-format code changed.

# Outcome and remaining risks

polite peer's one initial offer when it arrived before browser membership

early signalling in the same per-peer inbox used by the eventual session;
