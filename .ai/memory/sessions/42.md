title: Preserve WebRTC calls across WebSocket reconnects
date: 2026-10-31
---

# Request

The chat WebRTC subsystem has ICE auto-reconnect, but every signalling WebSocket
disconnect/reconnect refreshes the UI and disrupts active phone/music sessions.
Make ordinary signalling reconnects non-destructive to live peer connections and
calls.

# Scope and status

Status: complete. Implementation, two independent review rounds and their
corrections, focused/broader validation, and final writeback are finished.

Scope the fix to browser signalling/WebRTC lifecycle and focused regression
coverage. Preserve fresh-incarnation behavior on page reload, real identity
changes, actual peer departure, and explicit teardown. Do not treat a signalling
transport interruption as proof that WebRTC media has failed.

# Investigation

## Verified findings

- `SSProxyProvider` publishes `null` on disconnect, then a new `SSProxy` after
  reconnect (`web/site/src/api/ss/react.tsx`).
- `useSignalling` scopes `me`, `channels`, and listing state to the current
  proxy. A disconnect therefore renders `me: null` and `channels: []` until the
  replacement connection registers and lists again.
- `usePeerSessions` explicitly tears down every `RTCPeerConnection` on a proxy
  swap or identity change. Its demux cleanup also closes all per-peer inboxes.
  `usePhoneCalls` force-ends live calls when those sessions reset. This directly
  explains the reported phone/music interruption.
- Each negotiator writes to a stream bound to its original proxy. Merely keeping
  the peer connection alive is insufficient: reconnection must also preserve or
  replace its signalling input/output without losing in-flight SDP/candidates.
- Registration currently always asks for a fresh auto-assigned subscriber id to
  avoid reusing a dead page incarnation after reload (session 27). Reusing an id
  indiscriminately would reintroduce that bug.
- The SS permits same-id re-registration by the same authenticated
  `(user id, user session id, channel id)` tuple as a refresh. Session 27 and
  `TestReconnectRelearnsAddress` explicitly identify this as the roaming
  reconnect case. The id may therefore be retained in memory for a socket
  reconnect within one page incarnation, but not across page loads.
- The existing hook-level Vitest harness exercises real `useSignalling` and
  `usePeerSessions` effect ordering with mock proxies/peer connections. It is a
  suitable place for a deterministic reconnect regression test.

## Design constraints and risks

- During the socket outage the existing peer connection, tracks, data channels,
  and call model must remain untouched. Media may continue directly over ICE.
- Re-register the previous subscriber id only on the replacement socket. If the
  server returns a different identity or registration definitively fails, use
  the existing real lifecycle teardown behavior.
- Keep the previous confirmed membership during reconnect. Rendering an empty
  listing would otherwise close the very sessions the transport fix preserves.
- A stable per-peer signalling output must queue events while no proxy is
  available and flush them in order to the replacement proxy. Inputs from all
  proxies must feed the same per-peer inbox; an old proxy cleanup must not close
  an inbox now serving a new proxy.
- Queued signalling is only valid for the same subscriber incarnation. Actual
  identity changes/unmount must discard it. Avoid closing a peer merely because
  the transport is temporarily absent.

# Plan

1. Add a failing reconnect regression at the hook level: establish a peer and
   call-relevant session, swap through `null` to a replacement proxy, and prove
   the unfixed code closes/recreates the peer and resets consumers.
2. Change `useSignalling` to retain the current in-page registration/listing
   across transport loss and request the same subscriber id when registering
   the replacement socket. Keep fresh-id registration for the initial mount.
3. Decouple peer-session lifetime from proxy identity. Rebind the demux to each
   live proxy without destroying peer inboxes, and give negotiators a stable
   ordered output that queues while disconnected and flushes after reconnect.
   Retain teardown for actual subscriber identity changes, peer departure, and
   unmount.
4. Add coverage for uninterrupted peer/media ownership and call state across
   reconnect, queued SDP/candidate delivery, same-id re-registration, and real
   identity/departure teardown. Check pre-existing early-offer and incomplete-
   listing lifecycle cases.
5. Run focused Vitest tests, the frontend suite, TypeScript/lint/build checks as
   proportionate, and `git diff --check`. Record exact commands/outcomes and any
   real-browser validation blind spots below.
6. Request a concrete independent review of the completed diff; minimize review
   rounds per project rules and correct confirmed issues.

## Independent review round 1 and correction plan

The read-only reviewer confirmed five concrete interleavings; all are in scope
and will be corrected before broader validation:

1. Queued c2c output could flush as soon as the replacement socket attached,
   before roaming registration completed, and be rejected after registration
   aging/server restart. Expose current-proxy registration readiness; gate
   output attachment and membership reconciliation on it while leaving inbound
   demux active. Hold a register reply in the test and assert no c2c flush.
2. EOF during pending registration could clear the retained incarnation before
   React cleanup marked the effect dead. Ignore registration outcomes from a
   destroyed proxy; cover a second disconnect while registration is held.
3. An in-flight listing could resolve empty from EOF and overwrite the retained
   good listing. Discard listings from a destroyed proxy; cover a held listing
   followed by disconnect.
4. Proxy-driven reconciliation could count the retained listing as another
   omission and expire an early offer. Make listing revisions monotonic across
   proxies and count omission evidence once per completed listing revision.
5. A proxy swap while an old write was pending could leave the queue stranded
   when that write later rejected. Remember a requested flush and run it after
   the old attempt settles; cover with a controllable rejected write.

No unrelated files should change; the user's existing `AGENTS.md` modification
is untouched.

### Round 1 correction result

- Added `registrationReady` to `SignallingState`, propagated it through
  `ChatPage`, and gated peer output/reconciliation on current-proxy registration.
  Inbound demux remains active while output waits.
- Destroyed-proxy registration/listing outcomes are ignored, preserving state
  across EOF/cleanup races. Listing revisions remain monotonic across ordinary
  reconnects, and pending-inbox omissions are counted once per revision.
- Peer output remembers a proxy swap during an active write and flushes again
  when that attempt settles.
- Added regressions for all five cases. The test mock now models `destroyed` and
  supports controlled asynchronous writes; one older manual-registration test
  explicitly marks its override ready.
- The focused suite passed with 17 tests after these corrections.

## Independent review round 2 and correction

The reviewer verified all five round 1 fixes and found one remaining concrete
reset bug: `countedListingRevisionRef` survived an identity reset although the
listing revision restarts at zero, so revision 1 of a new incarnation could be
skipped. Genuine identity/registration teardown now resets that marker. A new
regression proves two omissions still expire an early offer after an identity
reset. The focused suite then passed with 18 tests. Review stopped after round
2; no further review round was needed for this one-line correction.

# Outcome and remaining risks

- `web/site/src/api/ss/react.tsx` retains the current in-page subscriber and
  last confirmed listing across socket reconnects. A replacement socket
  re-registers that id as a roaming refresh; a fresh page still requests a fresh
  id, and definitive failure/identity change clears retained state. EOF from a
  destroyed proxy no longer masquerades as a definitive outcome.
- `web/site/src/api/ss/peersessions.tsx` keeps peer connections, tracks, data
  channels, negotiators, and call reset state alive across proxy swaps. Ordered
  per-peer output queues SDP/ICE until roaming registration succeeds, and input
  inboxes survive reader replacement. Actual identity changes, peer departure,
  and unmount retain their teardown behavior.
- `web/site/src/app/chat/page.tsx` passes registration readiness into the peer
  lifecycle. Because `me`, membership, sessions, and reset notifications remain
  stable, the selected conversation and phone/music media are not reset merely
  by WebSocket reconnection.
- `web/site/src/api/ss/peersessions.test.tsx` covers same-id reconnect, retained
  UI/listing state, queue ordering and failed-write recovery, registration/EOF
  races, omission evidence, early offers, and identity-reset behavior.
- No live two-browser audio/music reconnect was run. Validation is deterministic
  hook/stream coverage plus production build, not a subjective media playback
  test. Long outages in which the remote actually leaves or rebuilds still rely
  on the normal fresh membership listing and ICE-restart recovery; socket
  reconnection itself deliberately does not force a media renegotiation.
- The user's pre-existing `AGENTS.md` change was not modified by this task.
