# Execution log

## Audit findings before editing

- `docs/signalling-server.md` omits `ackSequenceNumber` from the c2s `ping`
  request shape. The field is required by both wire prototypes; browser
  requests set it to 0, and pongs use it for `sequenceNumber + 1`.
- The c2c section names payload slots but not their nested exact shapes. Pion
  confirms `sessionDesc {type,sdp}` and `rtcICECandidate {candidate,sdpMid,
sdpMLineIndex,usernameFragment}`; all three ping/pong fields are required.
  `iceRestartRequest` is an optional/true boolean on the wire.
- The registration/roaming text predates non-destructive browser reconnect. A
  replacement socket in the same page re-registers the same subscriber id;
  only the initial page registration is necessarily fresh. The browser also
  starts a new SS ping session per socket, so the document must not claim its
  in-flight ping session automatically survives.
- The headless-client paragraph says its conflict retry mirrors the browser;
  current Go code retries a configured-id conflict once with an empty id, but
  the browser does not use that policy.
- Browser reconnect: established-socket loss retries immediately; failed
  connection attempts retry at a fixed 2s. The same in-page id is re-registered,
  UI identity/listing and peer sessions are retained, and per-peer c2c output
  queues until registration readiness. Page reload remains a fresh incarnation.
- Go bot reconnect differs materially: `startBotClient` retries at configurable
  `reconnectInterval` (default 5s), each `HeadlessRTCClient.Run` closes all peer
  sessions on exit, and handlers survive for the next run. Configured ids are
  reused; an initially empty/auto-assigned id is requested afresh on each run.
- ICE recovery matches on browser and Go: arm only after connected/completed,
  3s disconnected grace, immediate eligible failed recovery, 2s exponential
  base, nominal 30s cap, ±20% jitter. Only the polite peer originates restart
  offers; the impolite peer sends `iceRestartRequest`. Recovery continues until
  healthy/closed; checking does not cancel it.
- Queueing is best-effort and in-memory, not a durable/exactly-once replay
  protocol. ICE restart needs viable candidates and signalling; an actual peer
  departure/reload is intentionally not hidden by reconnect.
- The independent E2E wire view does not model every newer field (for example
  `iceRestartRequest`), so the testing section should claim drift detection for
  covered fields, not every accidental wire change.

# Potential issues and follow-ups

These were not changed as part of the documentation task. They are follow-up
candidates, not claims that new regressions were introduced by the docs work.

- **Go-bot reconnect still disrupts media.** `HeadlessRTCClient.Run` closes all
  peer sessions when its socket ends, so a music/echo bot rebuild can interrupt
  calls even though the browser now preserves its side. If seamless bot roaming
  is required, the Go client needs a separate design and media-level tests.
- **Browser offline queues are best-effort and unbounded.** They provide no
  durable/exactly-once delivery, and have no explicit item/byte limit, expiry,
  or coalescing. A long outage could accumulate stale candidates/restart
  requests and produce a flush burst; messages already handed to a failed
  network stack remain outside the queue's delivery guarantee.
- **Fixed reconnect delays can synchronize retries.** Browser failed dials use
  a fixed 2s retry (and an established socket retries immediately), while bots
  use their configured fixed interval. There is no reconnect backoff/jitter
  comparable to ICE recovery, so a server restart could produce a retry herd.
- **Relay sender binding deserves a security review.** Code inspection of
  `SimpleOnMemorySSProvider.handleRelay` shows that it checks whether
  `c2c.FromSubscriber` is live, but does not compare that subscriber's
  registered address with the authenticated envelope `ev.From`. The WebSocket
  handler overwrites the envelope only; the c2c payload passes through. A
  focused authorization/spoofing test should determine and close this gap; no
  exploit reproduction was attempted during the docs audit.
- **Coverage still has blind spots.** The independent E2E wire view does not
  model every newer field, including `iceRestartRequest`, and no live
  two-browser phone/music reconnect test was run. A wire-level restart-relay
  case and a real media reconnect/soak test would complement the unit tests.
- **Some implementation comments still use stale browser comparisons.** For
  example, `pkg/rtc/client.go` describes configured-id conflict retry as
  mirroring the browser, although the current browser uses fresh initial ids
  and same-id roaming. The Markdown is corrected; code comments can be cleaned
  up with a future implementation-touching change.
