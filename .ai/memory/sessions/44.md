# Request

全面梳理 WebRTC 子系统中 Web 浏览器、bot 和其他 UA 之间的信令交换方式。
所有信令必须走 WebSocket；发现直接经 DataChannel 传输的信令时，应重构或
清除相关技术债务。调查、编码、测试与审核均在本任务内完成。

# Scope and status

Status: complete. 调查、跨端实现、文档、测试与多轮审核均完成。工作树原有
`AGENTS.md` 修改不属于本任务，保持不动。

范围包括服务端 WebSocket/PeerConnection/DataChannel 处理、浏览器客户端、Go bot、
其他 UA/无头客户端、共享 wire types、调用点、测试和文档。用户进一步明确“信令”
采用传统边界：SDP、ICE candidate、类 SIP 呼叫/音视频会话建立消息。DTMF 按
RFC 4733 走 RTP，不属于本任务；文件 chunk ACK 是文件业务的伴生流控，也不属于
本任务。普通聊天、文件元数据、FILE/FACK 和 DTMF 均保持原传输路径。用户进一步
确认 `chatControl.sip`（呼叫状态与 UI 同步）同样属于信令，必须走 WS；普通文本/
文件 chat-control 仍是业务协议。

# Plan

1. 全局检索信令类型、WebSocket 端点、PeerConnection 和 DataChannel API，画出
   浏览器 ↔ UA/bot、浏览器 ↔ 服务端及 UA ↔ UA 的实际交换路径。
2. 阅读实现和测试，逐项确认哪些消息是信令、哪些是媒体/业务数据；记录兼容约束、
   技术债务和直接经 DataChannel 传信令的完整清单。已确认 SDP、ICE、ICE restart
   全部走 WS；直接走 `dcmsg` 的呼叫信令为 `application/x-sip`（INVITE、200 OK、
   603 Decline、CANCEL、BYE）。`chatControl.sip` 只修订历史卡片 UI，不是对话状态机
   的成因，但与 INVITE 有顺序依赖，设计时必须避免跨 WS/DC 后 amend 先到而永久丢失。
   `/play`、`/call` 等文本是 bot CLI 业务命令，不等同于 wire call signalling。
3. 具体设计（已确认）：
   - 在 `ClientToClientEv` 新增 `call`，其 payload 保留现有呼叫 DCMsg 的必要信封
     （mimeVersion/channel/from/to/timestamp/msgId/inReplyTo/mimeType/plaintext）和
     `sip` / `chatControl.sip` body。这样不改变 callId、历史 amend target 等语义。
   - 浏览器 `usePeerSessions` 在 per-peer negotiator 之前分发 `call`，提供独立订阅和
     发送 API；发送复用该 peer 的 ordered WS output，与 SDP/ICE 共用 roaming 门控和
     重连队列。`useDataChannel` 继续拥有消息 store，但 call 帧只经该 WS API；写成功后
     本地落 `echo:true` 副本，接收端不 bounce。无 peer session 时像现状一样拒绝发送。
   - Go `HeadlessRTCClient` 新增 call handler/send API，在 negotiator 前路由；发送复用
     peer session 的 WS 输出。`msg_handler.Server` 注册 handler，INVITE/response/
     CANCEL/BYE 与 `chatControl.sip` 全走 WS；Reply、普通 Amend、文件业务仍走 DC。
   - 浏览器和 Go 的 dcmsg 接收端都丢弃旧式 SIP / `chatControl.sip`，不保留双路径或
     滚动兼容双写。新旧版本混用时呼叫不互通，需要同步部署。
   - bot 的文本 CLI 与 WS call handler 可能并发，按 peer 串行化 bot 的 chat/calling
     handler 调用，避免 music bot 既有 unsynchronized call state 产生数据竞争。
4. 实施跨端修改并更新协议文档；重点保留 Accept 先 attach track 再发 200、状态 amend
   target、主被叫本地/远端状态折叠及媒体重新协商行为。
5. 测试：新增浏览器 call 路由/本地副本/旧 DC 拒绝测试，Go client call 收发与寻址
   测试；把 echo/music/SIP bot 的呼叫 probe 改为 WS，同时断言呼叫帧不再出现在 DC。
   运行聚焦 Go/Web 测试，再运行 `go test ./pkg/... ./e2e/...`（按环境能力）、Go race
   聚焦测试、Web lint/test/build；审核最终 diff 和残留引用。
6. 将实际交换方式、设计修正、文件变更、验证命令与结果、剩余风险写回本记录。

# Execution log

## Investigation results

- 浏览器唯一生产 WS 为 `/api/ss/ws`；register/list/keepalive/ping 走 c2s，SDP、
  ICE candidate、ICE restart 走 c2c relay。Go bot/HeadlessRTCClient 通过
  `WebSocketSignallingTransport` 使用同一协议，bot 不是服务端 in-process 特例。
- 旧呼叫路径为 `dcmsg` 文本 JSON：`application/x-sip` INVITE/200/603/CANCEL/BYE，
  以及 `application/x-chat-control` 的 `chatControl.sip` 历史状态 amend。音乐 bot 和
  SIP bot 的主动/被动呼叫都经过它；echo bot 拒绝呼叫也经过它。
- 不迁移项：普通聊天和文本/文件 chat-control 走 `dcmsg`，文件元数据也走 `dcmsg`；
  FILE chunk 与 FACK 走 `dcbin`；DTMF 按 RFC 4733 走 RTP telephone-event；SIP bot
  对外真实 SIP/REGISTER/INVITE/BYE/MESSAGE 走 sipgo/diago 网络腿，WHEP 走自己的
  HTTP 协议。这些均不是本任务要求的 DC→WS 改造对象。
- 新旧客户端不做双读双写：旧端只认 dcmsg 呼叫，新端只认 `c2CEv.call`，混合版本
  呼叫不互通，需同步部署。旧式 DC 呼叫帧在新端被明确丢弃。

## Implementation and first review

- 已增加共享 `call` wire payload、浏览器 PeerSessions 独立 call demux/send/subscribe、
  Go client CallSignallingHandler/SendCallSignalling，以及 msg_handler 的 WS 收发。
- `ResponseWriter` 的 Reply/普通 Amend 每次查询当前 dcmsg；呼叫方法不再检查 DC。
  Accept 仍先 attach tracks，再发送 200。
- 首次聚焦测试发现 WS INVITE 可早于 dcmsg，导致依附 DC 的 now-playing 文本失败。
  修正为动态 DC 查询；需要该业务文本的测试显式等待 DC，呼叫本身不等待。
- 独立审核发现：(1) negotiator 关闭共享 sess.out 可能令 call send panic；(2) 有界
  call/output queue 与同步 handler 重入可死锁；(3) Server hub 等应用锁而持锁回调
  等 Server hub 可死锁；(4) 浏览器早到 INVITE 能振铃但不能答；(5) 预注册 call
  缺少最终身份复核。已分别改为 context 管理输出、主动 drain 的无界有序队列、
  Server hub 不等待 handler lock、按 channel/self/peer 暂存 call 到 session 建立，
  以及注册后地址复核/两次 omission 清理。
- 回归覆盖：32 个事件的阻塞 handler 同步应答、negotiator 返回后 call output、
  早到 INVITE 建 session 后应答、预注册不同 incarnation 丢弃、WS 本地 echo 和
  amend、旧 DC SIP/amend 丢弃、普通聊天/文本控制/文件状态仍走 DC、三类 bot 的
  dcmsg 零呼叫帧断言。

## Review corrections and final outcome

- 后续审核确认上述五项修复有效，但发现 SIP 来电在浏览器 200 后立即 BYE 会在
  外部 SIP pre-ACK 窗口得到 481。增加 `answerDone` 后，又继续把 `/hangup`、
  `/register`、`/unregister`、session-end 统一到 `endLocally`；session-end 在
  Server hub 外等待。
- 最后一轮审核发现 phase 检查与 end 非原子的竞态，最终下沉为 `peerCall.endLocal`：
  ringing/已完成 answer 在同一 mutex 临界区 `endLocked`，仅 active 且 answer 未完成
  时等待 `answerDone` 或 SIP dialog 结束，最后仍由 exactly-once `end()` 收口。
  最终独立复核确认无剩余阻塞性 correctness/deadlock 问题。
- 文档：`docs/signalling-transports.md` 是新的完整传输矩阵；`signalling-server.md`、
  `music-bot.md`、`sip-bot.md` 与相关源码注释已去除 dcmsg 呼叫旧描述。
- 主要实现文件：`pkg/models/ss/ss.go`、`web/site/src/api/ss/types.ts`、
  `peersessions.tsx`、`datachannel.tsx`、`pkg/rtc/client.go`、
  `pkg/rtc/msg_handler/`、`pkg/rtc/sipbot/{call,handler,inbound}.go`。
  测试包括新增 `datachannel.test.tsx`、`sipbot/call_test.go` 及 client/bot 套件更新。

## Remaining risks / deployment notes

- **必须同步部署浏览器、Go UA 和 bots。** 本任务明确不保留旧 dcmsg 呼叫双栈，
  新旧版本的聊天/文件可互通，但呼叫不能互通。
- 新 pump 和浏览器 pendingCalls 采用无界队列以避免 hub 重入死锁；永久停滞的
  transport/handler 或长期无 call subscriber 的活跃 session 可造成内存增长。
  这是已记录的背压权衡，不是当前 correctness 阻塞项。
- 未进行人工浏览器 UI 通话；覆盖来自真实 hook 测试、Go UA/真实 WebRTC/SS relay、
  bot 媒体测试、SIP fake PBX 和全仓 e2e。
