# Request

用户要求调研、评估并落实三项 WebRTC 信令优化：

1. WebSocket 建连并确认 `(userId, userSessionId)` 后立即写入 CAM，保留收到有效消息时的源地址学习；提高浏览器与 bot 到 SS 的 ping 频率。
2. 调查 hub 对 CAM 未命中消息当前是 drop 还是 flood；实现可配置的 `unknownMessageFlood: true/false`，开启时 flood。
3. 浏览器与 Go UA/bot 都可能在 flood 时收到无关消息，因此客户端需要尽早知道自己的 EPAddr，最好在注册/重注册/重连前知道；浏览器将 `(userId, userSessionId)` 持久化到 localStorage，适时从服务器刷新，服务器有效值始终覆盖旧本地值；客户端据此过滤不属于自己的 c2c 和 s2c 消息。

# Investigation

## 已确认的事实与初步线索

- 当前 `WebSocketSSHandler.forward` 对空目标或 CAM 未命中直接 return，因此是 **drop，不是 flood**；已知地址会发往该地址对应的全部连接。
- 当前 CAM 仅在 `noteMessage` 时通过被服务器覆写的 `ev.From` 学习；upgrade 时虽已从 session 取得身份，却只把它传给 `readPump`，没有立即 `learn`。
- CAM 是 `(userId,userSessionId) -> set[*wsConn]`，另有 `byConn` 反向索引；关闭连接和慢消费者会清理关联。
- 浏览器已有应用级 c2s ping：默认 1s，pong 超时 3s；Go transport 已有 WebSocket 协议 ping：默认 1s、pong 超时 3s。用户所谓“更加频繁”需要在调查中确定合理新默认值，避免无意义地再加速已经 1Hz 的路径。
- 浏览器 `/api/profile` 已返回 `subject_id` 和 `session_id`，注册前已经调用 `fetchProfile`，但当前只使用 username/subject 作为显示名，并未形成完整 EPAddr，也未持久化。
- 浏览器 `SSProxy` 当前只是 JSON framing/fan-out，不过滤目标地址；`useSignalling` 的请求回复按 `msgId/inReplyTo` 匹配，peer session 按 subscriber/channel 过滤。需要系统核查所有 c2c/s2c 消费点，避免 flood 下误收。
- Go transport 当前同样是 dumb pipe；`HeadlessRTCClient` 主要按 `inReplyTo`、subscriber/channel 处理。Go bot 使用静态 session JWT，需要找到可靠的 session identity 来源，不能伪造或本地生成与服务器 session 不一致的 ID。

# Plan

## 方案评估与决定

### 身份获取：选择 per-connection endpoint hello，而非 profile 预取

评估了两个可行方案：

- **profile 预取**：浏览器和 Go bot 每次 dial 前额外 GET `/api/profile`，再以返回身份过滤。优点是不改 wire protocol；缺点是多一次 HTTP RTT/失败点，Go bot 需要从 WS URL 推导 profile URL，而且 profile 与 upgrade 是两个请求，cookie/session 在两者之间变化时仍有 TOCTOU。localStorage 若用于 profile 失败时盲信旧身份，会把实际 B 会话连接上的 A flood 消息误当成本端消息。
- **endpoint hello（采用）**：SS 在 upgrade 后、任何其他下行帧之前，向该连接直接发送 `s2CEv.endpoint`，其中 `To` 和 payload 都是经 session 确认的完整 EPAddr。浏览器和 Go transport 都先消费并校验 hello，再开放注册和其他下行消息。它标识的是**这条确切连接**，无额外 HTTP 请求，也无 profile/upgrade TOCTOU；bot 每次 reconnect 自然刷新身份。

浏览器仍在 dial 前读取 localStorage 中的 pair，作为提前可用的非权威 hint；有效 hello 总是原子覆盖缓存。hello 之前不把普通 c2c/s2c 交给业务层，因此 stale cache 永远不能用来放行错误身份的消息。401 和显式 logout 清缓存。相比让缓存直接参与未验证过滤，这个约束是有意的安全取舍。

### flood 的安全边界

当前 unknown 是 drop。新增 `WebSocketSSHandler.UnknownMessageFlood bool` 和根 XML 属性 `unknownMessageFlood`，默认 **false**，保持兼容并避免默认跨会话泄露 SDP/ICE/call metadata 及 N 倍流量放大。开启时仅对完整 `(userId,userSessionId)` 且 CAM 未命中的 outbound event flood 到当前所有连接；known 仍单播，空/半空/service-only 地址仍 drop。flood 包括发送者及其他 tab，复用每连接 queue 和慢消费者清理，不做离线缓存。文档明确它是诊断/受信环境选项，不是可靠投递或隔离机制。

## 实施步骤

1. **Wire model**：TS/Go `SSToClientEv` 增加 `endpoint?: EPAddr`；定义首帧 hello 协议和校验规则。
2. **服务端 CAM/hello**：`wsConn` 保存不可变 `camKey`；upgrade 后先将 hello 放入连接 queue，再通过 `noteRegister` 让 hub 学习身份。注册 note 增加处理完成确认，保证 hello 发出前 CAM 已学习；保留 `noteMessage` 的源地址学习。`forward` 实现上述 flood matrix 和默认 drop。
3. **配置**：根 `serverConfig unknownMessageFlood="true|false"` 镜像到 `ServerConfigXML`、XSD、example 和 `cmd/server` 装配；默认 false。
4. **浏览器**：新增 identity storage helper（单 JSON key、校验完整 pair、storage 异常不致命）；`getSSProxy` 在 open 后等待有效 endpoint hello，再构造带不可变 `identity` 的 `SSProxy`。`SSProxy` 在 fan-out 前对 c2c/s2c 同时精确匹配 `to.userId` 和 `to.userSessionId`，缺失/半缺失/不匹配均丢弃。hello 有效值覆盖 localStorage。
5. **浏览器注册生命周期**：注册身份直接取 `proxy.identity`，不再等 register ack 才获得 userId；新 proxy 的 EPAddr 与保留注册不同则立即作废旧 registration/listing/peer state，并以空 subscriberId 开始新 incarnation；相同 pair 保留 roaming 行为。401/logout 清缓存并关闭 proxy。浏览器 c2s ping 从 1s 提至 500ms，pong timeout 保持 3s，避免弱网误判。
6. **Go UA/bot**：transport 在启动 write pump 和转发普通事件前读取/校验 endpoint hello；之后以 hello 的完整 pair 过滤 c2c/s2c，阻止 foreign 事件进入注册循环、日志和 peer queues。Go WS protocol ping 默认从 1s 提至 500ms，pong timeout 保持 3s；不另增一套应用 ping，也不把 WS ping 误当 channel keepalive。
7. **测试**：服务端首帧 hello、silent connection 的 eager CAM、known/unknown/flood 开关矩阵、地址边界、断连清理；TS identity/proxy 过滤、server override、身份切换；Go transport hello/filter/ping 和现有 reconnect；配置解析；更新 raw WS test helpers 以显式消费 hello，保留独立 wire view。
8. **文档/验证**：更新 signalling server/transports/reconnect 文档中的首帧、CAM、flood、过滤和 500ms timing。先跑 focused Go/TS 测试和 `-race`，再跑 `go test ./...`、前端完整 test/lint/build、XML schema 校验；记录实际结果和未覆盖风险。

## 第一轮综合 review 及计划修正

独立 reviewer 确认三个初版集成问题，均已修复并加回归：

1. eager CAM 使 Go 在 register ack 前收到 c2c 成为可能，原 `registerOnce` 会丢弃。`clientRun` 新增有序 `pendingC2C`，最终 subscriber 确定后、tickers/listing 前 replay；注册失败的 ticker-nil 清理也已覆盖。测试使用真实 SDP offer 验证 answer 产生。
2. 浏览器 A pre-registration early offer/call 可跨 `A→null→B` 残留。`usePeerSessions` 在 demux 前的 effect 跟踪上一非空 endpoint，pair 改变时即使 `me` 始终 null 也清理 pending input；same-pair 保留。
3. `closeSSProxy` 原会被 provider 当作网络断开并立即重连。现在断开通知区分 `reconnect`/`shutdown`，另有 in-flight shutdown 通知；logout/401 停止 retry 且不自动重连。

父任务另修正 Go filter 的跨端不一致：普通事件只比较 `(UserId,UserSessionId)`，与 CAM/浏览器一致，额外 `ServiceId` 不再导致误丢；已加通过用例。

文档已同步 hello、eager CAM、flood 风险与默认值、客户端过滤、Go 预注册 replay、身份缓存以及 500ms timing。

## 第二轮 review 及 early-c2c 补齐

复审确认上述三项修复有效，但发现浏览器还有同类的更早窗口：hello 完成后、React peer demux 调用 `getReadStream` 前，proxy 没有 subscriber，本端 c2c 会直接消失。已在 `SSProxy` 增加按到达顺序的 self-c2c backlog；普通 ping/注册 reader 不认领，首次 `getReadStream({replayEarlyC2C:true})` 的 peer demux 独占 replay 一次，之后恢复正常 fan-out，foreign 事件仍在入 backlog 前过滤。新增测试覆盖：无 reader 前、普通 reader 后各一条 early c2c 均按序 replay，后续 reader 不重复接收 backlog。Go pendingC2C 与浏览器 backlog 共同覆盖 eager CAM 引入的两个注册窗口。

第二轮 reviewer 同时确认 localStorage 仅作 hint、hello 为唯一权威满足安全目标：缓存不参与消息放行，因此 stale/篡改缓存不能造成跨身份接收。

针对 backlog 的窄复核又发现 StrictMode setup→cleanup→setup 会在首次 pending read 解析前 cancel reader，初版“创建 reader 即清空”会丢事件。最终实现改为 demux 每实际 `reader.read` 出一条就 `acknowledgeEarlyC2C` 一条；cancel 只释放 reader ownership，未确认 suffix 留给下一 setup replay。回归测试先 cancel 一个 demux reader，再验证下一 reader 收到全部 early 事件且后续无重复。至此停止 review 循环，以针对性测试和最终全量验证收尾。
