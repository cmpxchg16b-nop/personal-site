# Request

用户要求继续完成 WebRTC 子系统的信令与媒体换网/断网自动恢复，重点修复：通话中切换到另一 Wi‑Fi 后，Firefox `about:webrtc` 已出现生效且有数据传输的 ICE candidate pair，但 Web UI 一直显示 `disconnected`。同时要求记录 `iceconnectionstate`、`connectionstate` 的变化，并输出关联的 `PeerConnection` 对象及有助于排障的上下文。允许使用工具复现和调试。

复现路径：打开 `/chat`，选择 `music-bot`，发送 `/play trancepulsefm`；快速开关 Wi‑Fi 时希望信令、连接、媒体与音乐快速恢复；切换到另一 Wi‑Fi 时出现上述状态卡死。

# Scope and status

Status: superseded by session 50. 本轮已完成 Firefox 现场复现、状态诊断和 aggregate watchdog 修改；后续 ICE 凭据根因、Pion rollback 补丁及最终自动化验证见会话 50。工作树已有非本任务修改：`AGENTS.md` 已修改、`docs/subscriber-channel-epaddr.md` 未跟踪，保持不动。

# Investigation

待调查。初步区分两个可能层面：

1. 真实 `RTCPeerConnection` 状态未恢复，或 ICE restart 使用了错误的 peer/session/generation。
2. 新 PeerConnection 已恢复且有流量，但 UI 仍订阅旧对象、错过事件，或被旧对象的迟到 `disconnected` 事件覆盖。

以上均为待验证线索，不是结论。

# Plan

1. 阅读 `usePeerSessions`、Perfect Negotiation、ICE restart、通话状态和媒体播放代码及现有测试，画出对象身份与事件订阅生命周期。
2. 在当前部署实例复现 Wi‑Fi 快速开关和换网，收集浏览器控制台、`about:webrtc`、系统网络和服务端日志；若本机自动化无法安全切换目标 Wi‑Fi，明确记录盲区并用确定性测试补足。
3. 先添加可关联 PeerConnection 对象的结构化诊断日志，包括 peer/call/session/generation、本地与远端描述、ICE gathering/signaling 状态、收发媒体 track 和事件时间。
4. 根据复现证据做最小根因修复，确保状态只来自当前有效 PeerConnection，并能从迟到状态同步中恢复；避免削弱已有 ICE restart 与 glare/rollback 语义。
5. 增加能稳定复现“新对象恢复但 UI 卡 disconnected”的回归测试，运行前端完整 test/lint/type/build 及相关 Go 测试。
6. 按项目规则进行证据化代码复核，回写所有中间发现、失败复现、修正、验证结果和剩余风险。本轮未获明确发布指令，不自行提交、推送或重启生产服务。

# Execution log

- 开始前本地 `main...github/main`，除既有非本任务文件外无其他改动。
- Chrome 实际部署实例完成音乐通话基线与两次物理 Wi‑Fi 切换（网络名称不记录）。两次都是同一个 PC 对象完成 ICE restart，`connectionState` 和 `iceConnectionState` 约 10 秒内恢复 `connected`，音频 RTP 包继续增长，未复现卡死。
- Firefox 实际部署实例完成独立访客登录、`/play trancepulsefm`、接听和麦克风授权。切换到另一网络后 15 秒 UI 为 `Disconnected`，成功复现用户现象。
- Firefox `about:webrtc` 音频对象（临时对象标识不记录）：存在 `succeeded / nominated=true / selected=true` candidate pair；其接收字节从 1,939,245 增至 3,187,940，但 inbound RTP 始终 4,833 packets、0.0 KBps，outbound 始终 4,882 packets、0.0 KBps。证明“有 ICE pair/流量”不等于媒体恢复，不能只修 UI 文案。
- 当前浏览器恢复控制器只在 `iceConnectionState=connected/completed` 时取消 watchdog，完全不看 `connectionState`。UI 只由 `connectionstatechange` 更新，ICE 事件不会重读整体状态。
- 代码文档另有“polite Go glare rebuild 的新 ICE/DTLS 身份可杀死浏览器旧 pair”的已知限制；本次对象是否由该路径或 Firefox 原 PC 恢复能力造成仍需用新增日志验证，暂不把它当既定根因。
- W3C 2026 年 issue #3139 记录了 Chrome 与 Firefox 在 `connectionState=failed` 后原 PC 能否通过 ICE restart 恢复的实现差异；这支持先验证原对象恢复、必要时成对重建的分阶段策略，而不是假定所有浏览器一致。
- 隐私要求：本次修改的代码和文档不得包含实际隐私信息；已将会话记录中的真实网络名称和临时对象标识改为泛化描述。

## 第一轮实现计划修正

先保持原 PC：watchdog 以 ICE 与整体 connection 都健康为成功条件，整体 disconnected/failed 也能驱动恢复；ICE 事件重读并上报当前整体状态。`startPeerSession` 使用独立 event listeners 记录两类状态变化及 PC/peer/SDP/track/channel 上下文，不覆盖 PerfectNegotiator 的处理器。用真实 Firefox 换网验证；若原对象仍不能恢复，再设计带会话代次的成对重建，避免新旧 SDP/candidate 串线。
