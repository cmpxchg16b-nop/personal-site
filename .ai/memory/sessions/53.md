# Diagnostic design

- 新增浏览器 `diagnostics.ts`，统一 `[rtc self→peer]` 标签和结构化对象：`at/sessionId/channelId/self/peer/polite/event`，并附带 ICE、aggregate、signaling、gathering 状态。
- SDP 日志增加信令 `msgId`、apply/send 开始与结果、collision/makingOffer 等上下文。m-section 只保留 mid、DTLS setup 和 ICE/DTLS 摘要哈希；不输出完整 SDP、明文 ufrag/pwd、候选地址或原始 PC 对象。
- `IceRestartController` 增加只读事件回调，记录 watchdog scheduled、restart attempt、recovered、closed，包含 attempt、delay、usable/recovering 和两种连接状态，不改变既有定时与重试行为。
- 已在历史上健康过的 PC 再次不健康时，立即并每 5 秒采样 `getStats()`；采样只保留 selected/nominated pair 的状态、字节、RTT、候选类型，以及 inbound/outbound RTP 的包数、字节、丢包、jitter。异步采样串行化，关闭后忽略迟到结果。
- DataChannel attach/open/close/error 与 remote track 也归入同一 session 时间线。控制台可用 `[rtc]` 过滤，再按 sessionId、peer、msgId 或 restart attempt 缩小范围。
- 测试覆盖 SDP/地址脱敏、统计摘要、异步关闭、restart 事件和现有 PC 状态同步；不通过改变恢复逻辑来让测试变绿。

## 修改

- 新增 `web/site/src/api/ss/diagnostics.ts`：统一 `[rtc self→peer]` 结构化日志，包含时间、sessionId、peer、polite、ICE/aggregate/signaling/gathering 状态。
- SDP 按 m-section 输出 type、mid、setup、ICE ufrag/pwd 和 DTLS fingerprint 的稳定哈希；不输出原始 SDP、明文凭据、候选地址或完整 PC 对象。
- `negotiate.ts` 增加 negotiationneeded、local SDP 创建、offer/answer apply start/ok、发送、失败、忽略 glare、重传、restart request 和候选处理日志。SDP 日志带实际信令 `msgId`，answer 还带 `inReplyTo`。
- `ice_restart.ts` 增加只读诊断回调：watchdog scheduled、restart attempt、recovered、closed，包含次数、退避、usable/recovering 和连接状态；定时与重试行为未改。
- `peersessions.tsx` 增加 signalingstatechange、icegatheringstatechange、icecandidateerror、DataChannel、remote track 日志。曾经健康的 PC 再次异常时立即且每 5 秒采样 getStats，恢复后停止；异步采样串行化，关闭后忽略迟到结果。
- stats 只保留 nominated/selected candidate pair 的状态、字节、RTT、候选类型，以及 RTP 包数、字节、丢包和 jitter，不输出 IP、端口或 raw candidate。
- 新增 `diagnostics.test.ts`；扩充 `ice_restart.test.ts`、`negotiate.test.ts` 和 `peersessions.test.tsx`，覆盖脱敏、RTP/pair 摘要、关闭后的异步结果、watchdog 事件和实际信令 msgId 关联。

## 下次 Firefox 控制台采集

1. 部署这份埋点后，在 Firefox 打开 DevTools Console，启用持续保存日志；需要候选级事件时再打开 Verbose/Debug。
2. 用 `[rtc` 过滤，先按 music-bot 对应 peer，再按同一 `sessionId` 阅读。建立通话、播放音乐并实际换网，保留从首次 `watchdog:scheduled` 到后续 `stats` 的完整时间线。
3. 检查 `sdp:offer:apply:start` 是否有对应 `sdp:offer:apply:ok`，以及 `sdp:answer:sent` 的 `inReplyTo` 是否等于 offer 的 `msgId`。失败时看同事件名的 error 和 signalingState。
4. 对照 `restart:attempt` 的 attempts 与 offer/answer 序列，判断 restart 是否只是空转、是否发生重复 answer 或 glare。
5. 对照连续 `stats`：candidate pair 字节不增长说明候选路径仍未工作；pair 字节增长但 RTP 包数不增长说明 ICE 之后仍有媒体/传输问题；RTP 增长但 aggregate 不恢复则继续查状态事件和 UI 同步。
6. 比较 local/remote description 的 ICE 哈希，确认 rollback/restart 前后凭据变化是否发生在预期 SDP 上；哈希仅用于同一会话关联，不需要明文。
