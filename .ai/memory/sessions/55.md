- `17:13:56.793Z` 直接 `getStats()`：transport `iceState=connected`、`dtlsState=failed`；selected pair 为 succeeded/nominated/selected，pair `bytesReceived` 增长到 297575，但 `bytesSent/packetsSent` 均为 0；inbound RTP 固定在 4956 packets，outbound 固定在 4609，dcbin/dcmsg 均 closed，UI Disconnected。媒体与 SCTP 均未恢复。
- 多次 remote restart offer 均 apply ok 且 answer sent，local/remote ICE 哈希随 restart 更新，DTLS fingerprint 哈希保持不变、answer setup=active。服务端同时段 Pion 报 ICE recovered，但仍持续 offer，并有 stable 上重复 answer 错误；浏览器侧剩余卡死的直接原因是 DTLS failed，不是 SDP 未应用。
- W3C issue #3139 描述了相同 Chrome/Firefox 分歧，且后续数据同样观察到 aggregate failed 时 Firefox ICE 可 connected；其讨论没有给出应用层统一恢复实现。当前证据支持检查 DTLS failed 后的传输重建，不支持仅把 UI 改成 connected。

## 根因

直接 stats 证据是 `iceState=connected` 与 `dtlsState=failed` 并存。Firefox 能通过 ICE restart 得到新 selected pair，但 failed DTLS/SCTP 没有随 ICE 恢复，所以 aggregate 合法地保持 failed，RTP/DataChannel 仍停止。原 watchdog 持续工作，UI 也在如实报告 failed；仅改状态显示会掩盖媒体故障。

## 修改

- `web/site/src/api/ss/peersessions.tsx`：DTLS failed 时在逻辑 session 内换 PC，重绑 track/channel，不触发 reset；保留旧 sender 的 remove/resolve 能力，隔离旧事件和旧 channel open。
- `web/site/src/api/ss/negotiate.ts`：同一信令流内安全 adopt fresh PC，隔离旧异步回调，并忽略退役 DTLS fingerprint 的迟到 offer/answer。
- `pkg/rtc/negotiate.go`、`client.go`：只对新 remote DTLS fingerprint 成对换 PC，保留 session context、track/codec pin 和 call queues；application offer 的 channel 由 offerer 创建，旧 source callback 被丢弃。
- `web/site/src/components/chat/useCallMedia.ts`：DTMF 能力读取与按键发送解析到当前 sender。
- `diagnostics.ts` 增加 transport ICE/DTLS 摘要；`docs/webrtc-reconnect.md` 记录 failed DTLS 的恢复协议。相关 Go/Web 测试覆盖身份矩阵、旧 SDP、媒体/channel/session 连续性。
