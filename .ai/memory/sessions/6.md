# Session 6

## dn42 deployment: Caddy restructure (deployment/dn42/caddy.json)

- Two servers now: `http` on :80 (308-redirects nexus.dn42 and chat.dn42 to
  `https://{http.request.host}{http.request.uri}`) and a single `https`
  server on :443 with two routes — nexus.dn42 reverse-proxies to
  `[fdda:8ca4:1556:3000::8376:bf72]:18972`, chat.dn42 308-redirects to
  `https://nexus.dn42/chat`.
- LESSONS (validated by the user remotely via `podman exec dn42-personal-site
  caddy validate`): (1) two servers cannot share a listen address —
  "listener address repeated: tcp/:443" — so both hostnames live in ONE
  :443 server with host-matched routes; (2) the `automatic_https` http-app
  key was rejected as "unknown field" by their build — leave automatic
  HTTPS at defaults, don't spell it out.
- Cert automation for both names rides the existing global ACME policy
  (acme.burble.dn42, `/dn42-root-ca.crt`), unchanged.

## Chat: message model union + file-transfer status UI

- types.ts: ChatMessage is now a union — TextChatMessage (old shape +
  `type: "text-chat"`) | FileTransferStatusMessage
  (`type: "file-transfer-status"`, fileId (opaque global id, added in a
  follow-up), filename, fileMIMEType, fileSizeTotalBytes,
  fileSizeTransferred, status pending|running|done, timestamp).
  MessageGroup.messages narrowed to TextChatMessage[].
- MessageList: foldMessages yields ListItems — text runs still group;
  each file-transfer message is a standalone item that BREAKS a text run
  and participates in day dividers via its own timestamp.
- FileTransferStatusItem (new): card with file icon+filename (MIME on
  hover), status chip, determinate LinearProgress while running,
  transferred/total bytes. When done, the CARD ONLY (not the whole row —
  user correction) becomes a button: hover/focus fill, Enter/Space,
  localized aria-label, fires onRequestFile(fileId). onRequestFile is
  threaded MessageList←ConversationView←ChatApp←page (handler currently
  just alerts; real byte fetch is the future hook point).
- i18n: chat.fileTransfer.{pending,running,done,download}, chat.attach.

## Wire format: file-transfer + chat-control (api/ss/datachannel.tsx)

- DCMsg gained two MIME body kinds with optional body fields:
  `application/x-file-transfer-status` (fileTransfer: DCFileTransfer) and
  `application/x-chat-control` (chatControl: DCChatControl {subtype
  delete|amend, targetMessageId, text?, fileTransfer?}); plaintext stays
  required (empty for non-text). Builders newFileTransferDCMsg /
  newChatControlDCMsg; decodeDCMsg validates bodies
  (isWellFormedFileTransfer helper).
- The attach button (paperclip in MessageInput, `multiple`, input value
  cleared per pick) sends one real file-transfer DCMsg per file — the
  earlier local-only store is gone; both ends render via the echo flow.
  DEMO behavior kept: random status, status-aware progress (pending 0 /
  done full / running random), MIME from the File API, random UUID
  fileId.
- Chat-control APPLICATION LIVES IN THE DATA LAYER: applyDCMsg folds an
  inbound control into the store on arrival (delete drops, amend rewrites
  plaintext/fileTransfer keeping msgId+creationTimestamp; sender's own
  messages only; unknown target/kind mismatch = no-op); control messages
  are never stored. The intermediate ChatControlMessage UI type +
  applyChatControlMessage reducer were added, then REMOVED as dead once
  application moved to the wire layer.
- PROCESS LESSON: the user rejected applying control messages in the
  page's render useMemo ("absolutely unacceptable") — business logic does
  not belong in the rendering function; hooks/data layer own it.

## Magic commands (components/chat/magic.ts)

- parseMagicCommand + buildMagicControl; intercepted in handleSend, never
  sent as text, sent as real chat-control DCMsgs (echo applies them
  locally):
  - `/magic a90926e3-c768-45b7-ab93-4709c5f4aa91 <target_msg_id>` — delete
  - `/magic 1f734b69-9c46-4629-9e73-0aed96166f7c <target_msg_id>
    <content>` — amend text (content may contain spaces)
  - `/magic 7f8d9d4e-f41e-4e18-958e-ebc990690666 <target_msg_id> <status>
    <transferred> <total>` — amend file-transfer status
- Amendments copy the target's immutable fields (fileId/filename/MIME)
  from local history; unknown target or kind mismatch → no-op.
