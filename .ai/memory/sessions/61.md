# Request and scope

Extend the user-level SIP subsystem documented in
`docs/user-sip-subsystem.md` with outbound audio/video calls, complete ringing
behavior, and SIP MESSAGE. The SIP dial dialog must support audio-only versus
audio/video calls and let the user choose a caller SIP identity among currently
registered SIP accounts. This is system-level SIP integration, not a standalone
SIP bot. Selective reference to sip-bot is allowed, excluding its registration
and yellow-pages features.

# Status

Complete — user SIP outbound voice/video, parallel inbound ringing, pager-mode
MESSAGE, browser UI, media relay, documentation, automated validation, and live
Chrome/PBX checks are implemented. No deployment was made. After validation the
user requested staging, commit, and push; the resulting commit is recorded in
git history. The not-permitted temporary-directory deletion is the only cleanup
exception noted below.

# Investigation

Verified from the implementation and tests:

- `pkg/sipregistration` owns independent per-credential diago UAs and the AOR
  index, but `diagoRuntime` currently retains only REGISTER/UA handles. Matched
  INVITE and MESSAGE return 501; the runtime has no outbound dialog handle.
- `pkg/api/websocket_ss` learns every socket at upgrade and already has bounded,
  nonblocking per-connection queues. Its provider routing requires a complete
  `(user, session)` pair and its CAM table must remain hub-owned. A new explicit
  subject fan-out is required; `UnknownMessageFlood` and synthetic channel
  subscribers are not valid substitutes.
- Existing browser `application/x-sip` events are only the internal channel
  call protocol. `PhonePanel.submitNumber` is a placeholder, and peer media is
  keyed by `(channel, subscriber)`. External SIP therefore needs first-class
  service events and a separate call/message/media adapter.
- sip-bot has useful digest INVITE/MESSAGE, dialog lifetime, pre-ACK, RTP
  passthrough and test mechanics. Its account registration, yellow pages,
  `HeadlessRTCClient`, one-subscriber call map, presumed codec lists and fixed
  SDP policy are deliberately not reusable for this subsystem.
- diago's serve callback must remain blocked until the inbound dialog ends.
  `Answer` waits for ACK; a browser hangup can cross that pre-ACK window.
  Static SDP injection through `MediaSession.InitWithSDP` and
  `InitMediaSession` supports audio+video without forking the bot.

# Plan

1. **Wire model and hub.** Add service-directed SIP call/MESSAGE/SDP/ICE types
   to the existing SS envelopes. Add an external SIP handler to `websocket_ss`,
   hub-mediated subject fan-out with one opaque delivery ID per socket, targeted
   sends, and disconnect notification. Preserve the existing bounded queue and
   slow-consumer disconnect behavior. Test multiple sessions, duplicate tabs,
   isolation, backpressure, stale deliveries and full `To` stamping.
2. **Runtime and outbound operations.** Retain diago and its validated/pinned
   registrar destination in each runtime. Add generation-safe acquisition only
   for an owned, enabled credential with a live registration binding. Runtime
   replacement/disable/delete/close cancels that generation's calls before UA
   teardown. Implement digest outbound INVITE and pager-mode MESSAGE through
   the existing registrar, never auto-registering or borrowing an account.
3. **Call controller and MESSAGE delivery.** Implement explicit outbound states
   (`dialing`, `ringing`, `answering`, `accepted`, terminal states), inbound
   parallel ringing, first-answer-wins, per-tab decline, all-tab decline,
   caller CANCEL/BYE, ring timeout, disconnect and exactly-once cleanup. Bind
   inbound callbacks to the receiving credential/generation as well as To AOR.
   Deliver inbound text/plain MESSAGE only after at least one browser queue
   accepts it; correlate outbound MESSAGE sent/failed results. Initially keep
   CPIM out of scope and reject unsupported types explicitly.
4. **Real-capability SDP and media.** Parse actual browser and SIP SDP. Match
   codec name/clock/channels and relevant H.264/Opus fmtp; never insert a codec
   or telephone-event capability. Use dedicated Pion peer connections per
   accepted browser delivery and plaintext RTP/AVP on the SIP leg, with a
   payload-preserving audio/video relay and PT/transport conversion only.
   Outbound starts from the browser offer; inbound selects only after the
   winning browser's real offer arrives. Keep early media, DTMF, re-INVITE/hold,
   late-offer inbound, and SIP-side SRTP outside this milestone with explicit
   failure/response behavior. RTCP is left to the endpoint stacks for this
   milestone and must be documented as a limitation, not claimed translated.
5. **Browser integration.** Mirror the event types. Add an external SIP hook
   owning calls, MESSAGE history, peer connections, trickle ICE and media.
   Improve the existing dial dialog with target, registered caller identity and
   voice/video selection. Add usable outbound/inbound MESSAGE UI and call
   accept/reject/hangup/video presentation without fabricating DM identities.
   Reuse `AudioGraph`/`VideoWindow` where practical. Add focused reducer,
   filtering and mocked signalling/media tests.
6. **Validation and records.** Run focused Go race tests and frontend tests,
   then broader Go/lint/type/build checks. Add real UDP digest INVITE/MESSAGE
   and media tests where practical. Update `docs/user-sip-subsystem.md` with
   a control-plane + media-plane architecture diagram (all browser tabs/sessions,
   SS fan-out, call controller, registration runtime, PBX, and Pion/RTP relay),
   API/state behavior, exact implemented/remaining scope, decisions and
   validation. Finish this note with commands, outcomes, review corrections and
   blind spots.

## Plan corrections during implementation

- Browser offers use `UDP/TLS/RTP/SAVPF`; SDP parsing now distinguishes that
  WebRTC transport profile from the SIP side's deliberately narrower plaintext
  `RTP/AVP` profile. Codec matching remains identical and capability-driven.
- Stopping a diago runtime's serving context before de-REGISTER broke the
  shared UDP listener. `StopOperations` therefore cancels only the derived
  outbound-operation context; the listener stays until unregister completes.
- The user additionally requested an architecture diagram in the subsystem
  document; it is part of the documentation deliverable.

# Review round 1 and correction plan

The first end-to-end implementation and broad tests passed, but an independent
comprehensive review found concrete issues that must be fixed before completion:

- A dropped socket could be re-learned by a queued frame, leading to stale SIP
  actions and a possible send-on-closed-queue panic.
- Independent service workers could reorder dial/ICE/cancel/disconnect. Browser
  negotiation failures could remain local and leave the SIP dialog alive.
- Inbound invalid accepts could leave a tab in `answering`; pre-answer setup
  failures could become 480 rather than the requested response.
- Diago could lose mandatory ACK/BYE when cancellation raced final-2xx SDP
  handling, answer 481 to matched CANCEL, pre-reject case-varied valid codecs,
  and leak pre-dialog media sockets on early INVITE failures.
- ICE server configuration was lost after browser SS reconnect, caller identity
  eligibility changed spuriously during refresh, and generated SDP/relay ignored
  the offered media direction.

Correction plan: serialize work per browser delivery while keeping bounded
nonblocking hub ingestion; make all local browser failures notify the server;
model per-leg negotiation rejection and explicit SIP pre-/post-answer state;
fix hub removal invariants and real diago CANCEL/2xx handling; close untransferred
media; preserve codec semantics and direction; align frontend eligibility with
unexpired leases. Add regression tests for each reproduced issue, then rerun
race/full frontend/backend checks and conduct a second review round.

# Review round 2

The first-round fixes passed their focused tests and the full repository Go
suite, frontend 128-test suite, typecheck/lint/build. A second independent review
verified those fixes and found three remaining concrete issues:

- Ordinary client c2c frames could retain a forged SIP service identity and
  server-only SIP payloads. The hub must strip server payloads/service identity
  on all client-originated frames, not only dedicated c2s SIP commands.
- Cancelling while the browser was still creating its offer could emit CANCEL
  before dial, or let dial proceed after a purely local cancellation. The client
  must distinguish no-command-yet from dial-in-flight and close the local runtime
  in the former case.
- A UAS can send 200 before `Answer()` later returns an ACK error. Cleanup must
  use diago's `Established` state, not `Answer()`'s nil/error result, to choose
  post-200 BYE versus a pre-200 final response.

A nested diago regression also exposed an existing test's response-count
assumption after reliable BYE cleanup; its fixture/assertions must be corrected
without dropping the cancellation-safe test.

# Live Chrome + loopback PBX validation

Used an isolated Chrome context and a temporary UDP PBX with real
REGISTER/INVITE/MESSAGE sockets, not a browser mock:

- Added `1001` and `1002`; the dial dialog listed both. Selected `1002` for a
  voice call, observed In call, and PBX logs confirmed `INVITE from=1002`, ACK,
  and browser-initiated BYE. The PBX's custom raw-UAS fixture logged ACK and later
  emitted its own ACK-missed warning because it did not bind the raw ACK to a
  diago server dialog; the observed client ACK itself was present.
- The first audio+video attempt failed before INVITE with sipgo `size of packet
larger than MTU`. Corrected `newOutboundSIPMedia` to keep up to four actual
  primary audio and two actual primary video capabilities in browser preference
  order after helper-codec removal. Added a large Chrome-shaped regression; its
  generated SDP is 431 bytes. This is a deliberate bounded-offer interop choice,
  not codec injection.
- Retried audio+video: browser PC became `connectionState=connected`,
  `iceConnectionState=connected`, stable, with live audio/video receivers and an
  answer containing only PCMU + VP8. `getStats()` showed real inbound audio RTP
  (674560 bytes / 4216 packets at observation). PBX did not generate valid video
  frames, and mic/camera remained at permission `prompt`, so no claim is made for
  local capture or a decoded two-way video picture.
- Outbound MESSAGE showed Sent and PBX logged its text; PBX-originated MESSAGE
  returned SIP 200 and appeared as Received while the call UI remained usable.
- Opened a second Chrome tab with the same visitor/session. PBX inbound INVITE
  rang both; accepting tab 2 produced In call and PBX answered, while tab 1's
  incoming popup disappeared. Ended the call cleanly.
- Deleted test credentials, closed only the isolated test tabs, and stopped the
  temporary PBX/server. Deletion of `scratch_sip_e2e/` was not permitted by the
  user/tool permission prompt, so the temporary sources/binaries/logs remain
  there for inspection; this is explicitly not claimed as cleaned up.

The final targeted review also caught and fixed a pending-inbound-accept decline
regression: incoming deliveries must receive decline even when their browser
offer creation is still pending; only an unsent outgoing dial is purely local.

## Remaining limits / blind spots

- SIP media is plaintext RTP/AVP. SRTP, early-media forwarding, DTMF,
  re-INVITE/hold, late-offer inbound, CPIM/in-dialog MESSAGE, durable/offline
  MESSAGE history, and RTCP translation are intentionally not implemented.
- TCP/TLS/WS wire paths, NAT/STUN/TURN combinations, external PBXs, packet
  loss/reordering, and multi-replica routing remain untested or unsupported as
  documented. Live Chrome did not grant mic/camera and the temporary PBX did
  not send valid video frames, so full decoded two-way video remains unverified.
- Temporary `scratch_sip_e2e/` remains untracked because deletion was denied;
  test accounts/tabs/processes were cleaned up. It is deliberately excluded
  from the requested git commit.
