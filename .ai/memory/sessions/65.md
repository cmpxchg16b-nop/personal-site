## Request and scope

Fix review issue 7: a CANCEL matching a pending inbound INVITE must receive 200
and the INVITE transaction/dialog must terminate correctly; an unknown CANCEL
must retain 481. Allowed changes are `third_party/diago/diago.go`, diago tests,
`pkg/sipregistration/integration_test.go` or a new
`pkg/sipregistration/inbound_wire_test.go`, and a clearly separate entry in
`third_party/diago/PATCHES.md`. Do not edit runtime operations, service, media,
or frontend code.

Required validation includes focused tests and `go test -race ./pkg/sipregistration`.
Add a real UDP wire regression that sends INVITE, observes 180, sends matched
CANCEL, and verifies 200 to CANCEL plus INVITE termination; include unknown
CANCEL 481 if practical.

## Verified findings

- `third_party/diago/diago.go` registers `server.OnCancel` with an unconditional
  481 response, but that alone does not establish which requests reach it.
- Both selected dependency versions were inspected: the root build uses sipgo
  v1.6.0 and the nested diago module uses v1.4.3.
- In both versions, `sip/transaction_layer.go:handleRequest` handles CANCEL
  before normal server routing. It constructs the INVITE transaction key and,
  when a server transaction exists, directly writes 200 to CANCEL, passes the
  CANCEL to the INVITE transaction, and returns without invoking diago's
  `server.OnCancel` handler. Only an unmatched CANCEL falls through to a new
  server transaction and that handler.
- Both versions' `sip/transaction_server_tx_fsm.go:actCancel` construct a 487
  Request Terminated response for the INVITE and run the registered cancel
  callback.
- Both versions' `dialog_ua.go:ReadInvite` register `tx.OnCancel` and
  `tx.OnTerminate`; before establishment these end the dialog context. Thus the
  original INVITE termination and diago handler wakeup are already owned by
  sipgo's transaction/dialog machinery.
- The user runtime reaches 180 through its real `Service` inbound path when a
  bridge has an active delivery. Existing test helpers provide a registrar,
  active-delivery fake bridge, and valid SIP SDP without modifying service code.
- The working tree has extensive pre-existing changes, including
  `integration_test.go`; use a new `inbound_wire_test.go` to avoid conflicts.

   Start the actual manager/runtime/service path, register a credential, and send

   transaction and assert 481. Keep UDP deadlines and cleanup bounded.
2. Run the new regression against the unmodified response path. If it exposes a

   behavior above. If it passes, do not add a redundant dialog-cache response or
   a second 200/487; instead clarify the diago handler's unmatched-only scope and
   add focused vendored documentation/tests as warranted.
3. Add a clearly separate PATCHES.md entry describing the actual vendored change
   (if any) and the transaction-layer ownership established by the regression.
4. Run focused tests, the nested diago tests relevant to the change, and

## Execution log

- Added `pkg/sipregistration/inbound_wire_test.go` with raw UDP messages and the
  real manager/runtime/service path. The unknown CANCEL uses a distinct Via
  branch because sipgo's RFC 3261 transaction key is based on branch, sent-by,
  and method rather than Call-ID.
- Baseline result before any diago edit: `go test ./pkg/sipregistration -run
'^TestDiagoRuntimeInboundCancelOverUDP$' -count=1 -v` passed. The wire exchange
  produced 180, then 200 to matched CANCEL and 487 to INVITE, delivered the
  service's cancelled event, and produced 481 to unknown CANCEL. This directly
  disproves the review's claim for the selected sipgo versions.
- Plan correction: no functional diago change is justified. Added a precise
  unmatched-only contract comment in `diago.go` and a separate, explicitly
  comment-only PATCHES.md addendum. Avoiding a dialog-cache 200 prevents
  duplicate responses and preserves unknown-CANCEL 481.
