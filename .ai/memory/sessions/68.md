title: Fix inbound call panic in SDP codec parsing
date: 2026-11-24
---

## Request and scope

Answering an inbound audio/video call panics with `index out of range [10] with length 10` in `third_party/diago/media.CodecsFromSDPRead` (`codec.go:233`), reached through `MediaSession.RemoteSDP` and `pkg/sipregistration.newInboundSIPMedia`. Investigate the actual parser and inbound call path, reproduce the failure, fix the root cause, add focused regression coverage, and validate the SIP packages and server build.

## Status

Root cause confirmed from the real FreeSWITCH INVITE. Adding the failing regression test before changing production code.

## Verified findings

- The supplied panic occurs after a successful `GET /api/sip/credentials`, while constructing inbound SIP media during `runInboundAccept`.
- `MediaSession.RemoteSDP` allocates `codecs` with `len(md.Formats)`, then passes every session/media `a=` line to `CodecsFromSDPRead`.
- `CodecsFromSDPRead` appends once for every matching `rtpmap`, not once per payload format. It has no `break` after a successful mapping, so reused payload numbers produce more writes than the allocated format count.
- The real offer has 10 audio formats and exactly 40 attributes, matching both stack arguments. Audio PT 96/97/98 map to opus/speex/speex while video PT 96/97/98 map to AV1/H265/H264. Each is scanned twice. Before audio PT 99, the parser has therefore written 10 entries; audio PT 99 (telephone-event/16000) collides with video PT 99 (VP8/90000), and its first write uses index 10. This reproduces the reported `index out of range [10] with length 10` exactly.
- Payload types are scoped to each media description, so this FreeSWITCH offer is valid; the caller-owned slice length is correct.
- Current upstream diago `CodecsFromSDPRead` uses a `found` result and breaks after the first valid `rtpmap`, confirming the one-codec-per-format invariant. The vendored v0.32.2-derived parser lacks that guard.

## Plan

1. Add the real audio/video SDP as a focused `MediaSession.RemoteSDP` regression and run it before the fix to observe the same panic.
2. Backport the minimal parser control-flow fix: stop scanning attributes after the first valid mapping for each format, preserving the first (audio-section) mapping in this offer and the caller's existing output-size contract. Do not add SDP logging now that the exact input is available.
3. Add/execute inbound-media coverage proving the real offer negotiates Opus audio plus VP8 video and reaches answer construction without a panic.
4. Run focused tests, the full vendored media and `pkg/sipregistration` suites, race checks where appropriate, server build, and diff checks. Update `third_party/diago/PATCHES.md` with this local backport.
5. Record exact outcomes and whether a rebuilt-backend live call remains necessary.

## Reproduction and intermediate corrections

- Added `TestRemoteSDPAudioVideoPayloadTypeCollision` with the supplied FreeSWITCH SDP. Before the production fix, `go test -count=1 -run '^TestRemoteSDPAudioVideoPayloadTypeCollision$' ./media` (from `third_party/diago`) panicked at `codec.go:233` with `index out of range [10] with length 10`.
- The first fixture omitted the final SDP newline, so diago's line reader dropped the final attribute and the stack showed 39 attributes. Adding the real terminating newline made the pre-fix stack exactly match production: 10 formats, 40 attributes, and a 10-entry output slice.
- After adding the one-`break` parser fix, the same focused media test passed.
- The first inbound-media test fixture used browser Opus without `useinbandfec=1;stereo=1`, so negotiation correctly returned `no common audio` before reaching the parser. The live call had already passed selection; the fixture was corrected to advertise those capabilities. No production negotiation behavior was changed.

## Outcome

Code fix and regression coverage are complete. Live rebuilt-backend verification is still pending.

Production change:

- `third_party/diago/media/codec.go`: after one valid `rtpmap` is emitted for a payload format, stop scanning its attributes. This caps parsed codecs at the number of formats supplied by `MediaSession`, prevents audio/video payload-number collisions from overflowing the output, and preserves the audio-first mapping in the reported offer. No logging probe was needed after the real INVITE became available.
- `third_party/diago/PATCHES.md`: documents Patch 7 and its upstream-consistent invariant.

Regression coverage:

- `third_party/diago/media/media_session_test.go`: the exact 10-format/40-attribute FreeSWITCH offer reproduces the panic before the fix and negotiates Opus, PCMU, PCMA, and G722 afterward.
- `pkg/sipregistration/media_test.go`: the real collision layout traverses inbound browser/SIP selection, `newInboundSIPMedia`, and answer generation, selecting Opus/96 audio and VP8/99 video.

Validation actually run:

- Focused vendored test before fix: failed with the exact reported panic; after fix: passed.
- `go test -count=1 -run '^TestNewInboundSIPMediaAudioVideoPayloadTypeCollision$' ./pkg/sipregistration`: passed after the test-fixture correction above.
- `go test -count=1 ./media` from `third_party/diago`: passed (`7.997s`).
- `go test -count=1 ./pkg/sipregistration`: passed (`6.632s`).
- `go test -race -count=1 ./media` from `third_party/diago`: passed (`9.168s`).
- `go test -race -count=1 ./pkg/sipregistration`: passed (`7.672s`).
- `go build ./cmd/server`: passed.
- `git --no-pager diff --check`: passed.

The pre-existing `web/site/next.config.ts` modification was not touched. No frontend checks were needed for these Go/SDP-only changes.

Remaining verification and blind spots:

- The backend was not restarted and no new live call was placed. Restart/rebuild with this change, re-register if required by the in-memory credential store, and repeat the same FreeSWITCH audio/video call for final runtime confirmation.
- This deliberately minimal backport follows current upstream's first-valid-mapping behavior and is proven on the reported audio-before-video offer. Diago still flattens session/media attributes; fully scoping attributes for an unusual video-before-audio offer would be separate parser hardening, not required to resolve this reproduced crash.
