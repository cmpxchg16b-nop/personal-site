# Session 69

## Request and scope

The existing WebRTC Chat / `pkg/rtc/sipbot` path supports DTMF, but the newer
user SIP subsystem and its second (`phone`) tab do not provide a working IVR
keypad for calls such as `5000`.

Required outcome:

1. Add backend DTMF support to the user SIP subsystem, using the proven
   `sip-bot` implementation as the reference.
2. Restore the phone UI's DTMF keypad by following the existing WebRTC Chat
   interaction and preserving/reusing existing frontend code where practical.
3. Validate the complete WebRTC-phone to SIP IVR path with focused and broader
   checks, and document any remaining blind spots.

## Verified findings

- The legacy path is fully implemented: `pkg/rtc/sipbot/dtmf.go` parses and
  deduplicates RFC 4733 events, `call.go` forwards fresh digits through diago's
  DTMF writer, and `web/site/src/components/chat/DialPad.tsx` plus
  `useCallMedia.ts` provide the existing keypad and negotiated-capability check.
- The new path is missing the feature at every layer:
  `pkg/sipregistration/sdp.go` classifies `telephone-event` as a helper and
  discards it; `media.go` registers/forwards only one primary audio codec;
  `ExternalSIPConversationView.tsx` never passes the existing `dialPad` control
  to `ConversationView`; and `api/ss/sip.ts` exposes no DTMF dialer.
- The new subsystem intentionally relays encoded RTP payloads and translates
  dynamic PTs. sip-bot's fixed-PT-101 diago writer must therefore not be copied
  literally: it would lose the new gateway's per-leg PT mapping. Pion's
  `TrackLocalStaticRTP.WriteRTP` also rewrites a packet's PT to the track's
  primary codec, so SIP-to-browser telephone-event cannot be sent through the
  existing audio track without additional track/interceptor work.
- Browser-to-SIP forwarding can preserve the browser's original RFC 4733
  start/update/END series through the existing `relayRTPWriter`. This is the
  architectural equivalent of sip-bot's WebRTC-to-SIP direction, without
  decoding/re-encoding events or accidentally treating END retransmissions as
  new presses. The IVR consumes the standard redundant END packets.
- Pre-existing user work: `web/site/next.config.ts` is modified and must remain
  untouched.

## Plan

1. Extend the SDP model with separate telephone-event capabilities. Include an
   actually offered browser capability in outbound SIP SDP, answer an inbound
   SIP capability only when both sides share it, and retain each leg's dynamic
   PT/fmtp in `negotiatedSelection`.
2. Register a negotiated telephone-event codec on the Pion answerer and the SIP
   media session. In the browser audio pump, dispatch DTMF packets separately
   from primary audio and relay their complete RFC 4733 payloads with the SIP
   leg's negotiated PT. Do not forward SIP-to-browser DTMF in this milestone.
3. Reuse the old frontend rather than creating another keypad: extract the
   existing live-sender DTMF predicate/inserter into a shared helper, expose
   `dtmfFor(callId)` from `ExternalSIPClient`/`useExternalSIP`, pass the current
   external call's dialer through `ChatApp` and
   `ExternalSIPConversationView`, and render the same `DialPad` and composer
   toggle used by WebRTC Chat.
4. Add focused coverage for SDP offer/answer negotiation (including capability
   absence and dynamic PTs), browser answer SDP, real WebRTC-track-to-SIP-UDP
   RFC 4733 forwarding with audio before/after it, and frontend sender
   capability/live-gate behavior. Use a test interceptor for DTMF injection
   because Pion's track API otherwise rewrites its PT to the primary codec.
5. Update `docs/user-sip-subsystem.md` to remove DTMF from exclusions and record
   the exact direction/transport behavior. Run focused Go and Vitest checks,
   full `pkg/sipregistration` tests (including race), the frontend suite,
   type/lint/build checks where available, server build, and diff checks.
6. Finish this note with exact commands/results and explicitly distinguish
   automated RTP-level proof from any unavailable live `5000` IVR test.

## Implementation findings and corrections

- The frontend now shares `api/dtmf.ts` between legacy and external calls and
  reuses the existing global `DialPad`. Its focused suite passed 26/26 tests;
  the delegated full frontend run passed 149/149 tests, TypeScript, and focused
  ESLint before backend work completed.
- The first backend test run failed only where old assertions required
  telephone-event removal. Those tests now describe explicit DTMF negotiation
  and absence instead.
- A real Pion answer test then proved that `MediaEngine.RegisterCodec` alone is
  insufficient: `AddTrack` narrowed the transceiver to the primary codec. The
  production answerer now pins primary-audio + telephone-event codec
  preferences, mirroring sip-bot's old `AttachMediaWithCodecPreferences` path.
- The Pion probe's default codecs also lack telephone-event, so the test helper
  explicitly registers the selected DTMF codec, just as sip-bot's probe does.
- The first RTP injection timed out because its test sequence numbers moved
  backwards (audio 1000, then DTMF 200) and were discarded before the relay.
  Correcting them to 1001+ made the real WebRTC-track-to-SIP-UDP test pass; no
  production change was made for that test-fixture bug.
- The RTP regression verifies browser PT 101 -> SIP PT 120, exact payloads and
  markers, one start/update plus all three standard END retransmissions, and
  audio before/after. Full `go test -count=1 ./pkg/sipregistration` and
  `go test -race -count=1 ./pkg/sipregistration` passed.

## Review findings and corrections

1. Review found that an optional DTMF/video PT collision could reject an
   otherwise valid video call on the shared SIP socket. Outbound offers now omit
   only the conflicting DTMF capability, and pinned inbound/outbound selections
   clear conflicting DTMF before either answer. Regression tests cover both
   directions and preserve selected video.
2. Review also confirmed diago learned its RTCP sender-report clock from the
   first packet on an SSRC. A DTMF-first Opus call could therefore retain 8 kHz.
   The relay now primes the primary-audio clock through vendored
   `RTPSession.PrimeWriteStats`; the nested regression verifies a DTMF-first /
   Opus-second sender report at 48 kHz.
3. Follow-up review caught that priming a nonzero SSRC could emit a pre-media
   zero-packet report. The first `PacketsCount == 0` guard was too broad: the
   existing `TestRTPSessionFork` intentionally seeds statistics with zero
   packets. The final implementation uses a private `primed` bit, suppresses
   only reports before the first primed-relay packet, and clears it on the first
   RTP write. Prime/no-RTP, DTMF-first, ten repeated Fork race runs, and the full
   nested media race suite all pass.

## Outcome

Implementation and automated validation are complete.

Backend:

- `pkg/sipregistration/sdp.go`: parses telephone-event separately from primary
  codecs, negotiates it only when shared, retains per-leg PT/fmtp, emits it only
  when explicitly supplied, and drops optional DTMF on selected-video PT
  conflicts.
- `pkg/sipregistration/media.go`: includes actual DTMF in outbound offers and
  shared inbound answers, registers and pins Pion's primary+DTMF transceiver,
  ensures diago knows the negotiated DTMF codec, relays the complete browser
  RFC 4733 series with dynamic PT translation, and primes primary-audio RTCP.
  SIP-to-browser DTMF remains deliberately unmatched/dropped.
- `third_party/diago/media/rtp_session.go` and `PATCHES.md`: explicit pre-media
  primary clock/SSRC initialization with no pre-first-packet RTCP report.
- `pkg/sipregistration/{sdp,media}_test.go` and nested `rtp_session_test.go`:
  SDP presence/absence and dynamic PTs, inbound/outbound answers, collision
  fallback, real WebRTC-track-to-SIP-UDP DTMF with audio before/after, and
  DTMF-first/no-RTP RTCP behavior.

Frontend:

- `web/site/src/api/dtmf.ts`: the legacy two-phase negotiated-capability and
  press-time live-sender gate, shared with `useCallMedia.ts` and external SIP.
- `web/site/src/api/ss/sip.ts`: accepted-live-call `dtmfFor(callId)`, exposed via
  `useExternalSIP`; remote-description publication makes answered codecs visible.
- `ChatApp.tsx` / `ExternalSIPConversationView.tsx`: the visible external
  conversation uses the existing composer toggle and global `DialPad`; no second
  keypad was created.
- `web/site/src/api/ss/sip.test.ts`: missing capability, negotiated capability,
  accepted-call gating, insertion, live `canInsertDTMF`, cleanup, and stale
  handle coverage.
- `docs/user-sip-subsystem.md`: current DTMF behavior, exclusions, implementation
  map, and validation limits.
