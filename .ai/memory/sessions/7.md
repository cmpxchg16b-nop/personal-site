# Session 7

## Binary file transfer: useBinaryDataChannel + dcbin channel

- New wire format module `web/site/src/api/ss/binaryframes.ts` (pure, no
  React — mirrors proxy.ts/negotiate.ts layering): the BinaryFrame codec.
  All integers big-endian (DataView default). Two frame kinds, 4-byte
  ASCII `frame_type`:
  - `FILE` (sender → receiver): 48-byte header — frame_type(4) +
    file_id(16, packed UUID) + seq(4, uint32, per-file_id from 0) +
    offset(8, uint64) + total(8, uint64) + payload_size(8, uint64, must
    equal the remaining frame length) — then the payload. file_id is the
    stream id, so files multiplex over one binary channel.
  - `FACK` (receiver → sender ack, 32 bytes, no payload): frame_type +
    file_id + ack_seq(4, cumulative next-expected seq) + acked_bytes(8,
    cumulative contiguous bytes).
- decodeBinaryFrame accepts ArrayBuffer ONLY (dc.binaryType is
  arraybuffer), mirroring decodeDCMsg's string-only rule — and that makes
  payloads `Uint8Array<ArrayBuffer>`, which feeds `new Blob(chunks)`
  without casts under TS's generic TypedArrays (an early
  `Uint8Array<ArrayBufferLike>` BlobPart error forced this; it turned
  into a cleaner API).
- Bigint LITERALS are banned by tsconfig (`target: ES2017` < ES2020);
  use `BigInt(x)` everywhere.
- uuidToBytes/bytesToUuid pack/unpack the 16-byte file_id; canonical
  lowercase dashed form is the registry key on both ends.

## One peer connection, two data channels (datachannel.tsx)

- Per user: reuse the same RTCPeerConnection, with a dedicated `dcbin`
  channel for file bytes. startPeerSession wires both channels (polite
  peer creates both; impolite's ondatachannel dispatches by label).
  NOTE the design driver: a second peer CONNECTION per pair would
  cross-wire PerfectNegotiator — both negotiators filter c2c by
  (channelId, from, to) only, so each would apply the other's SDP
  offers. Two channels on one connection sidesteps any c2c protocol
  change.
- useDataChannel now also returns `binaryTransport: BinaryTransport`
  (stable identity): `whenOpenChannel(channelId, peer)` (resolves the
  open channel, or null when the session goes away first; a
  never-appearing peer leaves it pending until teardown),
  `subscribeFrames(cb)` (inbound binary frames), `subscribeReset(cb)`
  (per-session and all-sessions teardown). Session close + the
  proxy/identity teardown release every parked waiter with null.
- binarydatachannel.tsx holds `useBinaryDataChannel(transport)` →
  `{ sendFile, getFileByFileId }`. Transport vs semantics split:
  datachannel.tsx moves bytes, binarydatachannel.tsx owns frame
  semantics.

## Transfer engine (binarydatachannel.tsx)

- sendFile(channelId, to, fileId, file) →
  ReadableStreamDefaultReader<DCFileTransfer> (reuses the datachannel
  status type so events feed chat-control amends directly). Emits
  pending immediately, running as FACKs advance (throttled to one per
  250ms — each event becomes a dcmsg amend), done when ack_seq covers
  every sent frame; then closes. Failures (channel close / session drop
  mid-transfer) reject the pending read. reader.cancel() stops the pump
  quietly.
- Sliding window: 64 unacked frames × 16 KiB chunks = 1 MiB max in
  flight — the window IS the flow control (no bufferedAmount polling).
  The pump's wakeup is a single `wake` resolver replaced per wait;
  correctness argument: every await point (file.slice().arrayBuffer())
  is followed by a re-check before the next wait, and the section from
  done-check to wake-assignment is synchronous, so no ack is lost.
- Empty file = one FILE frame with empty payload (receiver: received 0
  === total 0 completes it) — both sides handle 0/0 naturally.
- Receiver reassembles by strict concatenation (SCTP is ordered +
  reliable): first frame must be seq 0/offset 0 with total ≤
  MAX_SAFE_INTEGER; a gap/overlap/mismatched-total drops the whole
  transfer with a warn. Every accepted frame is FACKed. Completed files
  land in an in-memory registry keyed by fileId (received Blob; the
  sender registers its original File under the same id, so both cards
  download). getFileByFileId is imperative + non-reactive by design;
  the registry grows unboundedly (demo-acceptable, documented).
- Session resets drop partial inbound transfers per peer; completed
  files survive.

## Chat page wiring (app/chat/page.tsx)

- handleAttachFile is REAL now (the random-status demo is gone):
  announce pending via newFileTransferDCMsg (capture its msgId), then
  pump the sendFile reader — EVERY yielded status goes out as a
  chat-control amend of the announce (per user: update the UI on every
  event, in-flight, not just at the last ack); the receiver's echo
  applies each amend to the sender's own history, so both UIs render
  ack-truthful progress.
- handleRequestFile is REAL: getFileByFileId → object-URL download
  named from the status message in history (binary channel carries no
  filename); falls back to alert when bytes lag the done status (status
  rides dcmsg, bytes dcbin — cross-channel ordering is not guaranteed).
- Addressing reminder: ChatUser.id IS the subscriber id for members
  (listChannel: "the subscriber id doubles as the chat user id"), so
  ref.userId addresses the peer everywhere (sendTo, sendFile).

## Explicit transfer kind (follow-up, same day — USER CORRECTION)

- The user REJECTED deriving the render kind from fileMIMEType: "don't
  guess the media type of file attachment, don't be self-smart" — an
  Attachment pick must always transfer and render as a plain file, even
  for a PNG. Presentation semantics must be EXPLICIT ON THE WIRE, never
  inferred from content metadata.
- DCFileTransfer (the dcmsg wire body) gained `kind: "file" | "image" |
"video"` (DCFileTransferKind, validated in isWellFormedFileTransfer).
  useChatMessages maps kind → UI message type (file-transfer-status /
  image-chat / video-chat); magic.ts's amend does the exact inverse
  (UI type → wire kind — a bijection, no MIME involved) and now targets
  all three transfer types; UI message types carry no kind themselves.
- kind threads: MessageInput's per-input pickFiles(kind) →
  onAttachFile(files, kind) (ConversationView/ChatApp thread it) →
  page's handleAttachFile announces with it → sendFile(..., kind) so
  every status the reader yields (and thus every chat-control amend)
  carries it. types.ts re-exports the wire union as TransferKind so UI
  components stay free of api imports.
- Validation unchanged: tsc + lint --quiet clean.
