# Session 70

## Request and scope

The restored external SIP dial pad renders but pressing keys has no observable
effect. The previous Pion/UDP regression was not a real browser keypad / live
IVR validation. Reproduce through the actual UI, inspect frontend/backend logs,
find the broken stage in `DialPad.onDigit -> RTCDTMFSender -> Pion -> SIP RTP`,
fix the root cause, and validate with concrete runtime evidence rather than
another mock-only claim.

## Runtime evidence

- Real Chrome call to local FreeSWITCH `5000` negotiated Opus/111 and
  `telephone-event/48000` on PT 110. At accepted/connected time the real audio
  sender had `dtmf != null`, `canInsertDTMF=true`, and codecs
  `[audio/opus, audio/telephone-event]`.
- Clicking the real pad's 1, 2, and 3 buttons called `insertDTMF` with those
  digits and did not throw. This rules out a swallowed `DialPad.onDigit` and the
  frontend live-capability gate as the cause of the reported no-op.
- FreeSWITCH answered with the same PT 110 / 48000 capability and entered
  `ivr(demo_ivr)`, but after its input wait logged `digits ''`. Container
  tcpdump on the negotiated PBX RTP port captured no PT 110 event packets.
- A real Pion-to-SIP-UDP regression changed to the exact PT 110 / 48000 values
  still passed, so a simple Pion payload-type/clock-rate registration check does
  not reproduce the live Chrome failure.
- The running Go process later exited and the API began returning 500. It has no
  usable DWARF for Delve attachment. Backend packet logging plus a restart is
  required for further evidence.

## Design lead and plan

`relayRTPWriter` currently applies a single `previous` timestamp/delta sequence
to primary audio and DTMF. That assumes their RTP timestamp clocks and timeline
can be mixed directly. The user's clock-rate warning is material: the RTCP clock
priming in session 69 did not make this data-plane assumption safe. Do not decide
the conversion from the mocked test alone.

1. Add temporary backend logs at `browserToSIP` for actual PT, sequence,
   timestamp, previous audio timestamp, DTMF pair, and read/write errors.
2. Restart the backend with logs, recreate the local test registration if needed,
   and compare Chrome's real audio/event packets with SIP output and FreeSWITCH.
3. Fix the proven root cause. Explicitly account for distinct audio/DTMF clock
   rates and each event's constant start timestamp/duration semantics; do not
   simply preserve deltas blindly.
4. Add real-value regression coverage (including differing rates), rerun backend
   and frontend checks, and obtain live FreeSWITCH digit evidence before calling
   the fix complete. Remove or appropriately retain diagnostic logging.

## 根因与原理（本次排查必须保留的结论）

这次“按了没有反应”不是键盘按钮问题，而是两个后端层面叠加的问题。
最后一个直接导致 FreeSWITCH 收不到包的根因是 **NAT 下的实际 UDP 目的地址错误**；
在排查过程中还确认了初版实现没有遵守 sip-bot 的 DTMF 时钟/事件重建原则。

### 1. 前端按键确实发生了，不能再用 UI mock 代替真实验证

真实 Chrome 拨打了本地 FreeSWITCH 的 `5000`：

- `sender.dtmf != null`，`canInsertDTMF=true`，PeerConnection 为 connected；
- 点击真实 `DialPad` 的 1/2/3 均调用了对应的 `insertDTMF`；
- `toneBuffer` 从空字符串变成对应数字，说明 Chrome 接受了按键任务。

所以 `DialPad.onDigit` 没有被吞，`canInsertDTMF` 也没有误拦截。
此前只跑 Pion 注入和 Vitest 就宣称功能完成，验证层级不够。

### 2. 初版没有真正复用 sip-bot 的 DTMF 数据面原则

初版把浏览器 RFC 4733 包直接转发，并在 `relayRTPWriter` 里用一个
`previous` timestamp 差值累加器同时处理普通音频和 DTMF。这隐含假设两者
时间戳时钟和时间轴可直接混用，是不成立的通用设计：普通音频可以是 Opus
48 kHz，而 DTMF 通常使用 8 kHz；浏览器现场还曾协商到 PT 110 / 48 kHz。

正确做法与 sip-bot 一致：

1. 浏览器和 SIP 两侧优先协商标准的 `telephone-event/8000`；本次 Chrome
   offer 同时提供 48 kHz 和 8 kHz，最终选择 PT 126 / 8 kHz。
2. 从浏览器音频 RTP 流中按 PT 识别 RFC 4733 payload，解析 event、END 和
   duration。一次按键的多个包共享事件开始 timestamp。
3. 三个 END 是同一事件的可靠重传，不是三次按键。按 `(code, startTimestamp)`
   去重，只把一次完整按键放入有界队列。
4. 不直接转发浏览器事件 timestamp，也不让 DTMF 改写普通音频的 `previous`。
   由 diago 在 SIP 侧重新生成标准 7 包序列（4 个 start/update + 3 个 END），
   使用 SIP 协商的 8 kHz PT、SIP 自己的 SSRC、sequence 和 RTP 时间轴。
5. DTMF writer 与普通音频 writer 共享互斥锁，生成期间串行化写入；队列满时
   丢按键而不是阻塞音频读取。SIP→浏览器 DTMF 仍不在本次范围内。

这保证了“音频 48 kHz、DTMF 8 kHz”不会在同一差值累加器里相互污染，
也避免把三个 END 当成多次输入。相关回归现在用 5 个浏览器输入包验证只产生
一次 SIP 侧 7 包事件，并检查 DTMF 前后普通音频 timestamp。

### 3. `WriteDTMF` 成功仍不代表 PBX 收到：实际 NAT 地址才是最后断点

改成 sip-bot 式重建后，日志证明三个 END 被去重且 `emit digit` 执行成功，
但 FreeSWITCH 仍然记录 `digits ''`。继续往 diago 最底层加日志才发现：

```text
MediaSession.WriteRTPRaw ... addr=192.168.254.18:18252 nat=0 learned=<nil>
```

`192.168.254.18` 是 Docker 容器私网地址。macOS 的路由把它发往网关
`192.168.10.1`，而不是本机 Docker 的 RTP 映射，所以本地 `WriteDTMF` 返回 nil
只是本地 socket 写入没有报错，并不证明 PBX 收包。

`initializeSIPMediaSession` 原先让 `RTPNAT` 保持 0。改为
`media.RTPNATSymetric` 后，diago 从 PBX 的实际来包学习可回送地址，最终日志变为：

```text
addr=192.168.10.201:64658 nat=1 learned=192.168.10.201:64658
```

这说明 SIP SDP 中的 `c=` / `Raddr` 是逻辑对端地址，不一定是 NAT 后实际可
送达的源地址。音频和 DTMF 都必须使用学习到的映射地址，不能只修事件格式。

### 4. 最终的真实 IVR 证据

启用对称 RTP 后，同一部真实 Chrome、同一个 phone tab、同一个 FreeSWITCH
`demo_ivr` 上出现：

```text
switch_rtp.c: RTP RECV DTMF 1:800
switch_channel.c: RECV DTMF 1:800
switch_ivr_menu.c: digits '1'
switch_ivr_menu.c: IVR action on menu 'demo_ivr' matched '1' ... bridge(...)
```

这才是“按键被 IVR 识别”的验证，而不是仅证明按钮、`insertDTMF` 或本地
`WriteDTMF` 被调用。测试电话随后已挂断。

## 后续复查发现与修正

1. **对称 RTP 不能学到 demuxed video 的地址。** 初版全局启用对称 RTP 后，
   diago 会让任意 version-2 RTP 包更新 `learnedRTPFrom`。音视频目的地址不同
   时，视频包就可能把后续音频/DTMF 导向 video peer。vendored diago 新增可选
   `RTPNATPayloadTypes`：raw read 和 parsed read 的第一来源 CAS 都只允许配置
   的 PT 更新来源；nil/empty map 保持上游行为。`initializeSIPMediaSession`
   只把普通音频和 telephone-event 加入允许列表。回归在收到 demuxed video 后
   再发浏览器音频，证明它仍到 audio peer；vendored 测试证明 video PT 不会
   成为回送地址。
2. **连续按键不能共用事件开始 timestamp。** diago 的 `WriteDTMF` 每包都以
   0 增量写时间戳，连续调用而没有音频插入时，第二个事件会复用第一个事件的
   开始时间。`relayRTPWriter` 现在在连续事件之间按“800 units at 8 kHz”换算
   成主音频时钟推进开始时间（Opus 下为 4800），并记录补偿；音频恢复时先减去
   累计补偿，再使用原音频 timestamp delta，避免双重累计。回归对同一数字连按
   两次，验证两组 7 包事件的开始时间分别为 1000 和 5800，后续音频为 12000。
3. 后台 worker 只在所有可能失败的 relay setup 完成后启动，避免视频 setup
   失败时泄漏 `sendDigits` goroutine。临时 `[dtmf-debug]` 输出和 scratch 日志
   均已移除，vendored 仅保留正式的 Patch 9 过滤器与文档。
