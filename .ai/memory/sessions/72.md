## Current status

## Runtime evidence

- Both same-domain credentials registered over TCP. A controlled 1234-to-1235
  INVITE at 16:23 UTC preserved the target, completed the 407/digest sequence,
  then SignalWire returned `500 Internal Server Error` about 14 seconds after
  the initial request with `Reason: Q.850;cause=16;text="NORMAL_CLEARING"`.
- The callee's actual TCP listener was `152.53.46.158:44071`, confirmed by
  `ss -ltnp`. Its authenticated REGISTER instead advertised Contact port
  `41192`. Nothing listened on 41192; it was only the local source port of the
  outgoing TCP connection to the registrar.
- No provider INVITE reached the callee's real listener during the call. The
  caller's own Contact, by contrast, referred to its actual listening socket.
- `third_party/diago/register_transaction.go:169-187` explains the mismatch:
  after the first response, it unconditionally replaces Contact's host/port
  with Via `received`/`rport` before the digest retry. On UDP that source port
  is also the UA socket; on TCP it is an ephemeral outbound connection port,
  not the listener created by diago.

## 2026-11-25 follow-up: dynamic SIP-side SRTP

### Request and verified implementation facts

The user asked to continue this session and determine whether SIP-side SRTP can
be enabled dynamically from SDP.

- The browser leg already uses Pion ICE + DTLS-SRTP. The missing piece is the
  separate SIP leg; no browser SRTP bypass or payload forwarding is involved.
- Vendored diago already implements SDES-SRTP for `RTP/SAVP` in
  `media.MediaSession`: `RemoteSDP` creates the receive context from
  `a=crypto`, `LocalSDP` creates a fresh send context/key, and RTP/RTCP read and
  write paths apply decryption/encryption.
- The user gateway cannot merely set `MediaSRTP=1`: `pkg/sipregistration`
  creates each `MediaSession` itself and pins custom audio/video SDP through
  `InitWithSDP`, bypassing diago's own SDP generator. Its SDP parser currently
  rejects every profile except `RTP/AVP`.
- RFC 4568 requires SDES crypto only with a secure RTP transport, a fresh key
  from each sender, and the selected offer tag/suite echoed in the answer.
  `RTP/SAVP` without a usable crypto attribute must fail rather than silently
  send plaintext.
- Offer/answer imposes an outbound boundary: an initial `RTP/AVP` offer cannot
  later acquire SRTP merely because the peer prefers it, and an answer cannot
  legally switch that offer to `RTP/SAVP`. Always offering SAVP would regress
  existing plaintext-only peers. This follow-up therefore targets the observed
  provider-to-service inbound SAVP offer; outbound initial offers remain AVP
  unless a separate secure-offer policy/capability-negotiation design is added.
- Diago's single pair of SRTP contexts belongs to one `MediaSession`, while the
  gateway uses that session for shared audio/video RTP. The initial scoped
  implementation will negotiate SRTP for audio-only calls and reject active
  secure video explicitly rather than reuse one key incorrectly across m-lines.
  Plaintext audio/video behavior is unchanged. DTLS-SRTP, SAVPF, MKI/lifetime,
  and non-default crypto suites remain outside this patch.

### Plan

1. Extend the SIP SDP model/generator to retain and emit `RTP/AVP` or
   `RTP/SAVP` plus a validated local `a=crypto` line. Keep browser SDP parsing
   and codec matching unchanged.
2. In `newInboundSIPMedia`, select SDES only when the inbound audio offer uses
   `RTP/SAVP`. Apply the original offer through diago to create the receive
   context, ask diago for its local SDES answer to create a fresh send context,
   extract only the media profile/crypto attribute, then pin the gateway's
   existing codec/direction answer with those fields. Do not log key material.
3. Reject missing, malformed, unsupported, or mismatched SDES negotiation and
   active secure video with explicit errors. Keep all plaintext offer/answer
   generation byte-compatible apart from the refactored internal parameters.
4. Add focused SDP and media tests: SAVP parsing, plain-versus-secure answer
   profiles, selected crypto tag/suite and distinct send key, missing/invalid
   crypto rejection, and actual encrypted RTP in both directions against an
   independent diago SRTP peer. Run the new media test before the fix where
   practical to record the current failure.
5. Run focused and full `pkg/sipregistration` tests with race detection, the
   nested diago media tests, root tests/build, and diff checks. Update
   `docs/user-sip-subsystem.md` and this note with exact validation and any
   remaining outbound/video/DTLS limitations.
6. If local validation passes, use the established deployment path to test the
   original same-domain provider pair without changing its encryption setting.
   Claim live success only if the provider INVITE receives a valid SAVP answer,
   the browser call is accepted, and encrypted media/cleanup are observed.

### Remaining boundaries

- Outbound initial SIP offers are still RTP/AVP. Supporting secure outbound
  offering requires a separate policy or standards-based capability
  negotiation; answering an AVP offer with SAVP is not a valid shortcut.
- SRTP is currently inbound audio-only with bare-inline
  AES_CM_128_HMAC_SHA1_80. Active SRTP video, DTLS-SRTP/SAVPF, other suites,
  lifetime/MKI, and SDES session parameters are rejected or unsupported.
- SDES keys inherit SIP signaling security. SRTP over plaintext UDP/TCP
  signaling does not keep those keys secret from network observers; protected
  signaling is required for that confidentiality guarantee.
