## Request and status

In progress. Fix the incoming-call window's overflowing caller text. Present the caller in a way that exposes the complete display name and SIP AOR, including long AORs, and handle WebRTC callers whose identity is only a name rather than a full SIP URI.

## Scope

Inspect the shared incoming-call window and both SIP/WebRTC caller-data paths, implement focused presentation/data changes, add regression coverage for long and name-only identities, and run targeted plus appropriate broader frontend checks.

## Verified findings

- `IncomingCallWindow.tsx` applies `noWrap` to a single caller-name line inside a 264px-wide flex column. A long SIP URI therefore remains at its intrinsic width and is clipped by the paper's `overflow: hidden`.
- `ChatApp.tsx` constructs the SIP popup's synthetic user with `remoteUri` as its name, so the popup currently has no distinct display-name/AOR presentation.
- The backend does not send a caller display name at all. `serveInboundInvite` passes `request.From()` to `sipHeaderURI`, which retains only `Address.User` and `Address.Host` via `canonicalAOR`; `FromHeader.DisplayName` is discarded. Keeping the AOR canonical is appropriate for routing/conversation identity, but SIP does not require discarding the optional display name from presentation metadata.
- WebRTC calls use the existing `ChatUser.name`; their identity need not be a SIP URI. The shared UI must therefore treat the secondary AOR as optional.

## Plan

1. Add optional `remoteName` metadata to the SIP call wire/model types. Capture `From.DisplayName` for inbound calls, retain it on `serviceCall`, include it in every event emitted by `eventFor`, and preserve it across sparse frontend call-event reductions. Leave `remoteUri` canonical and unchanged.
2. In `ChatApp`, prefer `remoteName` for the SIP synthetic caller while retaining the existing URI/target/call-id fallbacks. In `IncomingCallWindow`, render the caller name prominently and the SIP AOR as a smaller `user@host` caption without the URI scheme. With no display name, promote the AOR's `user` portion to the main name while retaining the full AOR caption. Name-only WebRTC/SIP identities render no AOR caption.
3. Replace single-line clipping with a constrained, centered identity block whose name and AOR wrap at arbitrary characters when necessary. Use `subtitle1` for the name and `caption` for the AOR, and slightly widen the popup responsively without allowing viewport overflow.
4. Add backend wire/inbound metadata tests and frontend reducer/identity presentation tests. Run focused Go/Vitest tests, broader relevant suites, TypeScript, lint, formatting/diff checks, and browser layout inspection if the local app/test call path is available.

## Outcome

Complete (2026-11-25).

### Changes

- `pkg/models/ss/ss.go` adds optional `remoteName` to SIP call events. `pkg/sipregistration/service.go` captures `From.DisplayName` on inbound INVITEs, retains it on the call, and emits it alongside the unchanged canonical `remoteUri` on ringing and later sparse state events. This fixes the application-level display-name loss without changing routing/conversation identity.
- `web/site/src/api/ss/types.ts` and `sip.ts` carry and preserve `remoteName` in the frontend call model/reducer.
- `web/site/src/components/chat/incomingCallIdentity.ts` resolves presentation separately from the canonical URI. A display name is preferred; otherwise the AOR user becomes the main name. The secondary AOR is the complete `user@host`, with `sip:`/`sips:` removed only for display. A name-only identity produces no fabricated AOR.
- `ChatApp.tsx` uses that identity for the SIP caller/avatar. `IncomingCallWindow.tsx` renders a 16px `subtitle1` main name and a 12px `caption` AOR. Both use `overflowWrap: anywhere`; the old `noWrap` clipping is gone. The popup is 320px wide with a viewport-relative max width.
- Added backend wire/inbound lifecycle coverage plus frontend reducer and four identity tests for long AORs, missing display names, scheme-less AORs, and name-only callers.

### Remaining blind spots and notes

- No new live SignalWire INVITE was sent after the backend change. The running backend process was not restarted, so end-to-end display-name delivery still needs a rebuilt/restarted backend for a live call. Wire, service lifecycle, reducer, identity, and real browser presentation were tested separately.
- The separate legacy SIP-bot inbound path rings a bot-owned WebRTC conversation and does not use the external-SIP `remoteUri` popup identity; its call model was intentionally left unchanged in this scoped fix.
- Pre-existing user changes in `README.md` and `web/site/next.config.ts` were not modified.
