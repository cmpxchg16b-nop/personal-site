  `BinaryTransport` and the page passed it into

## PeerSessions API (peersessions.tsx)

- Data channels are DEMANDED BY LABEL: `subscribeChannel(label, cb)`
  registers a consumer; every session brings up one channel per
  subscribed label — the polite peer creates it (first creation starts
  negotiation), the impolite peer receives it via ondatachannel
  dispatched by label. cb fires for existing sessions' channels too
  (late subscriber catches up); channels live and die with their
  session (unsubscribe never destroys them).
- `getChannel(label, channelId, peer)` — sync, any readyState (sendTo's
  drop-with-warning path). `whenOpenChannel(label, channelId, peer)` —
  parks until open, resolves null when the session goes away first;
  waiters are keyed peerKey → label → resolvers (nested map, since one
  session now carries waiters of several labels).
- `subscribeReset(cb)` — per-session drop or null for the full
  teardown; unchanged semantics.
- PeerSession now: pc, channelId, peer, polite, channels (Map label →
  RTCDataChannel), createChannel(label) (polite-only, no-op if
  present), close(). startPeerSession's attach() registers the channel,
  hooks its open event for the waiters, then notifies the label's
  subscribers.

## Why a shared layer, not one connection per hook

- The session-7 constraint still holds: PerfectNegotiator filters c2c
  signalling by (channelId, from, to) ONLY, so two peer connections per
  pair (one per hook) would cross-wire each other's SDP offers. One
  connection per pair stays mandatory short of a c2c protocol change;
  the decoupling happens above it. Wire behavior is unchanged: same two
  labels, same polite-creates rule, same frames.

## Gotchas

- Effect ordering does the channel creation: on mount, reconcile may
  create sessions with no labels subscribed yet; useDataChannel's and
  useBinaryDataChannel's subscribeChannel effects then create `dcmsg`
  and `dcbin` on the polite sessions in the same task — one
  negotiation, both channels (onnegotiationneeded batches). When ICE
  servers settle late, reconcile runs with the labels already
  registered and creates both at session start. Symmetric, no races.
- Identity change: usePeerSessions' teardown ([proxy, me] cleanup)
  closes everything and releases waiters with null; the consumers'
  re-subscribe (deps include me?.subscriberId for the echo check)
  rewires the rebuilt sessions. React runs all cleanups before all
  setups, so the reconcile rebuilds with an empty label map and the
  consumer setups re-demand their labels — same commit, fine.
- useDataChannel still takes `me` (not just sessions): the echo
  sanity check (echo must name us as sender) needs our subscriber id.
