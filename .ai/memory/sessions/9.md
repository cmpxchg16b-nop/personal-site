# Session 9

## Voice calls (phone sessions) — overview

- Voice chat built on the existing per-pair peer connections. No
  dedicated RTCPeerConnection: `PeerSessions` gained `addTrack` /
  `removeTrack` / `subscribeTracks` (multiplexed `pc.ontrack`), and the
  PerfectNegotiator renegotiates on its own when tracks come and go —
  including the glare of both ends adding their mic near-simultaneously
  on call accept.
- One phone session per (channel, subscriber) pair, managed entirely at
  the application level and decoupled from the connection's own
  signalling state: the connection outlives calls, a call never creates
  or closes one.

## USER CORRECTION: chat control is the RESULT, never the CAUSE

The user's design principle, stated explicitly and to be followed
everywhere in this codebase:

> **Chat control is for modifying the _UI state_ of a phone session /
> file transfer / text message. Chat control itself is NOT for
> accepting / rejecting the session, nor does it convey the action of
> such behaviors (invite / accept / reject). UI state is the dependent
> variable; the action of invite / accept / reject itself is what causes
> the UI to change. Chat control is the result — you send one when you
> want the UI state to change _because of something_ — not the cause.**

The user's two canonical examples:

1. Text edit: a message with msg_id=2 displays "Hi" and you want both
   ends to display "Hello" — send a chat control to amend it. Fine:
   nothing but the display changed, so a pure UI-state mutation is the
   right tool.
2. Phone session: the status indicator shows "inviting", and you are
   informed **from somewhere else** (the session protocol's accept
   frame, not a chat control) that the peer has accepted your
   invitation. Now you want both ends' indicators to show "accepted":
   you send a chat control to amend the UI state of the status
   indicator. The accept itself traveled as its own protocol frame; the
   chat control merely propagates its consequence to the UI.

Corollaries this implies, all enforced in the implementation:

- **Actions are their own frames.** invite / accept / reject / cancel /
  end are a dedicated protocol (`application/x-phone-session` +
  `application/x-phone-session-event`), exactly as the file transfer's
  progress is driven by the `dcbin` FILE/FACK frames and not by chat
  control. The protocol drives the real per-(channel, subscriber)
  session state machine; media attach and the live indicators read it.
- **UI state follows, never leads.** The invitation message's stored
  `status` (what the log entry renders) changes only via chat-control
  amends, and only AFTER the protocol state caused it. An amend never
  performs an action — it reports one.
- **The owner reports.** The invitation's author (the caller) is the
  single writer of its UI state: it observes the protocol events (the
  accept/reject/end frames arriving, its own cancel/end echoed) and
  issues the amends. Chat control's own-messages-only rule therefore
  needs no exception. Both logs stay identical via the usual echo
  application.
- **Test for correctness of the split:** if removing chat control
  entirely would still leave the BEHAVIOR correct (the call rings,
  connects, ends; media starts and stops) and only the rendered
  statuses would go stale, the layering is right. Behavior must never
  depend on a chat control arriving.

The first cut of this session violated the principle (the callee's
accept WAS a chat-control amend, with cross-party target lookup and a
store-level precedence rule to make it safe) and was reworked into the
two layers below.

## Wire protocol (datachannel.tsx)

Two new DCMsg kinds ride `dcmsg` like any other message (and are echoed
like any other, so each end stores every frame exactly once):

- `application/x-phone-session` — body `phoneSession {sessionId,
status}`. THE INVITATION: the caller sends it with a fresh UUID
  sessionId and `status: "inviting"` (the builder takes just the
  sessionId). It is a stored message — the call's log entry in the
  history — and its arrival is simultaneously the invite ACTION (it is
  what rings the callee). `status` is the session's UI state (see the
  principle above): it starts "inviting" and is amended in place via
  chat control as the session's events unfold.
- `application/x-phone-session-event` — body `phoneSessionEvent
{sessionId, action}`, `action ∈ accept | reject | cancel | end`. The
  session protocol's actions: the callee answers with `accept` /
  `reject`, the caller aborts the ring with `cancel`, either party hangs
  up an accepted call with `end`. Never rendered; never amended. They
  ARE stored in the raw `dcMsgs` store (they are the fold input), but
  `useChatMessages` skips them explicitly (otherwise they'd fall into
  the text branch and render as empty lines).

Statuses: `inviting` (ringing) → `accepted` (media flows) →
`rejected` / `cancelled` / `ended` (terminals). Chat-control amends
carrying `phoneSession` target the invitation; the store validates the
body, requires the target to be a phone-session message, and requires
the amend's `sessionId` to match the invitation's — plus the unchanged
own-messages-only rule.

## Session model (usePhoneCalls)

`usePhoneCalls(me, dcMsgs, sessions, sendTo, audio)` → `{calls,
startCall, acceptCall, rejectCall, hangupCall}`. There is no separate
session store: the model is derived from `dcMsgs` (the raw frame
store), not from the UI messages:

1. Collect each conversation's phone frames — invitations and events —
   from both parties' sender lists (the peer's sends, plus our own
   list's echoes; the conversation's peer is `fromSubscriberId`, or
   `toSubscriberId` for echoes).
2. The current session is the LATEST invitation; earlier ones are
   terminated calls' log entries.
3. Fold the session's events into its protocol state as the PRECEDENCE
   MAX over `inviting(0) < accepted(1) < ended(2) < cancelled(3) <
rejected(4)` (each action maps to the state it establishes). Both
   ends see the same frame set (own frames via echo, the peer's
   directly) and the fold is order-independent, so the ends converge —
   a cancel/accept race settles to `cancelled` everywhere, and a
   terminal session is never revived.
4. `calls` (the exposed map) is the subset still `inviting` or
   `accepted`, minus the dead-session overlay (below). Live UI and
   media read this; terminal sessions remain visible only as log
   entries.

The UI-state reporter: an effect compares each session we OWN (we are
the caller) — protocol `status` vs the invitation's stored
`loggedStatus` — and sends a chat-control amend for the difference.
Self-terminating: the amend's echo removes the drift. Only the owner
ever amends (the principle's "you are informed from somewhere, so you
update the UI state").

Dead-session overlay: `sessions.subscribeReset` force-ends the dropped
peer's live calls LOCALLY (a `deadSessions` set consulted by the
derivation) — a gone peer can no longer exchange the protocol, so
neither the model nor the log can be updated on the wire; the log entry
keeps its last logged status (documented cosmetic wart).

The action senders just emit frames (`audio.resume()` inside the
startCall/acceptCall click gestures — see the audio graph); the local
state moves when the echo comes back, keeping the codebase's
echo-discipline invariant. `startCall` no-ops while a call with the
peer is live.

## Media (useCallMedia)

`useCallMedia(sessions, audio, calls)` → `{localAnalyser,
remoteAnalyserFor}`:

- While a call's protocol state is `accepted`: `audio.acquireLocalInput()`
  → the graph's processed mic track is `sessions.addTrack`ed onto THAT
  PAIR'S existing connection (the stream argument keeps the remote's
  `ontrack` stream association). Any other state: `removeTrack` +
  `audio.removeRemote` + `audio.releaseLocalInput()` — every attachment
  holds the mic capture and every detach releases it, so the capture
  stops with the last accepted call (see the audio graph's holds). Both
  abort paths of the async attach (the effect re-ran mid-open; addTrack
  unavailable) release their hold too. Attach/detach is a pure effect of
  the derived state; a `mediaVersion` bump keeps render-time analyser
  reads reactive (filesVersion-style).
- `subscribeTracks`: every inbound audio track connects into the audio
  graph under its pair key (`${channelId}:${peer}`).
- Glare: both ends addTrack on accept (the callee on its accept echo,
  the caller when the accept frame arrives) — two near-simultaneous
  offers; perfect negotiation resolves it (polite rolls back).
- Mic-permission failure logs and leaves the call accepted-but-silent.
- Repeated calls accumulate inactive m= sections (removeTrack doesn't
  recycle the transceiver) — demo-acceptable, replaceTrack is the noted
  follow-up.

## Audio graph (api/audio/audiograph.tsx)

- Module-level singleton `AudioGraph` + `AudioGraphProvider` in
  chat/layout.tsx (SSProxy pattern), but released on unmount so leaving
  /chat never leaves the mic open; a return mounts a fresh one.
- Local chain: one shared mic capture → gain (the mic send volume) →
  analyser (the local FFT tap) → `MediaStreamAudioDestinationNode`; ITS
  track is what peer connections send (one track, any number of
  connections). The local voice therefore passes the graph before the
  wire.
- The capture is REFERENCE-COUNTED: `acquireLocalInput()` takes a hold
  and `releaseLocalInput()` balances it (`localInputHolds`); the last
  release stops the mic tracks and tears the local chain down. It opens
  with the first attached call and stops with the last — the browser's
  per-tab recording indicator therefore lights exactly while a call is
  sending. (Before this, hangup only did `removeTrack` and the mic
  stayed open until leaving /chat: the stuck "recording" tab badge
  bug.) The hold is counted BEFORE the await, so acquisitions sharing
  one pending getUserMedia are all counted before any release can run.
  Guard: if the graph was released while the permission prompt sat open
  (`this.ctx !== ctx` after the await), the just-opened stream is
  stopped immediately instead of leaking.
- Remote chain: per-peer `MediaStreamAudioSourceNode` → analyser (the
  remote FFT tap) → ONE shared remote gain (the speaker volume) →
  `ctx.destination`. Several accepted calls mux at that gain node —
  by design, multiple peers' tracks are connected at once. Remote audio
  passes the graph before the speaker.
- Echo cancellation is OPTIONAL and OFF by default (headphones
  assumed): the call audio menu's toggle switches the capture-side
  voice processing (`echoCancellation` + `noiseSuppression` +
  `autoGainControl`, one bundle) on — live via
  `track.applyConstraints()` on the open mic, and via the constraints of
  future captures (`captureConstraints()` feeds both paths). When on, it
  is the capture-side browser AEC cancelling against the default output
  device — exactly where the graph plays (`ctx.destination`) — so the
  peer's voice coming out of the speaker is cancelled out of the mic
  instead of transmitted back. GOTCHA: browsers turn the processing ON
  when the constraints are merely OMITTED, so "off" must pass explicit
  `false`s. The graph keeps the setting as a plain field like the
  volumes (survives capture teardowns, pre-sets the next call);
  `useEchoCancellation(audio)` mirrors `useCallVolumes`.
- `resume()` creates/resumes the AudioContext and is called inside the
  call/accept CLICK handlers (autoplay policy); the caller's gesture at
  invite time is what lets media start later when the accept arrives
  with no gesture on that end. Analysers: fftSize 2048,
  smoothingTimeConstant 0.8.

## UI map (what reads which state)

- **Live indicators read the protocol state** (`calls`): the
  IncomingCallWindow (global, floating, draggable by its handle strip,
  pointer-capture based; the ONLY place to accept/reject — latest
  ringing incoming call), the sidebar member pills (ringing pulses,
  in-call steady; display-only), the conversation header button
  (ring → hangup/cancel; incoming-ringing → disabled; offline peer →
  disabled), and the CallPanel strip (ringing text + cancel for the
  caller; hint-only for the callee; in-call: remote spectrum over local
  spectrum + duration + hang up).
- **The log entry reads the UI state** (the invitation's amended
  `status`): PhoneCallItem — icon per status, "Outgoing/Incoming call",
  "In call", "Call ended", "Call declined", "Call cancelled" (own) /
  "Missed call" (theirs). Breaks text runs like transfers do.
- CallPanel's duration counts from when the PANEL first observed
  `accepted` — the wire keeps no accept timestamp; remounting restarts
  it (documented).
- VolumeControl (the call audio menu): mic and speaker sliders over
  `useCallVolumes(audio)` → the graph's two gain nodes, plus the
  echo-cancellation switch over `useEchoCancellation(audio)` (no divider
  between them — user correction). It lives in the TOP BAR, not the
  sidebar: the chat page portals it in via TopBarActions and renders it
  ONLY while a call session is live (`calls` non-empty — ringing or in
  call). Adjustments apply live; the graph keeps the values, so they
  also pre-set the next call.
- TopBarActions / TopBarActionsHost (src/components/TopBarActions.tsx):
  the portal bridge through which a page contributes contextual controls
  to the TopBar (so far just the chat page's VolumeControl). The host —
  an empty slot between the breadcrumb spacer and ProfileMenu,
  zero-width when unused — registers its element via callback ref into
  a module-level holder; TopBarActions subscribes with
  useSyncExternalStore and portals its children in, whatever the mount
  order. The TopBar never learns what it is showing; the portal
  unmounts with the page or the gating condition (the call ending).
- AudioSpectrum: canvas, rAF, 48 buckets averaged over the lower 3/4 of
  FFT bins (voice energy), midpoint-quadratic smoothing, stroke +
  translucent fill; null analyser = flat baseline.
- i18n: `chat.call.*` and `chat.volume.*` in en/zh.

## Gotchas

- The react-hooks lint rule bans ref reads during render: the popover
  anchor and the dead-session overlay are useState, not refs
  (refs-in-render only inside effects/handlers).
- React 19's useRef requires an initial value (no zero-arg calls).
- magic.ts's amend-file-transfer branch must exclude the new phone-call
  message type from the transfer-backed union.
- Crossed calls (both ends invite simultaneously): the LATEST invitation
  is the current session; the loser's log entry lingers at "inviting"
  (cosmetic, unreachable via the UI's guards).
- The `react-hooks/set-state-in-effect` lint rule bans synchronous
  setState in an effect body: looking up a DOM host on mount is done
  with useSyncExternalStore over a callback-ref-fed module-level holder
  (see TopBarActions), NOT useEffect + useState.
- Browsers enable the capture-side voice processing when getUserMedia
  audio constraints are merely OMITTED — disabling it takes explicit
  `false`s (`captureConstraints()`).
- The terminal tool's "authorization channel closed" flake recurred;
  retrying worked. Pre-existing prettier warning in
  src/components/HeroSection.tsx is NOT ours (unmodified in git).
